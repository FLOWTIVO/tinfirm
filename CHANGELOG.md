# Changelog

Every release of Tinfirm, newest first. The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and versions follow [Semantic Versioning](https://semver.org/). A release is cut by hand with `.github/workflows/release.yml`, which dates the section of its version in the release commit; its GitHub Release carries that section.

The server, the web app, the Helm chart and the runner host carry the release's version. The runner host and the server agree on the runner protocol and its features, never on a version number ([ADR-0109](docs/adr/0109-runner-version-is-the-release-version.md)).

Between releases, `main` is a development channel, not a release: the images tagged `sha-<commit>` and `main`, the charts `0.0.0-sha-<commit>` and the prerelease `rolling` ([README](README.md#status)).

## [1.0.0-rc.1] - 2026-11-09

The first release candidate of 1.0.0, built from the same code as 1.0.0 to test the release itself before the final version: the gate, the signed images and chart, the runner host binaries and the Compose tarball, and their signed `SHA256SUMS`. It contains everything described under 1.0.0 below. Install 1.0.0, not this candidate.

Fixed after this candidate: a run over the sandbox bridge could lose its work and fail with `GIT_ERROR`, "the sandbox's bridge is gone", after 30 s, when its agent ended at the moment the host stopped it. The sandbox's bridge now ignores a stop that comes after the agent has ended, and ends only when the host closes the session. A VM sandbox has the fix once its image holds a runner host of 1.0.0. And a runner host with a VM per run that restarted while its own VMs still held its driver's room, the runs it was about to take back or leftovers, refused to start, because that room no longer covered its `--max-concurrent-runs`; the start check now counts the host's own VMs. A request whose query string or form body was not valid UTF-8, held a malformed escape or had more than 1000 parameters answered 500, or Spring Boot's own error page on the sign-in and OAuth endpoints; it now answers `400 VALIDATION_FAILED` as a problem that never quotes the input, and SCIM answers `invalidSyntax`. A NUL character (U+0000) in a search, a JSON string, a form field or a file name reached the database and answered 500; every such request now answers `400 VALIDATION_FAILED`, a secret's value and a JSON body in UTF-16 included, and the MCP endpoint answers it as a JSON-RPC error. An upload over the file limit closed the connection instead of answering `413 ATTACHMENT_TOO_LARGE`, and a runner host's upload over the limit answered 500; for an authenticated caller the server now reads such an upload to its end, throws it away and answers 413, up to the new `TINFIRM_ATTACHMENT_MAX_DRAIN_SIZE` (64MB). An anonymous multipart request to the web app's paths, to the sign-in endpoints or to the authorization server was read and parsed in full before it was refused; a multipart request is now taken under `/api/**` alone and needs the `X-XSRF-TOKEN` header, as the web app sends it, or it is refused unread (403 without the header, 415 anywhere else). A runner host that died hard (a `kill -9`, the OOM killer, a power loss) after a run's agent had ended its turn, before the run's report reached Tinfirm, lost the run: Tinfirm marked it lost, and its work stayed unpushed on the host. The host now keeps the run's record, and then its report, until the report has been written to the server (and, but for an orderly stop, the connection stayed up for 3 minutes after it); its next start pushes the work, saves `/output` and the session, and reports the run with its agent's outcome. A run that leaked a credential value still sends nothing out after a restart. Under many concurrent requests a server could stop answering until its database pool's wait of 30 seconds ended, and then answer 500: some requests held one connection while they asked for a second, to record OWNER's read of another person's conversation or an instance admin's access to a company, to apply the declared companies after a sign-in, to delete a user's other sessions, or for other work after a commit. Such work now runs once the request's own transaction has released its connection, still before the request is answered: a read is on record before anything of it is returned, and the record of an action on another person's conversation, or of an instance admin's change, is written right after the action's commit. Work done after a commit could be lost without a trace: the roles SCIM no longer decides were not released when a new licence key took effect, a Slack system's Socket Mode slot was not released when its transport changed, and a runner host disconnected by the server did not record its disconnect. Each now runs in a transaction of its own. A request that finds no free database connection in time now answers `503 SERVER_BUSY` with `Retry-After` when it is a read, or a write before any change of it was saved; its authentication, authorization and access records do not count as its change. A write in which a change may already be saved answers 500, without `Retry-After`, with the detail "The request did not finish, but a change of it may already be saved. Look at the result before you send it again."; an MCP tool's error carries the same text. The wait stays 30 seconds (`SPRING_DATASOURCE_HIKARI_CONNECTION_TIMEOUT`). When the database pool was exhausted, Spring Session's save while a large answer was written made a read answer `500` "Failed to write request"; such a read is now answered `503 SERVER_BUSY`, and such a write with the 500 that says a change may already be saved. An answer that was complete when the session could then not be saved, for want of a database connection, was cut off by the server; it is now kept whole, with a warning in the log. A request that is answered busy no longer waits for the pool again for its session, and logs one line. A run cancelled because its user was suspended or deactivated has its git access revoked before the runner host hears the cancel, so it no longer pushes their work. A deactivated user's run says why its commits were not pushed ("the account's holder was suspended because their Tinfirm account was deactivated"), and the binding's card says who is suspended and what lifts it: an admin, an instance admin's reactivation of the user, or the company's identity provider.

### What 1.0.0 is

A self-hosted platform on which a company runs AI agents: people talk to them, triggers start them from the company's systems, each run works in a sandbox with the accounts its audience allows, and every decision that needs a person comes to one inbox ([PLATFORM.md](docs/PLATFORM.md)).

- **Agents and conversations.** Agents are definitions that hold no credentials, shared with groups and members, each person's settings narrowing them; the runtimes Claude Code, Codex, pi and OpenCode. Conversations with live transcripts, steering a running turn, questions, approvals and outputs, automatic retries (a turn whose runner host restarted before its agent got a prompt is started again by itself, at most three times in a row, also when its owner did not choose them), agent memory and a skills library ([ADR-0058](docs/adr/0058-authority-from-the-audience.md), [ADR-0060](docs/adr/0060-steering-a-running-turn.md), [ADR-0063](docs/adr/0063-agent-memory.md), [ADR-0064](docs/adr/0064-skills-library.md), [ADR-0073](docs/adr/0073-automatic-retries.md)).
- **Systems and triggers.** Jira Data Center and Cloud (Cloud service accounts by client credentials), GitHub, GitLab, git hosts and MCP servers, the company's, members' own and servers that need no account; triggers on tracker issues and change requests by polling, on schedules, chat channels and a generic webhook, with the outbox and the write-back; credentials on systems lent to groups and service accounts; internal hosts ([ADR-0071](docs/adr/0071-mcp-servers-without-accounts.md), [ADR-0072](docs/adr/0072-system-credentials-lent-to-groups-and-service-accounts.md), [ADR-0093](docs/adr/0093-jira-cloud-service-accounts-by-client-credentials.md)).
- **Chats.** Slack and Microsoft Teams: direct messages to the bot and channel triggers.
- **People's own AI clients and email.** The MCP endpoint, with Tinfirm as the OAuth 2.1 authorization server and personal access tokens; the Outlook add-in and the Gmail add-on, with an email's attachments and Gmail's draft replies ([ADR-0074](docs/adr/0074-outlook-add-in.md), [ADR-0083](docs/adr/0083-gmail-add-on.md), [ADR-0084](docs/adr/0084-email-attachments-and-gmail-drafts.md)).
- **Model access and budgets.** LiteLLM bundled, a key and a budget per principal, the company's own model key, more than one model gateway with keys a gateway team provides, and the server's model relay, which no provider-run tool passes ([ADR-0059](docs/adr/0059-litellm-budgets-and-the-model-proxy.md), [ADR-0094](docs/adr/0094-more-than-one-model-gateway.md), [ADR-0108](docs/adr/0108-no-provider-run-tools.md), [ADR-0110](docs/adr/0110-no-model-port.md)). Spend views and budget alerts.
- **Governance and audit.** The hash-chained audit with its daily check, retention, legal holds and erasure, kill switches, suspension, members who leave, error reports ([ADR-0070](docs/adr/0070-error-reports.md)). For Pro and Enterprise, the audit chains' heads anchored outside the database: signed checkpoints to a bucket with object lock, a directory or syslog, compared by the daily check and by the offline tool `tinfirm-audit-verify` ([ADR-0111](docs/adr/0111-audit-chain-heads-anchored-outside-the-database.md), [Anchor the audit](docs-site/content/operator-guide/audit-anchor.md)).
- **Sign-in.** Local sign-in, OIDC, SAML and SCIM provisioning; companies and their sign-in declared by the deployment; roles and companies from the identity provider ([ADR-0075](docs/adr/0075-companies-and-sign-in-from-the-deployment.md), [ADR-0086](docs/adr/0086-saml-sign-in.md), [ADR-0087](docs/adr/0087-scim-provisioning.md), [ADR-0088](docs/adr/0088-roles-from-the-identity-provider.md)).
- **Runner hosts.** Company and personal hosts in every company, with Docker or Kata Containers sandboxes, runner protocol 2, a model proxy that keeps a run's model token out of the sandbox, and a member's Claude login on their host. The sandbox bridge and a VM per run with a VM driver of your own are in every edition; elastic runners for Pro and Enterprise are DigitalOcean's VM driver, ready VMs on a schedule and session bundles. A host reports its level of isolation in `hello.isolationTiers` (`machine`, `vm-jail` or `container`; a Kata host reports `container`), and an agent's runs go to the strongest level its company's hosts report, or to the level chosen for the agent, and never to a weaker host by themselves; a member's own host takes their runs at that level or a stronger one. With the bridge, the archives and git bundles a sandbox sends back are read in a confined process per reading that holds no credential, not in the host's own process; such a reader can neither signal nor limit a process outside its own process group, on any kernel. The host reads a Codex login's `auth.json` only as a regular file of at most 256 KiB, never through a link (path C of [ADR-0112](docs/adr/0112-no-credential-on-a-sandbox-machine.md), Proposed; [runner/README.md](runner/README.md#the-reader-and-the-front)). The model proxy, the git proxy and the platform tools bound a request's head: 64 headers, names of 64 bytes, values of 8 KiB and 24 KiB in all (`431`), and a query of 4 KiB (`414`); header values pass byte for byte, and a body whose length differs from its head gets `400` ([ADR-0085](docs/adr/0085-claude-login-on-the-runner-host.md), [ADR-0092](docs/adr/0092-personal-runner-hosts-in-every-company.md), [ADR-0095](docs/adr/0095-sandbox-bridge.md) to [ADR-0100](docs/adr/0100-elastic-runners-in-pro.md), [ADR-0113](docs/adr/0113-levels-of-isolation-and-placement.md), [ADR-0114](docs/adr/0114-the-secure-sandbox-is-in-the-core.md)).
- **A bridge port per sandbox** (path C of [ADR-0112](docs/adr/0112-no-credential-on-a-sandbox-machine.md), Proposed; [Runner hosts](docs-site/content/operator-guide/runner-hosts.md#the-sandbox)). On a Docker host with the sandbox bridge, each sandbox's bridge has a listener of its own on the sandbox network's gateway address, on a port the system picks or one of the new `run --sandbox-bridge-ports FROM-TO` (`TINFIRM_RUNNER_SANDBOX_BRIDGE_PORTS`; the Ansible role's `tinfirm_runner_host_sandbox_bridge_ports`). The range must hold a port for each run at once: a run that finds none free fails. The host opens no listener for the git proxy, the tools, the model proxy or the egress proxy any more: the sandbox reaches them through tunnels inside its bridge. A host firewall between the sandbox network and the gateway address admits TCP to the bridge ports (the range, or the system's `net.ipv4.ip_local_port_range`), where it admitted one shared bridge port and the proxies' ports before; during the first start after the upgrade, the old shared port (kept in `runs/bridge.json`) is opened once more, only while the runs of the release before are taken back. A run's record (`runs/<run>.json`, mode 0600) now holds its bridge's TLS identity, port and peer. A host with VMs gives each VM a front of its own too, and still dials each VM and listens on nothing for it.
- **For image builders.** A sandbox image must leave 127.0.0.1 ports 18761, 18762 and 18763 free: the bridge listens there for the git proxy and the tools, the model proxy and the egress proxy. A program of the image that holds one of them fails the run at its start, with an error that names the service and the port.
- **A runner host says when it can take no run** ([ADR-0117](docs/adr/0117-a-host-reports-that-it-can-take-no-run.md), Proposed). A runner host with a VM per run whose driver can make no VM tells the server with the optional protocol feature `host.health`. The server then sends it no run: its turns wait with the queue reason `RUNNER_HOST_UNHEALTHY`, and no assignment, audit event or token is spent. The host's card says "Takes no runs" and why, the audit records `runner_host.health_failed` and `runner_host.health_restored`, and the waiting turns start as soon as the host takes runs again. A run that the same runner host rejects again waits twice as long each time, from `TINFIRM_RUN_REJECT_BACKOFF` (10 s) up to the new `TINFIRM_RUN_REJECT_BACKOFF_MAX` (5 minutes; a shorter value is not used, and the server logs a warning at start). The server and the hosts can be upgraded in either order: an older host still rejects, now with the longer waits, and an older server gets no frame.
- **A run's git token can be revoked** ([ADR-0116](docs/adr/0116-short-lived-and-revocable-git-tokens.md), Proposed). The server tells a run's host to drop a repository's git token, on every code host, when the run's binding fails its check (an account disconnected or needing a new sign-in, a credential disabled or removed, a grant or lending withdrawn, a person who left the group, a holder suspended or gone, a system removed), when an admin pauses the system, with or without stopping its running turns, and when a trigger's binding follows another credential. The agent's next fetch fails with the reason, and the repository is not pushed: a run with unpushed commits there ends `GIT_ERROR`, and its other repositories go on. Audited as `run.git_revoked`. Pausing an agent or a trigger, and the company's stop, revoke nothing. It needs a server and runner hosts of this release: the server sends `run.git.revoke` only to a host that lists that feature, and ends its answer to such a host's `hello` with `welcome.done`. The host confirms each revocation it applied (`run.git.revoked`), and the run's page then shows it as `CONFIRMED`, audited as `run.git_revoke_confirmed`. A runner host that took runs back at a restart pushes their work only after the server has answered its hello, however long that takes: the runs' work and records stay on the host meanwhile, a second restart or a shutdown keeps them, and `doctor` lists the runs that wait. A host that restarts still redacts, and blocks from a push, the git tokens that a run held before the restart and that its record no longer holds, revoked ones and a GitHub App's earlier ones: the record keeps salted hashes of them, not the tokens. A run taken back from a record whose hashes are damaged pushes nothing and fails `INFRA`, with its work kept on the host. A runner host refuses an assignment whose git token is over 16 KiB. A run on an older host keeps its token until it ends: the run's page shows the revocation with `delivery` `UNSUPPORTED`, and the conversation says so.
- **A GitHub App on a GitHub system** ([ADR-0116](docs/adr/0116-short-lived-and-revocable-git-tokens.md); [Set up the GitHub App](docs-site/content/admin-guide/systems.md)). An admin sets the company's own GitHub App on a company `GITHUB` system (its id and private key, kept in the vault and never shown again) and adds its installations as credentials of the new kind `APP`. A run on such a credential gets tokens of its own, for GitHub's hour, limited to its repositories and to `contents` and `pull_requests`, never `workflows`. Its host renews them through the server, which checks the binding again each time. Such a run goes only to a host that renews tokens (`run.git.refresh` with `run.git.revoke`), and waits with the queue reason `NO_HOST_FOR_APP_TOKENS` until one is connected. For the server's own calls Tinfirm mints an installation token with the installation's permissions less `workflows`.
- **For integrators** ([api/openapi.yaml](api/openapi.yaml), [runner-protocol-v2.md](docs/operations/runner-protocol-v2.md)). `RunRepository.gitRevoked {reason, message, revokedAt, delivery}`, with `delivery` `CONFIRMED` (the host said that it dropped the token; `confirmedAt` says when), `SENT` (the frame was written to the host's connection and is not confirmed yet), `PENDING` (it goes when the host reconnects) or `UNSUPPORTED`. `GET`, `PUT` and `DELETE /systems/{systemId}/github-app`, `GET …/github-app/installations` and `POST /systems/{systemId}/credentials/app`, for OWNER and ADMIN; a `PUT` with the same App id replaces the key. The kind `APP` of accounts and credentials, and `ExternalSystem.githubApp`. The queue reasons `NO_HOST_FOR_APP_TOKENS` and `RUNNER_HOST_UNHEALTHY`, and `RunnerHost.problems` and `problemsSince` (ADR-0117). The problems `GITHUB_APP_REFUSED` (400), `GITHUB_APP_IN_USE`, `GITHUB_APP_REQUIRED`, `GITHUB_APP_CHANGED` and `DUPLICATE_INSTALLATION` (409), and `GITHUB_UNREACHABLE` (502). Runner protocol 2 gains the optional features `run.git.revoke`, `run.git.refresh` and `host.health`, the frames `run.git.revoke`, `run.git.revoked`, `welcome.done` and `host.health`, `welcome.features`, the request kind `GIT_TOKEN`, and `expiresAt` and `mirrorKey` in a workspace's git credentials.
- **Editions and licence.** Community, Pro and Enterprise from one image, an offline licence key, seats counted by role with the Viewer role; an MIT core and a commercial `ee/` ([ADR-0077](docs/adr/0077-licence-editions-and-seats.md), [ADR-0082](docs/adr/0082-licence-notices-and-dependency-licences.md)).
- **Deployment.** The Helm chart on GHCR, Docker Compose, Ansible for runner hosts with Kata Containers, signed release images and assets, and the public docs at <https://docs.tinfirm.com> ([ADR-0080](docs/adr/0080-helm-chart-published-to-ghcr.md), [ADR-0081](docs/adr/0081-signed-release-images.md)).

### Known limitations

These are limits of 1.0, not features of it ([PLATFORM.md §14](docs/PLATFORM.md#14-later-work-and-open-items), [threat model](docs/threat-model.md)):

- **One server replica.** The server keeps runner connections, event streams and tool calls in flight in its process, and several limits count per replica (the runner frames' buckets, the sign-in throttle, the refusals per address, the AI clients' metadata fetches, the catalogue refresh; Q43). Run one replica. High availability across replicas, which Enterprise lists, is not built.
- **Enterprise's audit streamed to a SIEM and its air-gapped installation bundle are not built.** Export the audit from the app; on an air-gapped network, copy the signed images with `cosign save` and `cosign load` ([Verify your images](docs-site/content/operator-guide/verify-images.md#on-an-air-gapped-network)).
- **Not built either:** reusing agents (duplicate, templates, export and import as code), a GitHub App's user tokens (PLATFORM §14), webhooks as hints for the next poll, Jira's changelog for issues that are not yet subjects, reuse of the model proxy's connections, and Buzz, which is parked.
- **Sandbox nodes are not ready for production** ([ADR-0112](docs/adr/0112-no-credential-on-a-sandbox-machine.md), Proposed). The runner host has the `node` VM driver, and `tinfirm-node-agent` makes and deletes jailed Firecracker VMs, each in a jail that is a file system of its own in memory (`firecracker.jailMib`, 64 MiB by default), and only while the node's own firewall table is loaded, unless the node's `helper.json` says `"nodeFirewall": "not-required"`: that ran on one node with KVM, driven by the runner host over TLS ([the evidence](docs/reviews/2026-11-19-node-agent-execution/README.md)). The hardening of [ADR-0113](docs/adr/0113-levels-of-isolation-and-placement.md) (decision 5) is built and ran on one node once, on 2026-11-22 (Ubuntu 24.04, kernel 7.0): the play, the 13 checks, the unit that sets kexec, lockdown and module loading at each boot, and the VMMs' AppArmor profile in both modes held, and the profile logged nothing; a real conversation has run through a hardened node since, and a control host's report of the mark reached a server, also when a line was set back by hand while the host ran; a new VM going to a hardened node first is not shown. The VMMs' profile is in enforce mode by default since 2026-11-22 (`tinfirm_sandbox_node_harden_mac`), after a real conversation and a make that failed after its VMM started ran under it with no denial; with the defaults a node now reports `hardened: yes` where every line holds, where it reported `no` for `vmm-mac` alone. Where VMs stop starting after the change, the kernel's log has `apparmor="DENIED"` lines of `tinfirm-vmm`: set `complain`, which stays the value for a first run on a distribution or kernel the profile has not run on, and report them. The role `tinfirm_sandbox_node` sets the hardening up, the node agent's helper checks each line of it and reports the node's mark in `verify`, and a control host reports `hardened: yes` only while every node that offers its template reports `yes`; `doctor` and the host's log name each line that does not hold, and a new VM goes to a hardened node first. A lower mark stops nothing. A change of the mark while the host runs reaches the server by a new hello: the host asks the node driver's `verify` every 5 minutes and at its other health checks, and reconnects at once when the mark is lost, or when a gain has held for two checks in a row, at most once per 5 minutes; runs go on through that reconnect. At each `verify` the node agent's listener also sends one empty datagram towards its control host, which the node's own firewall table must refuse: where it passes while the table is required, `verify` names a problem and the control host places no VM on the node. That try covers the control host's address alone; it ran on one real node, refused by the loaded table, and named the problem with the table deleted or replaced by one that lets the datagram pass. Tinfirm publishes no VM image: you build it with `runner/images/vm/local-disk.sh`, since built with every runtime it holds Claude Code, which Tinfirm does not redistribute; a CI job that builds and boots it is not built yet. A single machine, the control host and the node agent together, is set aside: the node agent refuses a control host on its own machine. The Ansible roles that set up a node and a control host ran on machines once, and ten conversations with real runtimes (Claude Code and PI) and a model ran through the node they set up. The chart's runner pod has not run against a node. Kata Containers stay, and a Kata host reports `container`: Kata is removed only in the release where sandbox nodes are ready for production, not in this one; the node agent is released as a static Linux binary beside the runner host, under the same signed `SHA256SUMS`; its service units, the node's own firewall table and the setting that turns user namespaces off are in the source tree (`runner/crates/tinfirm-node-agent/units/`), and the role `tinfirm_sandbox_node` installs them; a host with a driver other than `node` reports itself hardened only where its operator states it. The chart's runner pod takes `runner.vm.driver: node`, with the nodes in `runner.vm.node.nodes`, the client certificate and key in the Secret `runner.vm.node.existingSecret`, and the published bridge ports in `runner.vm.node.publishedPorts`; its NetworkPolicy opens those ports with `endPort`, which needs Kubernetes 1.25 or later (the chart needs 1.29). `run` refuses the driver at its start when a node's `verify` reports a problem ([Helm](docs-site/content/operator-guide/helm.md#with-sandbox-nodes)). `tinfirm-runner-host node identity` and `node fingerprint` make and read the control host's client certificate, with the same files as `tinfirm-node-agent identity` and `fingerprint`, so a control host needs no node agent's binary for its own certificate. `doctor` checks a host as `run` would start it, with `run`'s sandbox and VM options and its environment: with `--executor vm` it checks the VM driver (the `node` driver's configuration and client keys, a `verify` of the template, and room for `--max-concurrent-runs`) and no longer fails for want of Docker. When no node can take a VM, the failed run's message names each node's cause (its problems, that it did not answer, or that it is full) instead of "no free slot"; when the driver's `verify` then answers with problems and no room, the host rejects new runs with that cause, so that they wait in the server's queue instead of failing, and takes runs again once `verify` answers clean. The built-in VM drivers answer a line that is not a request with a JSON-RPC error (-32700, -32600) and exit non-zero when they got no request. Who prepares a node now meets two checks of the node agent: the listener's configuration requires `tls.controlHost`, the one address it takes TLS connections from, and the helper refuses a `helper.json` that is not root's or that its group or others can write. A VM whose delete fails, because its node is down or reboots, is deleted by the host on its own once the node answers again, so a node's slot no longer stays taken until the control host restarts; and a run whose VM ends under it (its VMM dies, its node reboots) fails as `INFRA` and names the VM, not as the agent's fault; both were shown on machines, with a VMM killed and a node rebooted during a run. The node agent overwrites every block of memory with zeros when it frees it (the `zeroizing-alloc` allocator), so that a VM's one-time ticket does not stay in memory that its TLS or JSON library dropped. A sandbox node is a tier-1 asset, a lower tier than the control host: it holds no credential, so give its administration only to the people who administer the control host, and replace its image on a schedule.
- **Ansible for sandbox nodes and their control host** (not ready for production: both plays ran on machines once, on Ubuntu 24.04, with ten conversations through the node they set up, a node's hardening has run on one node, a real conversation through it included, and Tinfirm publishes no VM image; [Sandbox nodes on your own machines](docs-site/content/operator-guide/sandbox-nodes.md)). `deploy/ansible/sandbox-node.yml`, with the role `tinfirm_sandbox_node`, installs a node: the node agent from the release's signed `SHA256SUMS`; Firecracker 1.14.2 with its jailer and the guest kernel of Kata Containers 4.3.1, each against a pinned SHA-256; a VM image that you build with `runner/images/vm/local-disk.sh` and give with its SHA-256; the agent's units, the sysctl file, the node's firewall table and the listener's `IPAddressAllow=`; and the node's TLS identity, made on the node. It ends with the helper's check of every template and fails when one reports a problem. `deploy/ansible/control-host.yml` runs the runner host's role with `tinfirm_runner_host_executor: vm`: `run --executor vm --vm-driver node`, the node driver's configuration from `tinfirm_runner_host_nodes`, a client certificate made on the host, a `verify` of every node through the driver, and no Docker, Kata or runner image on that host. The play writes the node driver's configuration with the nodes that have a `nodeSha256` and reloads the host when it changes, so emptying a node's pin takes the node out at the next run; with no pinned node it stops the host and removes the file. It refuses a machine with Docker, containerd or Kata, or whose runner host user is in the `docker` group, and starts the host only after a check that the user reaches no Docker socket. A first set-up runs the control host's play, then the nodes' play with the control host's fingerprint, then the control host's play again with the nodes' fingerprints. The runner host's role no longer reports a change on a second run for the release's `SHA256SUMS`. The nodes' play shows each node's entry for the control host's `tinfirm_runner_host_nodes` with its `publishedPorts` as numbers, and says that the entry is for the control host's inventory, not for `node-driver.json`.
- **A pod per run in a Kubernetes cluster is not ready for use** ([ADR-0115](docs/adr/0115-sandbox-vms-in-a-kubernetes-cluster.md), Proposed; paid, with elastic runners). The runner host has the `pod` VM driver (`run --executor vm --vm-driver pod`, the chart's `runner.vm.driver: pod`): each run's sandbox is a Firecracker VM in a pod of a namespace for runs alone, as an unprivileged user in a user namespace of the pod's own, and the cluster schedules it. The chart installs that namespace with two network policies, a quota, the driver's role and an admission policy; the driver creates no policy and reads no Secret. Such a host reports `machine` on its operator's statement in the driver's configuration, and `hardened: no`. It has run in no cluster. Tinfirm publishes no image for run pods: the operator builds it with `ee/runner/images/vm/pod-image.sh`, from the release's runner host binary, Firecracker 1.14.2 and the sandbox nodes' guest kernel, each checked by its checksum, and the VM image of `runner/images/vm/local-disk.sh`, shrunk to what it uses; the image has no shell. That VM image carries a unit that grows its root file system to its disk at boot where the kernel's command line asks for it, which a run pod's VM does and a sandbox node's does not. The cluster's admin must provide workers with KVM, a device plugin, and `/dev/kvm` open to every user of those workers. `doctor` checks the driver's configuration and says where the driver must run. The operator guide has a page for a cluster's admin, with what the cluster must have, what the admin applies and the chart's values ([Sandbox VMs in your Kubernetes cluster](docs-site/content/operator-guide/kubernetes-pod-per-run.md)).
- **The runner host parses what a sandbox sends outside its own process** ([ADR-0112](docs/adr/0112-no-credential-on-a-sandbox-machine.md), path C). On a host with the sandbox bridge or a VM per run, each sandbox has a front process of its own, confined with Landlock and seccomp and holding no credential: it holds the sandbox's bridge (its TLS, with an identity of its own, its frames and its tunnels) and parses the HTTP of the sandbox's git, model and egress proxies and of the platform tools. The runner host decides each bridge's `hello` with the ticket it keeps, checks each request again, makes each connection and attaches the model gateway's key and the run's git token itself. What a sandbox sends back is read in a confined reader per archive or bundle. Such a host refuses to start where it cannot confine the reader or a front, unless `--allow-unconfined-reader`, which covers both. Still parsed in the runner host: the agent's ACP messages, the JSON of the platform tools' calls and the fronts' bounded messages; by default the push runs there with the run's git token. `run --push-client host` (`TINFIRM_RUNNER_PUSH_CLIENT`) pushes with the runner host's own receive-pack client instead: a confined process without the token packs the objects and the runner host sends them, with the same lease. It was checked on 2026-11-22 against a git server run for the test and, for a new branch, against GitHub, not against GitLab, Gitea or Azure DevOps, so `git push` stays the default. Through a front, a bridge handshake takes about 1.9 ms and 1 GiB moves at about 375 to 450 MiB/s.
- **Git credentials outside a GitHub App live as long as the account's** (Q41). Members' own tokens, a credential's stored token and every GitLab or git host's token are not short-lived: they gain the revocation, not a shorter life. GitLab's per-run tokens are not built.
- **What a revocation does not reach** (threat model R44 and Q48). A request already under way with the token, what the sandbox already fetched, the token at the code host (a revoked App token stays valid at GitHub until its hour ends), a runner host older than this release, and a disconnected host until it reconnects. Revocations that arrive late in some cases: one that commits while the server answers a host's `hello`, a taken-back run that pushes after 2 minutes without `welcome.done`, and a suspension, whose cancel and revocation come in no fixed order.
- **The GitHub App is untested against GitHub.** Every call to GitHub ran against a stub; no request has reached github.com or a GitHub Enterprise Server, and the GitHub Enterprise Server half follows GitHub's documentation only. That GitHub refuses a push that changes workflow files without `workflows` is not verified.
- **The server pod runs the migrations** (Q17), so it holds the `tinfirm_owner` password; there is no separate migration step, and no pre-upgrade backup hook in the chart.
- **The SAML and SCIM guides** for Entra ID, Okta and AD FS are checked against the providers' documentation, not yet against live tenants, and the SCIM endpoint has not yet run Microsoft's SCIM Validator or Okta's test suite.
- **Runner host binaries:** no Windows build yet, and the macOS binary is not signed by Apple.
- **The sandbox hardening** the threat model lists as accepted risks (its section 7).

### Upgrading from development builds

An installation that ran the development channel (the images `sha-<commit>`, a chart `0.0.0-sha-<commit>`, or a Compose host that followed `main`) moves to v1.0.0 in this order. The operator guide's [Upgrade, back up and rotate secrets](docs-site/content/operator-guide/maintenance.md) has each procedure.

1. **Back up** Tinfirm's and LiteLLM's databases, and keep the vault keys and LiteLLM's salt key. Migrations only move forward.
2. **Replace the published development secrets.** The server does not start with `.env.example`'s vault key, LiteLLM master key or bootstrap admin password unless the public URL is a localhost URL: rotate them first ([Rotate the vault master key](docs-site/content/operator-guide/maintenance.md#rotate-the-vault-master-key)).
3. **The model port is gone** ([ADR-0110](docs/adr/0110-no-model-port.md)). Helm refuses a values file that still sets `litellm.modelApi`: move its `from` to `litellm.from` and drop the rest. The company's services that used port 4001 call LiteLLM's own port 4000, `http://<release>-litellm.<namespace>.svc:4000`, where they also reach its admin API: give each a key made with `key_type` `llm_api` first. On Compose, a company service joins the gateway network and calls `http://litellm:4000`; remove the `model-api` container with `--remove-orphans` and the `TINFIRM_MODEL_API_*` lines of `.env`.
4. **No provider-run tools** ([ADR-0108](docs/adr/0108-no-provider-run-tools.md)). The company setting `providerTools` is gone from the API and the database (a client that still sends it changes nothing), and so are `MODEL_API_PROVIDER_TOOLS`, Helm's `litellm.modelApi.providerTools` and Compose's `TINFIRM_MODEL_API_PROVIDER_TOOLS`: remove them. Agents search the web through a search MCP server.
5. **Model gateways** ([ADR-0094](docs/adr/0094-more-than-one-model-gateway.md)). The bundled gateway's variables are now `TINFIRM_MODEL_GATEWAY_ADMIN_URL`, `_MODEL_URL` and `_ADMIN_KEY`; the server still reads `TINFIRM_LITELLM_ADMIN_URL`, `_MODEL_URL` and `_MASTER_KEY` while the new names are unset. The chart and Compose set the new names. A company may now use a gateway whose keys its own team provides.
6. **Upgrade the server.** Helm: `helm upgrade tinfirm oci://ghcr.io/flowtivo/charts/tinfirm --version 1.0.0`, with `image.tag` empty or `v1.0.0` (a `sha-<commit>` tag left in your values runs that build, not the release), and by the digests you verified. Compose: the files of `tinfirm-compose-1.0.0.tar.gz` and `TINFIRM_SERVER_IMAGE` set to the `v1.0.0` image by digest. A deployment repository that followed `main-complete` names `v1.0.0` instead.
7. **At once, upgrade every runner host with a VM per run or with Kata Containers** ([ADR-0113](docs/adr/0113-levels-of-isolation-and-placement.md)). A host now reports its level of isolation in `hello.isolationTiers`, where an older host sent its tier. The new server refuses a host that still sends `microvm`, a host with a VM per run (`--executor vm`) or with Kata, with `UPGRADE_REQUIRED`, which names the server's version, until it runs this release; and an older server refuses a host of this release that reports `machine` or `vm-jail`, so these hosts go with the server; the chart's runner pod goes with it in step 6. Docker hosts with runc or gVisor send `container` or `gvisor` in both releases and are upgraded at any time (step 8). A Kata host of this release reports `container`; a host with a VM per run at DigitalOcean reports `machine`; a host with a VM driver of your own reports `container` until you state its level with `run --isolation-level` (and `--isolation-hardened`). An agent's runs go to the strongest level the company's hosts report, and wait while those hosts are offline or full: in a company with VM hosts and container hosts, upgrade its VM hosts together, or choose `container` for the agents that should stay on the container hosts. A member's own host does not raise the level of their runs ([docs/operations/runner-isolation.md](docs/operations/runner-isolation.md)). Before that, run `tinfirm-runner-host doctor` of 1.0.0 on each host with a VM per run or with `--sandbox-bridge`: a host with `--executor vm` or `--sandbox-bridge` now refuses to start where it cannot confine the reader of what its sandboxes send back or the front process of each sandbox, which needs Linux 5.19 or later with Landlock enabled at boot, unless you accept that with `--allow-unconfined-reader` (`TINFIRM_RUNNER_ALLOW_UNCONFINED_READER`), which covers both; `doctor`'s lines `reader` and `front` say which ([runner/README.md](runner/README.md#the-reader-and-the-front)).
8. **Then upgrade the other runner hosts**, to `tinfirm-runner-host` 1.0.0, a build of runner protocol 2, logged in at the server's public URL, as for every upgrade: the server first, then its hosts. The new server keeps working with the Docker hosts you run now: every host of runner protocol 2 sends its own token with a run's model requests, and the server decides nothing from a host's version, so you can upgrade them at your own pace. A host must be logged in at the server's public URL (`TINFIRM_PUBLIC_URL`), since its model proxy sends that token to that origin only; log in again a host that uses another address. The model relay requires a host's own token from every host and no longer has `TINFIRM_MODEL_RELAY_REQUIRE_HOST_TOKEN`, which is ignored where it is still set; the server decides nothing from a host's version, and the API's `RunnerHost.gatewayRuns` is gone ([ADR-0109](docs/adr/0109-runner-version-is-the-release-version.md)). `--model-proxy` has no effect. With the chart's runner pod, rebuild the VM image with the 1.0.0 runner host. On Linux, `run` makes itself not dumpable: it writes no core dump, and another process of the host's user can no longer read its memory through `/proc/<pid>/mem` or attach to it with `ptrace` (root still can).
9. **Re-provision company hosts with the Ansible role's defaults**: the egress proxy, the bridge, systemd sandboxing, Kata Containers 4.3.1 with its known checksums, and the release archive checked against the signed `SHA256SUMS`. The service user's uid moves from 1000 to 1990: drain each host first ([deploy/ansible/README.md](deploy/ansible/README.md)).
10. **Git token revocation and the GitHub App** ([ADR-0116](docs/adr/0116-short-lived-and-revocable-git-tokens.md)). The server and the runner hosts can be upgraded in either order: a host of this release with an older server works as before, and a new server tells an older host nothing, so its runs keep their git tokens until they end. Revocation needs both. The migrations V087 (the revocation commands, a version on each binding, and an epoch on the repositories of the runs that were running, lost or assigned at the upgrade, so that a revocation reaches them too) and V088 (the GitHub App and the credential kind `APP`) run with the server. Set up a GitHub App only once the company's hosts run this release: until a connected host renews tokens, the App's runs wait with `NO_HOST_FOR_APP_TOKENS`, and the App's section of the system's page counts the hosts that cannot.
11. **Ready VMs are off unless you turn them on** ([ADR-0114](docs/adr/0114-the-secure-sandbox-is-in-the-core.md)). `run --pool-max-ready` and the chart's `runner.pool.maxReady` now default to 0, where a development build's default was 4: a host that kept ready VMs by that default sets the value itself, and needs a Pro or Enterprise key as before. A host with the sandbox bridge, or with a VM per run through a driver of your own, no longer needs one.
12. **Set up MCP servers' apps again.** An MCP server's app stored before the security review's fixes was not checked against its issuer's origin: open each and choose **Set up the app**, which now refuses endpoints off the issuer's origin and asks before a changed token or revocation endpoint removes accounts. Name split-hosted providers in `TINFIRM_OAUTH_DISCOVERY_ALLOWEDENDPOINTORIGINS` first.
13. **Tell people that personal access tokens expire** after 90 days, tokens made before then included, 90 days after their migration; a token names its companies, and a password change revokes it. The web app's token page renews them.
14. **Instances with several companies:** review the users that SCIM provisioned, have never signed in, and hold memberships in more than one company, and confirm that every company of the instance shares one operator.
