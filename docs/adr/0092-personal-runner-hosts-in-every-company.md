# ADR-0092: A personal runner host serves its owner in every company they belong to

- Status: Accepted
- Date: 2026-10-24
- Decided by: the owner, 2026-10-24
- Sources: [CONVENTIONS.md](../CONVENTIONS.md) §7 (`runner_host`, `runner_credential`), §8, §10, §15.4, §15.6; the [package 2 contract](../reviews/2026-10-12-package-2-contract.md) §2, §5.2, M4, M5; the [threat model](../threat-model.md) 5.6, 5.14, Q10; [ADR-0089](0089-companies-from-the-role-claim.md)
- Amends: the package 2 contract's §2 (a host belongs to one company) for personal hosts; [ADR-0058](0058-authority-from-the-audience.md) on the personal host's row
- Changes: migration `V064` (`personal_runner_host`, `personal_runner_credential`, `runner_host.personal_host_id`, the lookups `runner_host_for_token`, `personal_runner_host_presences`, `member_principals`, `run_company`, `personal_runner_host_occupying`, `personal_runner_host_occupying_subscription`, `personal_runner_host_active`); the runner module (`ConnectedHost` placed per company, `RunnerHostStore`, `RunnerHostSessions`, `RunnerConnectionRegistry`, `RunnerWebSocketHandler`, `RunnerHostService`, `RunnerHostDependents`, `RunnerAuthentication.forRun`, `RunnerActivity.hasActiveRunsOnMachine`, `RunnerHostInfo.personalHostId`); the run module's counts (`RunStore.occupyingByMachines`, `occupyingBySubscriptionOfMachine`, `hasActiveForMachine`, `RunDispatcher`); the runner's HTTP endpoints and the model relay place the host in the run's company; `PrincipalDependents.memberJoined`; the web copy of Accounts › Runner hosts; no change to the runner host program or the protocol

## Context

- A runner host belonged to one company: its row in `runner_host` carried the company, the token's hash and, for a personal host, its owner's principal there. Row-level security, the composite foreign keys of runs (`run_host_fk (runner_host_id, company_id)`) and the dispatcher, which works company by company, all rest on that.
- A member of two companies registered their laptop twice, with two tokens, and ran two host processes, or chose one company. Their Claude subscription, which the host holds and never sends, served one company's runs only. ADR-0089 makes a person a member of each company the identity provider's claim names, so the pattern grows with every provider that fills several companies.
- Threat model 5.6 and Q10 left open how a personal host could serve its owner in several companies. The security invariants must hold whatever the answer: a personal host runs only its owner's work (M4), its credentials serve only its owner (M5), a host's frames are accepted only for runs assigned to it with their current epoch, and each company's rows stay under its own row-level security.

## Decision

**A personal runner host is a machine of its owner's, present in every company the owner is a member of. One registration, one token, one connection; a presence per company, which that company's run side sees as a host of its own. The machine's slots and subscriptions are one across its presences. Presences follow the owner's memberships: created when they join a company, removed when they leave one. Company hosts are unchanged.**

1. **The rows** (§7). `personal_runner_host` is the machine: `owner_user_id` (the user, `ON DELETE CASCADE`), `name` (unique per owner), `token_hash` (unique), the capacity (`max_concurrent_runs`, its ceiling, the desired value, `draining`, `config_version`, `applied_config_version`), the facts of its last `hello` (`runtimes`, `runner_version`, `hostname`, `os`, `arch`, `last_seen_at`). It is an instance-level table without row-level security, as `app_user` is: nothing in it is a company's. `personal_runner_credential` holds the credentials the machine reports, as `runner_credential` held them per host; `runner_credential` is dropped. A presence is a row of `runner_host` with `scope` `PERSONAL`, `owner_principal_id` (the owner's principal in that company, as before) and `personal_host_id`; it carries no token and no facts (`runner_host_personal_ck`, `runner_host_token_ck`; `runner_host_presence_uq` on `(personal_host_id, company_id)`). The runner module reads a host as `runner_host` joined with its machine, so a presence shows the machine's slots, facts and credentials, and writes the machine's row for a personal host and the host's own row for a company host. A company host's name is unique among the company's company hosts; a personal host's among its owner's machines, and so among the owner's presences in each company.
2. **The migration.** Every personal host becomes a machine with its registration as its presence (the token, capacity, facts and credentials move to the machine), and gets a presence in each other company its owner is a member of now. Two personal hosts of one owner with one name, in two companies, keep both: the later one is renamed with the company's key as a suffix (the company's id when the owner has that name too), within the column's length.
3. **Registration and removal** (§15.4). A member registers a personal host in any company they are in, as before (`POST /runner-hosts`, scope `PERSONAL`): the server writes the machine and a presence in each of the member's companies (`member_principals`, a `SECURITY DEFINER` lookup of the user's memberships), each in its company's tenant context and audited in its chain, `runner_host.registered` with `personalHostId`. The answer shows the presence in the company of the request. A duplicate name is `409 DUPLICATE_RUNNER_HOST_NAME` whichever company the owner's other host of that name was registered in. The owner removes the host in any company (`DELETE /runner-hosts/{id}` on its presence there): the machine goes, with every presence and credential, audited `runner_host.removed` in each company, and the connection closes with 4401; it is `409 RUNNER_HOST_HAS_ACTIVE_RUNS` while a run of any company is queued for it or running on it (`personal_runner_host_active`). The removal, and a capacity change, take the locks in the dispatcher's order: the machine first (`FOR UPDATE`, which also holds back a new presence, whose foreign key to the machine waits for it), then the presences by id, each in its company's tenant context; the removal checks for runs under those locks, so no dispatcher of any company assigns a run to a presence meanwhile, and no presence appears after the ones it saw. The capacity (`PATCH`) is the machine's: set in one company, shown in all, audited where it was set; the host gets one `host.config`.
4. **Memberships** (`RunnerHostDependents`). When a member joins a company, each of their machines gets a presence there, in the joining transaction, audited `runner_host.registered` with the cause `principal.joined`, and the machine's current connection serves the company from the next dispatch on. When a member leaves, only their presences in that company go, audited `runner_host.removed` with the cause `principal.left` as before; the machine, its token and its connection stay for their other companies. A member of no company keeps their machine: it connects, reports its credentials and takes no runs, until they join one.
5. **The connection** (§15.6). The token names the machine; the connection is one, keyed by the machine's id in the registry, and every presence's id names it, so the run side of each company asks `RunnerConnections` by the presence it knows. `hello` records the machine's facts and credentials, and the reconciliation of the runs the host reports runs once per company, each with the runs of that company (`run_company`, a `SECURITY DEFINER` lookup of a run's company); a reported run of no company of the host's is cancelled. The `welcome` names the machine's id and the first of its companies by id (the nil UUID for none); the runner host program keeps both in its state file and uses neither for anything the server reads. A run frame is handled in the company of the run it names (`UNKNOWN_RUN` when the host is not in it); a `run.heartbeat` that names runs of several companies is split; a disconnect extends the leases, and a sign of life renews them, in every company. The runner's HTTP endpoints (files, skills) and the model relay place the host in the run's company (`RunnerAuthentication.forRun`), so a token reaches only runs of the companies its host is in, and among them only the runs assigned to it, as before.
6. **Dispatch** (§15.6). A presence is eligible as a personal host was: for its owner's work only (M4), with its owner's credentials only (M5), since each presence names the owner's principal in its company and shows the machine's credentials. The machine's slots are one: the dispatcher of any company locks the machines of the personal hosts it considers `FOR NO KEY UPDATE` (in the order of their ids) before the hosts themselves, and counts the machine's runs across its presences (`personal_runner_host_occupying`), and a subscription's pool likewise (`personal_runner_host_occupying_subscription`). The lock serialises the dispatchers of every company the machine is in, as the host's row did within one company.
7. **What a company sees.** Nothing new in the API: a presence is a `RunnerHost` of the company with `scope` `PERSONAL`, its owner there, and the machine's state. The company's audit chain records the presences' registrations, capacity changes made there and removals, with `personalHostId`; a presence created or removed by a membership carries its cause. Owners and admins of a company see no personal host of a member, as before.
8. **Testing.** `RunnerHostIntegrationTest`: the presence in a second company (another row, the same name and owner, the registration in each chain), the duplicate name across companies, one connection online in each company with the credentials, a capacity change made in one company seen in the other with one `host.config`, a run of each company accepted and kept alive over the one connection, the removal refused while a run of the other company runs, the presence that joining a third company adds (`principal.joined`), a departure that removes the presence and keeps the connection, the removal in one company that removes the machine everywhere and revokes the token; a member who leaves their only company keeps the machine, which connects with no company. The constraints: a credential is a machine's, a presence carries no token, one presence per machine and company, the owner checks as before.

## Consequences

- A person with one laptop and several companies runs one host process with one token. Their Claude or ChatGPT subscription on it pays their conversations in each company.
- Their machine's slots are shared across their companies: a long turn for one company occupies a slot the others wait for. Each company's view shows the slots in use by the machine's runs anywhere, and the runs of that company among them.
- An owner or admin of a company sees in the company's audit chain that a member's host was registered or removed through a membership change, with the machine's id, never the other companies' names or ids.
- A personal runner host that reconnects across this change gets a new id in its `welcome`, the machine's, and keeps it in its state file. The host program uses that id for one thing: it labels each run's container with it (`dev.tinfirm.runner-host`) and, after a connect and at a start, removes the containers so labelled whose run is no longer live (the cleanup of orphans). Containers started before the reconnect carry the old id, so that cleanup no longer sees them. A run that was live across the reconnect still removes its own container when it ends, as every run does, so only a container orphaned in that window (its run lost while the host was down) stays, as a stopped `tinfirm-run-<run id>` container to remove by hand with `docker rm`. Company hosts keep their id.
- Threat model 5.6 and 5.14 change their binding: a personal host belongs to its owner and is present in the owner's companies; the server still accepts a frame only for a run assigned to the host, in that run's company. Q10 is closed.

## Alternatives considered

- **A host row per company with the same token.** One `runner_host` row per company, each with the token's hash. The token lookup would return several rows, which this decision's machine makes explicit, but the capacity, facts and credentials would be written in every company on each `hello`, and the slots could not be one without a row of their own. Rejected: the machine is that row.
- **A machine without presences: runs of every company naming the machine.** The run's `runner_host_id` would point outside the run's company, against `run_host_fk (runner_host_id, company_id)` and the per-company row-level security of everything that joins a run with its host. Rejected.
- **A registration per company, as before.** Works, at the cost of a host process and a token per company on the same laptop, and a subscription that serves one company only. The owner asked for the change.
- **Presences only for the companies the owner chooses.** A member could keep a host out of one company. Not asked for; every presence runs only the owner's own work anyway, and the owner may remove the host. Open for a later decision if wanted.
