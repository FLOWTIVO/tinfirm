## Context

**How a run gets its git token today.**

- In the second phase of an assignment, outside any transaction, `TurnSourceImpl.content` reveals each workspace repository's token through `ConversationBindings.use(binding, "run:{runId}")`, the one gate of ADR-0105, audited as `secret.accessed`. The token is the bound account's: a member's own personal access token or OAuth grant, a credential lent to their group, or a trigger's author's or service account's (R27, A10).
- `run.assign` carries it in `workspaces[].git {username, token}`, with the user name `x-access-token` on GitHub, `oauth2` on GitLab and `git` otherwise. The schema says it is used only by the runner host and never passed into the sandbox.
- The host holds it until the run ends, up to the run's wall-clock limit: 60 minutes by default, up to 24 hours for an agent that sets it (§6.6).

**What the host does with the token.** More than the git proxy:

| Where | What | With the token |
|---|---|---|
| `mirror.rs`, before the clone | Creates or fetches the host's bare mirror of the repository, then clones the workspace from it | Yes. The mirror's name is SHA-256 over the URL and the `Authorization` header, so that two principals never share one (M15) |
| `git_proxy.rs`, while the agent runs | Forwards `git-upload-pack` from the sandbox to the code host, adding the host's `Authorization` | Yes, held in the route (`Route.authorization`) for the run's length. `git-receive-pack` is refused with 403: **the sandbox never pushes** |
| `run.rs`, before the push | Fetches the mirror again, to know the repository's current refs for the credential scan | Yes. A failure only warns, and the scan compares with the refs at clone time |
| `git.rs` `Git::push`, at the end | Pushes the run's commits to `agent/<key>` with `--force-with-lease` on the branch's tip at clone time | Yes. **A cancelled run pushes its work too**: the host takes the work back and pushes before it reports the cancel |
| `run.rs`, the redaction | Adds every token of the run to the secrets it redacts from events and scans for in outgoing commits | The value, for the run's length |
| `takeback.rs`, with the sandbox bridge | Writes `runs/<runId>.json` (0600), which holds the whole `RunAssign`, the tokens included, until the sandbox stops (ADR-0101, 6.20) | Yes, on disk |

Each holds its own copy: `Git.authorization`, `Route.authorization`, and the record's `assign`. Nothing can replace or remove a token once the run has started.

**What happens when a binding fails its check.**

- Package 1's events (`AccountDisconnected`, `AccountNeedsReconnect`, `CredentialChanged`, `LendingReplaced`, `GrantChanged`, `GrantDeleted`, `GroupMembersChanged`, `PrincipalSuspended`, `SystemDeleted` and others) reach `BindingEvents`. That class has `BindingService.reevaluate` look again at every binding of an open conversation that they may concern.
- A check that fails records the binding `WAITING` or `GONE` with its reason, and publishes `ConversationEvents.BindingWaiting` or `BindingGone`. A check at any other use, such as a tool call, does the same.
- A paused system is different: the check answers `Waiting` without recording anything, and the pause publishes `SystemEvents.SystemPaused`. A pause with `stopRunning` cancels the running turns of the conversations bound to the system (`ConversationSwitches`), and those turns then push their work with the token.
- None of this reaches a run that holds its token: "disconnecting the account, withdrawing the grant or disabling the credential stops only the next reveal" (R44, 8.33, §6.6).

**The model relay does this per request.** The server's relay checks a run's one-run token at every relayed request (`RunModelTokens.active`), and revokes it when the run ends (ADR-0059). Git cannot copy that shape without passing every clone and push through the server (R29). ADR-0112 rejects that shape again.

**The protocol has what this needs.**

- Optional capabilities are feature names in `hello.features`. The server sends a feature's frames only to a host that lists the feature (ADR-0109; CONVENTIONS §14.10). ADR-0113 made one exception, a change of `hello.isolationTiers`'s values that a server and its VM hosts take together, and called it the only one.
- A host asks the server with `run.request {kind, payload}` and gets exactly one `run.request.ack`. `TOOL` requests run outside any transaction (`RunRequests.call`), because they call other systems.
- The server's durable commands to a host are `run_command` rows. Today there is one type, `CANCEL`, which stays `PENDING` until the run ends and is sent again when the host says hello.

**No GitHub App exists.** ADR-0007 decided that each installation makes its own App. PLATFORM §14 lists one, and A10, 8.2, 7.6 and Q11 wait for it. Q11 asks for its permissions without `workflows`.

**ADR-0112** puts every token on a control host that runs no agent code. It also says that this shortens nothing. Decision 7 builds TIN-42 first, for every host and edition, and for the control host afterwards.

## Decision

**When a binding fails its check, the server tells the run's host to drop that repository's git token. This holds on every code host. The host's git proxy, its own git and its take-back record then forget the token. The proxy refuses the sandbox's next fetch, and the push of the run's commits at its end fails with a message that names the reason. On GitHub, a credential backed by the company's GitHub App gives each run installation tokens of its own. They are limited to the run's workspace repositories and to `contents` and `pull_requests`, never `workflows`, and they are valid for GitHub's hour. The host renews them through the server, and the server checks the binding again at each renewal. GitLab keeps its tokens and gets the revocation alone. Both parts are optional features of runner protocol 2.**

1. **The frame `run.git.revoke`** (server to host).

   | Field | Meaning |
   |---|---|
   | `type` | `run.git.revoke` |
   | `runId`, `epoch` | The run and its assignment, as in `run.cancel` |
   | `componentIds` | The repositories whose token goes (`workspaces[].componentId`): one to 20, always named. No "every repository" form, so a frame never means more than the server checked |
   | `reason` | A code: the binding's reason (`RECONNECT_YOURS`, `RECONNECT_COMPANY`, `SUSPENDED`, `NOT_ENTITLED`, `GRANT_REMOVED`, `LEFT_GROUP`, `IDENTITY_CHANGED`, `HOLDER_LEFT`, `SYSTEM_REMOVED`, …), or `SYSTEM_PAUSED`, `CREDENTIAL_REPLACED`, `REFRESH_REFUSED` or `BINDING_CHANGED` (settled while building: a binding that holds but changed since the run cloned, found before a cancel, below). Like the request codes, the schema lists them as examples; it fixes only their form, `^[A-Z][A-Z0-9_]{0,63}$`. The host decides nothing from the code, and a code it does not know is no error |
   | `message` | Text that the server writes for the run's log and the agent, at most 1000 characters, e.g. "Tinfirm revoked this run's access to acme/shop: the credential 'CI bot' was disabled." |

   - **The feature `run.git.revoke`.** A host that implements the frame lists it in `hello.features`. The server sends the frame only to such a host.
   - **Durable, confirmed by the host.** The server writes a `run_command` row of the new type `REVOKE_GIT`, with the run's epoch, the component ids, the reason and the message (V087). It sends the frame after the commit. The row stays `PENDING` until the run ends, and goes again at every `hello` that lists the run, as `CANCEL` does, but only for the run's current epoch, and before any `run.cancel` of the same `hello`. A run may have several such rows, one per cause; each names only repositories that no earlier row of the same epoch named, so `CANCEL` alone keeps its one pending row per run. The host applies the frame once and ignores it after that. It reports the revocation in a run event (decision 3). Settled with the owner's decision of 2026-11-20 on Q48: the host also confirms it with `run.git.revoked {runId, epoch, componentIds}` (host to server, the same feature), once it has dropped the tokens from its holder and written its take-back record again. It names exactly the repositories of that frame that the run has, also those it had revoked already, so a frame that comes twice is answered the same; for an unknown run or another epoch it sends nothing. The server takes it only from the host the run is assigned to, for that epoch, and ignores any other without an `error`. The rows that name one of those repositories become `CONFIRMED` with `confirmed_at`, and the first confirmation of each is audited `run.git_revoke_confirmed`. A row that stays `SENT` is sent again at the next `hello`, as before; a confirmed one goes again too, which changes nothing.
   - **Settled while building: when else it goes.** Also when the host accepts the run (`run.accepted`), since a frame sent while `run.assign` was on its way may reach the host first, and the host drops a frame for a run it does not know; and when a heartbeat resumes a lost run. The row counts as sent (`delivery` `SENT`, `last_sent_at`) only once the frame was written to the host's connection, after the commit or after the answer to a host's frame was written; a send that fails leaves it to the next `hello`. A confirmed row stays `CONFIRMED` whatever write is recorded after it. A run that a host without the feature reports and that is cancelled has its revocations marked `UNSUPPORTED`: that host is never told.
   - **Settled while building: before every cancel of a reported run.** A cancelled run pushes its work, and a host can report a run long after the server stopped tracking it: a run lost longer ago than the resume window, whose rows its end completed, or a run that ended on the server. So before any `run.cancel` of a run that a `hello`, a heartbeat or a `run.accepted` reports, the server sends `run.git.revoke` for that report's epoch: every revocation recorded for that assignment, pending or done, and, for a run the answer's transaction holds locked, every repository of that assignment whose token the server would not let the run use now, which it records (completed), audits and sends there (`TurnSource.gitAccessGone`): its system removed or paused, its binding not `BOUND`, or its binding at another version than the token was revealed at (`BINDING_CHANGED`). This check at the report was chosen over recording revocations for `LOST` runs of any age, since the latter would write a row and an audit event per old run at every later cause, for ever, and would still miss a run that ended on the server (a cancel by a person) whose host comes back. Settled with the owner's decision of 2026-11-20: a heartbeat of an earlier epoch locks its run (its conversation first) and gets the same check. The check reads what that assignment cloned from `run_assignment_repository` (V087), which each assignment writes for its repositories with a binding's token, with the binding's version and the host it went to, and which a later assignment does not replace; its rows stay with the run, which is never deleted, since a host may report an execution at any later time from its take-back record. A run that a machine reports and that is of a company the machine is no longer in (its owner left it) gets the same before its cancel, in that company's context, with the run locked, but only when that assignment went to this machine (`run_assignment_repository.personal_host_id`): a host learns nothing of a run it does not hold beyond the frame for it. Settled after a review, 2026-11-24: the same holds inside a company. A host may name any run of its company in a `hello`, so all of this is done only for an assignment that went to the reporting host: to its presence (`run_assignment_repository.runner_host_id`), or, for a member's machine, to the machine (`personal_host_id`), whose presence is a new one once its owner left the company and joined it again. The cancel of a run whose assignment of that epoch went to another host goes alone, and nothing is sent, recorded, audited or marked `UNSUPPORTED` for it.
   - **The run's view.** The Runs API's `RunRepository.gitRevoked {reason, message, revokedAt, delivery, confirmedAt}` shows the revocation on the repository it concerns, and the web app's run page shows it there ("Git access revoked", with the message); the conversation's turn line says that the commits were not pushed ("1 commit not pushed: git access revoked") and leads to the run's page. Settled while building, in place of a flag `hostTold`: `delivery` is `CONFIRMED` once the host answered `run.git.revoked` ("The runner host dropped the token."), `SENT` once the frame was written to the host's connection and not confirmed yet, `PENDING` while it was not written (the host was not connected, or the send failed: it goes when the host reconnects, before it can push), and `UNSUPPORTED` for a host without the feature, whose run keeps its token until it ends (`run_command.delivery`, V087).
   - **The end of a hello's answer: `welcome.done`.** Protocol 2 has no end to the frames the server sends again at a `hello`. So the server sends `{"type": "welcome.done"}`, no other field, to a host whose `hello` lists `run.git.revoke`, once per connection, as the last frame of its answer to the `hello`: after everything the reconciliation sends again (the pending `run.git.revoke`, then `run.cancel`), also when it sends nothing. It promises that every revocation of a run the `hello` listed, for the epoch it listed, that committed before `welcome.done` was written went on this connection before it. Settled with the owner's decision of 2026-11-20, in place of the earlier limit (a revocation that committed while the answer was written could come after `welcome.done`): every revocation of a run that has a host takes, before its insert, a shared transaction lock of that host (`pg_advisory_xact_lock_shared` on the host's id), held until its commit. After the answer's frames the server takes the same lock exclusively for each of the host's presences, in the order of their ids, which waits for every revocation that took it to commit and holds back every other; it reads in each company, in a transaction of its own, the revocations of the listed runs (for the listed epoch, of an assignment that went to that presence) that were never written to a connection, writes them, writes `welcome.done`, and only then lets go. This is sound: a revocation that committed before the exclusive lock is read, unless it was written already; one that had not committed then cannot commit before `welcome.done` was written; none is lost, since the after-commit path and this one both write a row that is not yet written and both only advance its delivery; and a duplicate is harmless, since the host applies a frame once. The reads take no row locks, so the hold waits on nothing that waits on it. A push already under way when a revocation arrives finishes (decision 5). A host sends nothing back for a `run.git.revoke` of an unknown run or another epoch (unlike a `run.cancel`, which it answers `error` `UNKNOWN_RUN`); a host of protocol 1 never gets either frame and answers an unknown type `error` `UNKNOWN_TYPE`.
   - **A host without the feature** gets no frame. The run keeps its token until it ends, as today; the ticket keeps this behaviour for older hosts. The audit event says so (`sent: false`), and the conversation's note says that the run keeps its token until it ends, once per revocation and on every path (the run module publishes `RunEvents.GitTokensKept` in the revocation's transaction, which the conversation module turns into the note: a suspension and a leaving member's included).

2. **What sends it, and for which runs.** A listener of the conversation module (`GitRevocations`) runs inside the transaction that changed the binding (an `@EventListener`, not after the commit), so that the command is durable with the change; the run module's port (`RunGitRevocations`) writes the command, audits it and sends the frame after the commit. A pause revokes in its own transaction, before its dependents cancel anything. Settled while building, the rule everywhere: where one cause both revokes a run's git token and cancels the run, the revocation is written in the transaction that cancels, before the cancel, so that its frame, registered after the commit before the cancel's, reaches the host first. A principal's suspension does so in the transaction that cancels the runs it acts for or pays (`RunSwitches`): first the `BOUND` bindings that act through its accounts (`SUSPENDED`, `TurnSource.bindingsHeldBy`), then the cancels; the bindings' own change after the commit finds those repositories revoked. A user's deactivation, by an instance admin or by SCIM, is such a suspension (cause `USER_DEACTIVATED` or `SCIM`): its cancelled runs do not push the work the agent committed, because the user's credentials must no longer act, and the revocation's message says so on the run's repository (settled while building: "the account's holder was suspended because their Tinfirm account was deactivated", or "… because the company's identity provider deactivated them"; an admin's suspension keeps "the account's holder was suspended"). Settled while building too: the suspension's bindings change after the commit as well, beside its cancel, and a revocation that transaction records sends its frame after its own commit, which the cancel's frame could overtake; so every live cancel sends first the run's revocations that another transaction recorded (`GitRevocationService.beforeLiveCancel`), as the answer to a `hello` does before its cancels (decision 1). A member who leaves does so in the leaving transaction, before each of their conversations' turn is cancelled: every binding of the conversation that holds (`HOLDER_LEFT` for their own account, `LEFT_GROUP` for a credential lent to their group), since the conversation ends and no later check would look at it. A system's removal and an account's deletion cancel no run, and revoke after their commit as any binding's change. A service account is suspended, never removed. The company's stop revokes nothing (decision 2, below), and its cancelled runs push their work, as every cancelled run does: the owner's decision of 2026-11-20 ("Questions the owner answered", 6). The causes:

   | Cause | Event | Runs and repositories |
   |---|---|---|
   | A bound binding fails its check, for any reason and on any path: an account disconnected or needing a new sign-in, a credential disabled, a grant or a lending changed or withdrawn, a person who left the grant's group, a holder suspended or gone, a system removed, an identity changed | `ConversationEvents.BindingWaiting`, `BindingGone` | The runs with a `run_repository` row of that `binding_id` |
   | A system paused, with or without `stopRunning` | `SystemEvents.SystemPaused` | The runs with a `run_repository` row of that `system_id`. With `stopRunning`, the revoke goes before the cancel, since a cancelled run pushes its work |
   | A trigger's binding that follows another credential after a replaced lending (ADR-0072) | `conversation.binding.bound` with `followed` | The runs of that binding: their token belongs to a credential that the service account no longer borrows (`CREDENTIAL_REPLACED`) |
   | A refresh that the gate refuses for good | Decision 9 | That run's repositories in the request |

   - **Which runs.** Runs that are `ASSIGNED` or `RUNNING`, and `LOST` runs within the resume window (written completed with the run's end, as the run's other commands are, so that the run's resumption opens it again; sent at once when the lost run's host is connected and lists the feature, since it may still run it, and again when a heartbeat or a `hello` resumes it). Only the repositories of the run's current assignment count: `run_repository` gains the assignment's `epoch` and the `component_id` that `run.assign` named, which a repository's removal does not clear (V087). A run outside these is checked when its host reports it (decision 1).
   - **Settled while building: the upgrade.** V087 gives the rows of the runs whose current assignment may have reached a host their epoch: `RUNNING`, `LOST`, and assigned (`QUEUED` with `dispatched_at`). Settled with the owner's decision of 2026-11-20: those rows with a binding also get `binding_version` 0, every binding's version at the upgrade, and their assignment's record in `run_assignment_repository` with the run's host, so that the check for `BINDING_CHANGED` and the check of a later report work for them; a change of the binding between the reveal and the upgrade cannot be told apart, and a run whose host was removed gets no record. An assignment's third phase writes its rows and marks it sent in one transaction, after it deleted an earlier assignment's rows, so an assigned run's rows are its current assignment's once that was sent; one whose third phase had not committed when the server stopped was never sent and never is, and a revocation of its rows names an epoch no host runs, which the host ignores, until the accept timeout takes the run back.
   - **The race with an assignment in progress.** `run_repository` rows are written in the third phase of an assignment, after the second phase revealed the tokens. So the third phase's transaction (`RunDelivery`) reads again the bindings of the rows it writes (`TurnSource.workspaceRevoked`). Where one is no longer `BOUND`, or its system is paused or gone, it sends nothing. Settled while building: nor where the binding is no longer at the version the gate checked when it revealed the token (`conversation_binding.version`, V087, which a trigger moves at every change of the binding's state, kind, account, holder or grant; `TurnSource.Workspace.bindingVersion`, kept in `run_repository.binding_version`): a trigger's binding that followed another credential, or one that waited and was bound again, would otherwise send the old credential's token. This holds for a GitHub App's binding as for any. It revokes the relay's token as for a stale assignment, and the run goes back to the queue, where the next pass says why. Once that phase has committed, the listener finds the run. The phase locks the workspace's systems `FOR SHARE` in the order of their ids, then the conversation's row, then the run's: a pause, which holds its system's row, and a binding's change, which holds the conversation's, either commit before the phase reads or wait for it and then find its rows.
   - **What does not send it.**
     - The kill switches that hold (ADR-0105, decision 3): the company's stop, a paused agent, a paused trigger. They cancel runs or let them finish by their own rules (C§15.13). At a refresh they answer `GIT_HELD` (decision 9).
     - A repository that leaves the workspace because the agent no longer lists it. That takes effect at the next turn.
   - **The audit events.** `run.git_revoked`: its actor is the actor of the transaction that changed the binding: the admin who paused the system, the person whose use found the binding failed, and SYSTEM for package 1's events (a credential disabled, a grant withdrawn), which reach the bindings after their own commit; that change's own event (`credential.changed`, `grant.deleted`) names the admin. Its target is the run, with `conversationId`, `bindingId` (or `systemId` for a pause), `componentIds`, `reason`, `epoch`, `sent`, and `delivery` (`SENT`; `ON_RECONNECT`, a host not connected now; `UNSUPPORTED`, a host without the feature). There is one event per run and cause, and it records what was meant at the commit. `run.git_revoke_confirmed` (settled with the owner's decision of 2026-11-20): one per revocation when its host first confirms it, actor SYSTEM, with `conversationId`, `componentIds`, `reason`, `epoch` and `runnerHostId`. Neither carries a token.

3. **What the host does.** A run's tokens get one holder per run (planned name `RunGitTokens`). It keeps, for each repository, the token and its expiry, or why the token is gone. The proxy's route, the run's `Git`s and the take-back record read from it, in place of the three copies of today. For each repository that a `run.git.revoke` of the run's current epoch names, the host does the following. It ignores a frame for another epoch, as it does a `run.cancel`.

   | What | After the revocation |
   |---|---|
   | Memory | The holder drops the token and keeps the reason and the message |
   | The take-back record | The host writes the record again, whole and 0600 as today. The repository's `git` is null, and a new optional field `revoked` names the repository with the message. A host that restarts then neither uses the token nor pushes the repository. The record's format version stays 1 for a record that only drops a revoked token; a record that keeps a run's own end ([ADR-0101](0101-closing-the-elastic-runners-gaps.md), amended 2026-11-23) is version 2, which a host before it discards rather than misreads |
   | The git proxy | The route stays. Each new request gets 403 with the server's message as plain text, as `git-receive-pack` gets today |
   | A clone or mirror fetch not yet started | Fails with `cannot clone <repository>: <message>`, `GIT_ERROR`, as a failed clone does today |
   | The mirror fetch before the push | Is not attempted. The scan compares with the refs at clone time, as after a failed fetch today |
   | The push of the run's commits | Is not attempted. The repository's error is `<repository>: not pushed: <message>`, the run's `failureMessage` is "git failed in …", and its class is `GIT_ERROR`. The `git` result says `pushed: false` with the commits counted |
   | The redaction | The token stays on the run's list: what was revealed stays redacted. After the host restarts too: the take-back record keeps salted hashes of every token the run has held, and a run taken back redacts and scans with them |
   | The run's events | A `LOG` event at `warn` with the message, which the run's page and the conversation show |

   The repositories that the frame does not name go on as before.

4. **What the run sees, and how it ends.** As the ticket proposes, the run goes on without git for those repositories (the owner's answer 1).

   - The agent's next `git fetch` fails, and so does a blob that a partial clone fetches lazily. Both fail with the proxy's 403.
   - The sandbox's own `git push` was refused before the revocation as well. The push that fails is the host's push at the end, and it fails visibly. A revoked repository with commits ahead ends the run `FAILED`, `GIT_ERROR`, with a message that names the repository and the reason. A revoked repository without commits fails nothing. The other repositories are pushed as usual.
   - The commits that were not pushed stay only in the host's kept failed workspace (`keep_failed_workspaces`). With the bridge they are nowhere else.
   - The conversation's binding already waits or is gone, so its next turn waits for its card, as today.

5. **What is not revocable.**

   - **A request in flight** that already carried the token: a fetch through the proxy, a mirror fetch, or the host's push. Each finishes, and its result is reported as it is.
   - **What is in the sandbox already:** the clone, its objects, and what the agent read.
   - **The token at the code host.** A run's revocation does not revoke a member's personal access token or OAuth grant at GitHub or GitLab. A copy taken from the host's memory before the revocation keeps working: a personal access token until someone rotates it at the code host, an App's token until its hour ends. Decided by the owner, 2026-11-19: a revoked App token stays valid at GitHub until its hour ends, because the server stores no run's token (decision 8) and does not call GitHub's revoke.
   - **A host without the feature**, and a host that is disconnected, until its `hello`. The run's lease (30 s) and the reconnect grace (2 minutes) bound how long that is.
   - **A host that does not obey**, such as a modified binary. A company host is trusted with what it reports (5.13).

6. **A GitHub App on a `GITHUB` system.**

   - **What the system holds.** A `GITHUB` system can hold one GitHub App: the App's id, and its private key as a managed company secret of the system (a new secret kind; planned name `SYSTEM_GITHUB_APP_KEY`). The key is never shown again; an admin rotates it by replacing it. The system's OAuth app for members' sign-in stays as it is.
   - **The API.** `GET`, `PUT` and `DELETE /systems/{systemId}/github-app`, `PUT` with `{appId, privateKey}`, all with `MANAGE_SYSTEMS` (settled while building: the view names the permissions to give the App and counts the connected hosts that cannot renew its tokens, `hostsWithoutAppTokens`; the problems are `400 GITHUB_APP_REFUSED`, `409 GITHUB_APP_IN_USE`, `409 GITHUB_APP_REQUIRED`, `409 GITHUB_APP_CHANGED`, `409 DUPLICATE_INSTALLATION` and `502 GITHUB_UNREACHABLE`; the App is kept in its own table, `system_github_app`, V088). The server checks the pair by asking GitHub for the App, with a JWT that the key signs. `DELETE` on the same path answers `409` while an `APP` credential remains. Settled while building: so does a `PUT` with another `appId` (`409 GITHUB_APP_IN_USE`), since such a credential stands for an installation of the App an admin verified, and another App's key would mint for it; a `PUT` with the same `appId` replaces the key, which is its rotation. Adding an installation (`POST …/credentials/app`) asks GitHub with the key of the App it read first, and stores the credential only while the system's App is still that one, the same id and the same key secret, which it locks `FOR SHARE` until its commit; else `409 GITHUB_APP_CHANGED`. `GET …/github-app/installations` lists the App's installations: the account's login and type, and its repository selection. The audit actions are `system.github_app_set` and `system.github_app_removed`, beside the vault's `secret.*`.
   - **The web app.** On the system's page an admin sets the App's id and key and sees its installations. The **Add credential** dialog gains "GitHub App installation". The page names the permissions to give the App: Contents and Pull requests (read and write), Issues and whatever the system's tools need, and never Workflows. It says how many of the company's hosts lack `run.git.refresh` (decision 12).
   - **No vendor App.** The App is the company's own: each installation of Tinfirm registers its own App (ADR-0007). An App that the owner might publish is not part of this decision.
   - **Scope.** One App per system (the owner's answer 2), on github.com and on GitHub Enterprise Server (answer 3), whose half is untested against a real server.

7. **Credentials backed by the App; members' own accounts.**

   - **A new kind `APP`.** A credential of kind `APP`, beside `TOKEN`, `OAUTH` and `CLIENT`, is one installation of the system's App. An admin chooses the installation from the list (`POST /systems/{systemId}/credentials/app {name, installationId}`). It holds the installation's id and the account's login, and a system has at most one credential per installation. Settled while building: its identity on the system is `installation:{id}`, which no member's own account can be, in place of the App's bot user, which GitHub would have to be asked for and which this build has not verified. It takes no token, sign-in or client credentials. It is lent to groups and service accounts, disabled and removed like every credential (ADR-0072). Only such a credential is "backed by the App".
   - **The server's own uses.** Tool calls, change requests, the write-back, polls and the catalogue reveal the credential as `CLIENT` does (ADR-0093). The account module mints an installation token under the refresh lock when the last one expires within the margin (five minutes), and keeps it in the credential's secret. GitHub refusing the App or not knowing the installation (401, 403, 404) turns the credential `RECONNECT`. It asks for the installation's permissions less `workflows`, so that no token Tinfirm mints carries `workflows`. This token never goes to a runner host.
   - **Members' own accounts.** They keep their OAuth or personal access tokens on GitHub and on GitLab, and get the revocation alone (decisions 1 to 5). A GitHub App's user tokens (PLATFORM §14) are not part of this decision.
   - **A repository outside the installation.** The App cannot mint for a repository that the installation does not cover. The content of the assignment then answers `NotReady` with `Cancel`, and a message that names the repository and the installation: an admin installs the App there, and the person retries. Settled while building: a repository whose clone URL names another owner than the installation's account is refused before GitHub is asked; one GitHub refuses to mint for (422 or 404) is refused the same way.

8. **A token per run.**

   - **When.** In the assignment's second phase, for a binding on an `APP` credential, `TurnSourceImpl.content` calls `ConversationBindings.use` with the purpose `run:{runId}` and a scope: the run's workspace repositories of that binding, each with its access. The gate checks everything it checks for any reveal (ADR-0105). The account module then mints outside any transaction, audited as `secret.accessed` with the purpose `run:{runId}`.
   - **What it asks GitHub for.** One token per credential and access:

     | The repository in the run | Permissions | Repositories |
     |---|---|---|
     | `WRITE` | `contents: write`, `pull_requests: write` | The run's `WRITE` repositories of that installation |
     | Read-only (a `READ` grant or lending, or read-only for the cause `AGENT` or `REQUEST`) | `contents: read`, `pull_requests: read` | The run's read-only repositories of that installation |

     So a run has at most two tokens per credential. They never carry `workflows` or any other permission.
   - **Lifetime.** GitHub's hour from the mint. `workspaces[].git` gains the optional `expiresAt`, an RFC 3339 instant.
   - **The mirror key.** `workspaces[].git` also gains the optional `mirrorKey`: a stable key that the server derives from the credential's id, the lowercase hex of a SHA-256 over `tinfirm-git-mirror:v1:{companyId}:{credentialId}`, never derived from a token. `expiresAt` and `mirrorKey` come together or not at all. The host names the mirror from `repoUrl` and `mirrorKey` in place of the `Authorization` header. The host keys the mirror with it in place of the token's hash. Otherwise a new token every run would make a new mirror every run (`mirror.rs` keys by the `Authorization` header). The mirror still holds what one principal's credential fetched (M15).
   - **What the server keeps.** Neither the vault nor the database keeps a run's token. The server sends `expiresAt` and `mirrorKey` only to a host that lists `run.git.refresh`.
   - **Placement.** A run with a binding on an `APP` credential goes only to a host that lists `run.git.refresh`, as a run with skills goes only to a host with `run.skills`. Otherwise it waits with the new queue reason `NO_HOST_FOR_APP_TOKENS`.

9. **The refresh: `run.request` of kind `GIT_TOKEN`.**

   - **The feature `run.git.refresh`.** The host reads `git.expiresAt` and `git.mirrorKey`, and renews a token before it expires.
   - **When the host asks.**
     - When a token has 10 minutes or less left.
     - Before the push at the run's end, when it has 20 minutes or less left.
     - After it took a run back, once it is connected (decision 10).

     One request covers every repository whose token is due, and the host asks at most once a minute per repository.
   - **The request.** `payload {componentIds}`, one to 20. At most one `GIT_TOKEN` request of a run waits for its answer; another is `REJECTED TOO_MANY_REQUESTS` at once. A host that lists `run.git.refresh` lists `run.git.revoke` too.
   - **The answers.**

     | Answer | `payload` or `code` | The host |
     |---|---|---|
     | `DONE` | `{git: [{componentId, username, token, expiresAt}], refused: [{componentId, code, message}]}`: each repository of the request in exactly one of the two. `refused` holds the repositories that have one of the three codes below while others got a token | Takes the new tokens into its holder, its redaction and the take-back record; keeps the old ones on the redaction list. Treats each entry of `refused` as the answer of its code below; an unknown code as `GIT_UNAVAILABLE` |
     | `REJECTED` `GIT_REVOKED`, with `message` | No repository got a token, and for each: the binding waits or is gone, its system is paused, a `REVOKE_GIT` command names the repository, or the repository is not one of the run's on an `APP` credential | Applies it as a `run.git.revoke` with that message (decision 3) |
     | `REJECTED` `GIT_HELD` | No repository got a token, and the gate answered `Held` for each: a kill switch | Keeps the token until it expires, and asks again |
     | `REJECTED` `GIT_UNAVAILABLE` | No repository got a token, and for each GitHub could not be reached, or answered 5xx or 429 (`BindingUse.Failed`) | The same |
     | `REJECTED` with a protocol code | `RUN_NOT_ACTIVE`, `INVALID_REQUEST`, `TOO_MANY_REQUESTS` | As for any request |

   - **A token that expires without a new one** goes as at a revocation (decision 3), with the message "the git token expired and Tinfirm could not renew it". The server did not revoke it, so nothing is audited as `run.git_revoked`.
   - **The server's checks.**
     1. The run module checks what it checks for every request (the kind, the run `RUNNING` on this host with this epoch, the payload an object).
     2. It hands `GIT_TOKEN` to its implementation outside any transaction, on a virtual thread, as it does `TOOL`, since a mint calls GitHub. The answer comes within 30 seconds, which is how long the host waits, as for `ACCESS`.
     3. The implementation takes only the run's own repositories (`run_repository`) on an `APP` credential that no `REVOKE_GIT` command names.
     4. It calls `ConversationBindings.use(binding, "run:{runId}", scope)` again. So the binding's check, the kill switches and the personal-host rule are all checked again.
     5. The access is the lower of the assignment's and the current one. A grant lowered to `READ` therefore gives a read token, and the push fails visibly.
     6. Each mint is `secret.accessed` with the purpose `run:{runId}`.
   - **A refusal for good is a revocation.** A `GIT_REVOKED` answer also writes the `REVOKE_GIT` command and the audit event of decision 2 (`REFRESH_REFUSED`, or the binding's reason). So a repository once revoked stays revoked for the rest of the run, also when its binding holds again.

10. **The end of a long run, and a host that restarts.**

    - **The final push needs a valid token.** The host renews before the push (decision 9), and the mirror fetch and the push use the new token. If the server refuses, or the token has expired while the server could not be reached, the repository is not pushed. The run says so (`GIT_ERROR`), as after a revocation. A run that a person cancelled pushes its work, so the same holds for it.
    - **With the default limit of 60 minutes,** a run's first token barely covers the run, and the push at its end almost always renews it.
    - **A host that restarts** (ADR-0101). The take-back record keeps the latest token and its expiry. A restarted host takes its runs back before its `hello`, and can renew only once `welcome` has come. Settled with the owner's decision of 2026-11-20 on Q48, in place of an earlier rule that pushed after 2 minutes without `welcome.done`: a host that took a run back pushes it, and uses its git tokens, only once the current process has had the server's `welcome`, and, from a server that lists `run.git.revoke` in `welcome.features` (decision 12), `welcome.done`; there is no time limit. The take-back record stays, marked collected, until the run ends. `welcome.done` follows every revocation of its runs that committed before it was written, those of the runs it cancels included (decision 1), and the host renews first where the token is due; a revocation that commits later is applied when it arrives. An older server, which sends no `welcome.done`, lets the host go on at `welcome`. A server that cannot complete its answer once `welcome` was sent (the reconciliation or the end of the answer fails) sends `error` `INTERNAL_ERROR` and closes the connection with 1011, which the host does not take as fatal: it reconnects, and its next `hello` is answered whole. So no connection stays open after a `welcome` without its `welcome.done`.

11. **GitLab: revocation alone.**

    - GitLab's accounts and credentials keep their tokens and get decisions 1 to 5. So does a `GIT` system's.
    - GitLab has no equivalent of an installation token for a member's own account. Minting project access tokens per run (ADR-0023's "project access tokens per job") is recorded as a follow-up, to be built once there is demand. It would fit decisions 8 and 9 as a second kind of credential that mints, with the same feature `run.git.refresh`.

12. **Order and compatibility.**

    - **Two features, no lock-step.** `run.git.revoke` and `run.git.refresh` are features in ADR-0109's sense. No existing field changes its values, there is no new protocol version, and server and hosts are upgraded in either order. ADR-0113's exception stays the only one.
    - **The new request kind.** `GIT_TOKEN` joins the schema's `run.request.kind`. A host sends it only for a token that has an `expiresAt`, which only a server of this decision sends.
    - **What ships first.** The revocation ships first, server and host, for every code host. The App follows. Both ship before ADR-0112's split is released (decision 7 there), and both hold for every kind of host: Docker, a VM per run, a single machine, and later the control host, which is the runner host the server already knows.
    - **Placement.** A run on an `APP` credential needs a host that lists both `run.git.refresh` and `run.git.revoke`.
    - **The server's features in `welcome`.** Settled while building: `welcome` gains the optional `features`, every optional feature of protocol 2 the server implements, sent by a server of this decision and later. A host that took a run back waits for `welcome.done` (decision 1) only when `welcome.features` lists `run.git.revoke`; with an older server it pushes as before, without waiting, which keeps "works as today" for the mixed releases below.
    - **Mixed releases.**

      | Server | Host | What happens |
      |---|---|---|
      | This decision | Older | No revocation frame: the run keeps its token, and the audit event says `sent: false`. A run on an `APP` credential never goes to this host (`NO_HOST_FOR_APP_TOKENS`) |
      | Older | This decision | The host lists both features, and the server ignores names it does not know. No frame comes, and no `expiresAt` or `mirrorKey`: the host works as today |
      | This decision | This decision | Everything above |

    - **Set up the App after the hosts.** An admin should set up the App once the company's hosts list `run.git.refresh`. Until then the App's runs wait, and the App's section of the system's page says how many hosts lack the feature.

## Consequences

- **R44 closes for a host with the feature.** A disabled credential, a withdrawn grant or lending, a suspended holder or a paused system stops the run's next fetch through the proxy, and the push at its end. The ticket's acceptance criterion is that this happens within a second of the change's commit, with an integration test against a fake host and an end-to-end test against the real runner host.
- **An App-backed run's token** works for at most an hour, only for the run's repositories, and only for contents and pull requests. A copy stolen from the host is worth that much (R27, 8.33 for credentials backed by the App).
- **Q11 closes.** No token that Tinfirm mints carries `workflows`, so GitHub refuses a push that changes workflow files with such a token (to verify), and 7.6 is built for those credentials.
- **Members' own tokens stay long-lived and broad.** They gain the revocation, not a shorter life. On a company host they remain the largest standing exposure that R27 names, with GitLab's tokens.
- **A revoked run's unpushed commits do not reach the code host.** They stay in the host's kept failed workspace, if the operator keeps one. That is what a revocation means. The alternative, failing the run at once, loses the same commits (the owner's answer 1).
- **A cancelled run whose binding failed no longer pushes.** Today, pausing a system with `stopRunning` cancels runs that then push with the paused system's tokens.
- **A new credential to protect: the App's private key.** Whoever holds it mints tokens for every installation of the App (8.2, no longer hypothetical). It is a vault secret, revealed only to mint, and rotated on the system's page.
- **GitHub is called more:** one mint per run, credential and access at the assignment, one an hour per long run, and the server's own mints as for `CLIENT`. GitHub's limits on minting are to verify.
- **A mirror per credential, not per token,** for App-backed repositories (decision 8). Mirrors keyed by the token stay as they are for every other account.
- **The refresh is a second reveal of a run's git token through the gate.** ADR-0105 holds without a change: the refresh inherits the binding's check, the switches and the personal-host rule.
- **A kill switch that holds does not revoke.** A paused agent or trigger without `stopRunning` lets its runs finish, as it does today. An App-backed run's token then stops being renewed and ends within the hour, while a personal access token's run keeps its token (the owner's answer 5).
- **Nothing new passes through the server** but small frames and requests. Clones, fetches and pushes stay between the host and the code host (R29).
- **ADR-0112 is unchanged.** On a separated host the tokens are on the control host only; with this decision they are also shorter-lived and revocable there.
- **The threat model changes** when this is built:
  - R27: the App's tokens, the revocation, and members' tokens as the remaining exposure;
  - R44: closed for hosts with the feature, with decision 5's limits;
  - 8.33: the revocation, and App-backed credentials;
  - §6.6: the git token's row (an hour for the App's, a revocation path for all), and a new row for the App's private key;
  - Q11: closed;
  - Q41: closed for GitHub and for revocation, with GitLab's follow-up;
  - 6.20: the record loses a revoked token and holds an App's token for at most an hour;
  - A10, 8.2 and 7.6: the App exists.

## Alternatives considered

- **A git relay in the server,** the shape of the gateway that inspired the ticket, where every request is checked and the token is injected on the server. Rejected in the ticket and again in ADR-0112:
  - every clone and push would use the server's bandwidth;
  - git would be bound to the one replica that holds the runner connections (R29);
  - it would duplicate the host's git proxy and push lease, which work;
  - the host's own token would still be on the sandbox's machine.

  Once ADR-0112's control host exists, the control host is that relay, outside the server.
- **Rotating personal access tokens.** Tinfirm cannot rotate a person's own token.
- **Shorter run time limits.** They do not fit agents that work for hours.
- **The host asks the server before each git operation,** as the relay checks each model request. Every blob that a partial clone fetches lazily would cost a round trip to the server, and a server that cannot be reached would stop git. A durable command, sent once and sent again at `hello`, gives the same effect within a second.
- **Cancel the run in place of revoking the token.** A cancelled run takes its work back and pushes it with the token, so a cancel alone would push exactly what the revocation is meant to stop. It also ends the agent's turn where the ticket lets it go on.
- **Cancel the runs of a host without the feature.** Not chosen: the ticket keeps today's behaviour for older hosts, and the cancel would still push.
- **A revocation without repositories, meaning "every token of the run"** (the ticket's optional `repository`). Rejected: the server always knows which bindings failed, and a frame should never mean more than the server checked.
- **One token per repository.** More mints, and no narrower token than one per credential and access.
- **The installation's full permissions for a run's token.** That is what the ticket's narrowing exists to avoid.
- **A second lock-step release, as ADR-0113 had.** Not needed: everything here is new and optional, so a feature carries it.

## To specify and verify during the build

These are parts of the work, not of the decision. Each is settled when its code exists.

- **GitHub's API,** checked against GitHub's documentation and a real App before the build depends on it. This record states only these facts: an installation access token expires after one hour, and it can be limited to repositories and permissions when it is created. The build follows GitHub's REST documentation as its authors knew it, and is exercised only against a fake GitHub: no request reached GitHub or a GitHub Enterprise Server while it was built, and none of the following was checked against GitHub's published documentation or a real App during the build. Built as: `POST /app/installations/{id}/access_tokens` with `repositories` (names on the installation's account) and `permissions`; the JWT RS256 with `iat`, `exp` at most ten minutes later, `iss` the App's id; `GET /app`, `GET /app/installations` (paged by 100), `GET /app/installations/{id}`; a 422 for a repository the installation does not cover; the user name `x-access-token`. Still to verify:
  - the mint's endpoint and body (the repositories by name or by id, the permissions);
  - the App's JWT (its algorithm and its longest life);
  - how the installations are listed, and how a repository's installation is found;
  - whether `metadata: read` comes with every token;
  - whether a token can be asked for a shorter life than the hour;
  - whether a push that changes `.github/workflows/` is refused without `workflows`;
  - whether a token can be revoked at GitHub before it expires (Tinfirm does not, decision 5);
  - the user name for git over HTTPS with such a token (`x-access-token`, as the server sends today);
  - the bot user that an installation's credential reports as its identity;
  - the limits on minting.
- **What git in the sandbox shows** of the proxy's 403 text, and whether the agent learns the reason from it or needs another path, such as a `run.steer` where the host lists it.
- **The holder of a run's tokens** in the runner host, and how the proxy's route reads it on each request.
- **The take-back order** (decision 10), and the record's new field `revoked`.
- **`run_command`** for `REVOKE_GIT`: the migration's columns (the component ids, the reason, the message), its replay at `hello`, and its end with the run. Settled: V087 adds `epoch`, `component_ids`, `reason` and `message` to `run_command`, and `component_id` and `epoch` to `run_repository` (decisions 1 and 2).
- **The third phase's check of the bindings** in `RunDelivery`, and its test with a binding that fails between the reveal and the send. Settled: `TurnSource.workspaceRevoked`, and `GitRevocationIntegrationTest` (decision 2).
- **The refresh's margins** (10 and 20 minutes) and its pacing, measured against real runs.
- **The App's setup:** whether the system's page also offers GitHub's manifest flow to create the App (ADR-0007); and the queue reason's text.
- **The tests of the ticket's acceptance criteria:** a credential disabled during a run stops its next push within a second (an integration test with a fake host, and an end-to-end test against the real runner host); a run on an App-backed credential never receives a token valid for longer than an hour or for a repository outside its workspace (a fake GitHub).
- **The documentation:** the operator's pages on systems (setting up the App), accounts, and the runner protocol's features, and the release notes.
