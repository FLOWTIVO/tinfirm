## Context

- ADR-0040 made Tinfirm an MCP client of the company's servers, for agents. The owner now wants the opposite: a person's AI client, Claude Code first, controlling Tinfirm.
- A person's only credential is the browser session with CSRF (ADR-0008). The runner hosts' `tfr_` token is the one bearer precedent: shown once, its SHA-256 stored, on a stateless filter chain of its own.
- Everything below an endpoint exists: about 92 REST operations, `CompanyAccessGuard`, row-level security, the audit chain, the limits. A client must act as the member through the same services, never as a company-wide key with powers of its own.
- The MCP specification (2026-07-28) makes authorization optional; where an HTTP server has it, it is OAuth 2.1, with the server as a resource server (RFC 9728) and a discovered authorization server (RFC 8414). Claude Code does this, with Client ID Metadata Documents, pre-registered ids or dynamic registration, and also takes a static bearer header. It asks the person before each call of a mutating tool.
- Spring Boot 4.1.1 carries Spring Security 7, which holds the former Spring Authorization Server. No official Spring project covers MCP security; MCP Security for Spring AI is a community project at 0.1.x.
- PLATFORM.md §6: an agent never decides a decision. Claude Code is an agent.
- OIDC providers are instance-wide today (ADR-0008, ADR-0026). Companies want their own; a company without one uses local accounts.

## Decision

**Tinfirm serves an MCP endpoint per company to people's clients, as an OAuth 2.1 resource server, and is itself the authorization server over its own login. A client acts as the member who authorized it, with that member's role, through the services the web app calls, within the scopes the person granted.**

**Endpoint.** `POST /api/companies/{companyId}/mcp`, MCP Streamable HTTP in its stateless mode: no `Mcp-Session-Id`, no GET stream, no server push. It has a filter chain of its own, like the runner endpoint: bearer only, stateless, no CSRF. It ignores the session cookie and refuses every request with an `Origin` header, so a browser cannot call it. Its canonical resource URI is `{TINFIRM_PUBLIC_URL}/api/companies/{companyId}/mcp`, and a 401 names its protected-resource metadata, `/.well-known/oauth-protected-resource/api/companies/{companyId}/mcp`. It is JSON-RPC, outside `openapi.yaml`, so the module has its own tenant test that calls every tool as a member of company A against company B. A per-principal rate limit answers `429 RATE_LIMITED`.

**Authorization server.** Tinfirm is the OAuth 2.1 authorization server, on Spring Security 7's: authorization code with PKCE, refresh tokens, revocation, the JWK set, RFC 8414 metadata, one issuer named in the authorization response. The authorization endpoint needs a Tinfirm session, from the login Tinfirm has: a local account, an instance provider, or the company's own. The request survives that login (a `RequestCache` on the server, a same-origin `returnTo` in the SPA), which changes ADR-0008's redirect to `/` for this case only. The consent page is a web app route under the strict CSP that posts to `/oauth2/authorize` with CSRF and names the client, its domain, the company and the scopes. `/oauth2/authorize`, `/oauth2/token`, `/oauth2/jwks`, `/oauth2/revoke`, `/.well-known/oauth-authorization-server` and the protected-resource metadata become reserved paths; the OIDC client's paths stay.

**Client registration.** A client is known by its Client ID Metadata Document (CIMD) or by a pre-registered list. A CIMD `client_id` is an https URL: Tinfirm fetches it through the one outbound client and its guard (https only, no redirects, no private addresses), requires its `client_id` to equal the URL, caches it by its HTTP headers, accepts a loopback redirect URI with any port and others only exactly, and shows its domain on the consent page. The pre-registered list holds public clients that cannot do CIMD; which ones, and whether owners may add one, the owner decides as clients ask. Open dynamic registration stays off: the specification deprecates it in favour of CIMD, and it is a public, unauthenticated write endpoint.

**Scopes.** `tinfirm:read`, `tinfirm:write` and `tinfirm:decide`, each including the ones before it: read tools need the first, write tools the second, `decide` the third. The 401 advertises `tinfirm:read` only, so least privilege is the default and the person widens it on the consent page. A tool beyond the token's scope answers 403 `insufficient_scope` naming the scope it needs. Claude Code does not step up on that answer: it fails the call, and the person authorizes again and chooses a higher level, or pins the scopes in the client's configuration. A scope never widens a member's role: the guard decides every call, and a VIEWER with `tinfirm:decide` decides nothing.

**OAuth tokens.** Access tokens are JWTs of 1 hour; refresh tokens last 30 days and rotate on use; both are revocable. `aud` is the canonical URI of the company endpoint asked for (the `resource` parameter) and is validated, so a token for company A is refused at company B. The signing key is RSA, generated once and kept as an instance secret in the vault, which gains instance-level secrets for it: the same envelope encryption, never listed or revealed over the API. Spring's `oauth2_registered_client`, `oauth2_authorization` and `oauth2_authorization_consent` come by Flyway as instance-level tables, since a grant is a person's; it records the company it was consented for. A deactivated user's refresh and requests are refused, as their sessions are. The lifetimes are defaults the owner may change.

**Personal access tokens.** For scripts and CI, a user creates a token on `/me`: a name, one of the three scopes, an optional expiry. It is shown once, `tfp_` and 43 base64url characters; the server keeps `hex(sha256(token))`, `last_used_at` and the revocation in `api_token`, as `RunnerTokens` does for hosts. `GET` and `POST /api/me/tokens` and `DELETE /api/me/tokens/{tokenId}` go into `openapi.yaml` under a new tag `Tokens`; a user sees and revokes only their own, and holds at most 25 active tokens. A token is the user's, so it works at each company where the user is a member. Both credentials arrive as `Authorization: Bearer` on the one MCP chain: `tfp_` by its format, anything else through the JWT decoder. A session never reaches that chain, and a bearer never reaches the browser API.

**Consent.** The consent page offers all three levels whatever the client asked for: Read; Read and write; Read, write and decide. The level the client asked for is preselected, and deciding never is. The server treats a request for any `tinfirm:*` scope as a request for all three, so a consent may grant any level, and keeps the scopes the client sent to preselect one. The code and the tokens carry the level the person chose, and the token response's `scope` says so, as OAuth allows when the granted scope differs from the requested one.

**Web.** The consent page, and "Connected apps and tokens" on `/me`: the person's grants and tokens, each revocable, and the form that creates a token and shows it once.

**Tools.** The catalogue of the analysis §3.5, around what a person does rather than one tool per operation. Read tools first: `get_inbox`, `list_work_items`, `get_work_item` (by id or key), `list_comments`, `get_job`, `list_jobs`, `get_decision`, `list_decisions`, `get_run`, `get_run_transcript`, `list_agents`, `get_agent`, `list_connections`, `list_triggers`. Then the write tools: `start_conversation`, `start_thread`, `post_comment`, `cancel_job`, `retry_job`, `end_thread`, `close_work_item`, `cancel_run`, `run_trigger`, `poll_connection`, and `decide`. Every tool calls the service the controller calls, with the same inputs, so permissions, the usage policy, the one-active-run rule, the limits and the audit apply unchanged. A result is the REST DTO as `structuredContent` and a capped text in which other people's words are labelled; cursors pass through. Reads carry `readOnlyHint`; end, close and cancel carry `destructiveHint`. Admin surfaces stay off: agents, connections, triggers, members, secrets, runner hosts, credentials, uploads and `/api/admin/**`.

**Separation of duties.** Through this endpoint PLATFORM.md §6 holds because a person stands between the model and `decide`: the client's confirmation of each call is the person's act, as a click in the inbox is, and only a person grants `tinfirm:decide`, on the consent page or a token. The operations guide says never to allow-list `decide`, `post_comment`, `start_*`, `end_thread` or `close_work_item`, to give unattended use `tinfirm:read`, and `tinfirm:decide` only to a person at the keyboard.

**Companies' own identity providers.** A company's owner configures an OIDC provider on the settings page: issuer, client id, client secret in the company's vault, the email trust of ADR-0026, auto-provisioning; audited. `ClientRegistrationRepository` reads these registrations (`company-{companyId}`) beside the instance ones. The login page offers "sign in with your company" beside the instance providers and the local form. A user is still `(issuer, subject)`, never linked by email; a user a company's provider creates is a member of that company only, with the role it configured (VIEWER by default). Instance providers and local accounts stay. The authorization server needs only a session, so a company's SSO reaches MCP clients without OAuth work per provider.

**Library.** Spring AI's `spring-ai-starter-mcp-server-webmvc` (2.0.x), stateless, as ADR-0001 named. MCP Security (`org.springaicommunity`, 0.1.x) through its manual configurers, never its auto-configuration, which assumes it owns the filter chains: `McpAuthorizationServerConfigurer` with CIMD on and open registration off, `LocalhostWildcardPortValidator` and the audience customizer on the authorization server; the resource side uses Spring Security's resource server directly, so its `mcp-server-security` module is not a dependency. It is a community project whose APIs may change: pinned, in Dependabot's scope, its dozen glue classes small enough to vendor if it stalls. The heavy parts are Spring Security 7's own.

**Modules.** A new module `mcp`, at the top beside `sync`, depends on `work`, `agent`, `connection`, `run`, `identity` and `shared` and owns no table: it reaches the access guard through the services, and the audit through what they record. The authorization server, both tokens, the bearer resolver and the company providers belong to `identity`.

**Audit.** `token.created`, `token.revoked`, `oauth.consent.granted`, `oauth.grant.revoked`, and `oauth.client.resolved` with the client's domain. An action done through a grant or token keeps the `USER` actor and carries the `grantId` or `tokenId` in `details`, so the chain shows which decisions came from a tool.

**Instance admins.** An instance admin who is not a member reaches a company's endpoint with the same audited break-glass as in the web app. This is a default the owner may reverse.

## Consequences

- A person adds Tinfirm to Claude Code with one `claude mcp add --transport http` line; the first call opens the browser for login and consent. A company's SSO and its MFA apply.
- A client can do what the person can do in the web app, and nothing more. The tool catalogue is a second thin surface over the services.
- Tinfirm gains an authorization server on its public URL, with a trust boundary and threats of its own ([threat model](../threat-model.md) TB10). Whoever holds the signing key mints tokens for every company; it is rotated like a master key.
- Tool results put other people's words into the client's model. Tinfirm cannot make the client resistant; the person's confirmation and the scopes contain it.
- Stateless means the client polls. Sessions and notifications wait for the replica question (R29).
- The cost beyond the endpoint: the consent page, the login round trip, the key and instance secrets, four tables, "Connected apps and tokens", the company providers, the module's own tenant test.
- A 0.1.x community library sits on the security path; Spring Security does the heavy part, and the glue can be vendored.
- The deployment contract holds: new paths and tables, no new port, no renamed or required variable.
- Later: sessions and notifications, resources and prompts, admin tools, open registration if a client needs it, a CLI on the same tokens. The build follows the packages of the analysis §5.

## Alternatives considered

- **Validate the company IdP's own tokens.** Each provider would need a client, an audience and scopes for Tinfirm set up by its administrator, local accounts would have no way in, and no IdP binds an audience to one company's endpoint. Tinfirm's login already covers both.
- **A stdio MCP server beside the client.** The same token work in the server, and the API contract duplicated in a second codebase per release. Kept for air-gapped clients.
- **An OpenAPI-to-MCP bridge.** Operation ids as names, raw DTOs, nothing capped, every tool a write to the client. A demo, not a product.
- **A `tinfirm` CLI.** It complements MCP on the same tokens; later, if people ask.
- **Open dynamic registration.** Deprecated by the specification, and a public write endpoint. Can come later behind a rate limit, a cap and a sweep.
- **Spring AI without the library.** The glue (CIMD, loopback ports, the audience from `resource`, the 401's pointer) would be hand-written on Spring Security 7.
- **Hand-written JSON-RPC**, as `McpClient` and the runner host's `mcp.rs` are. No dependency, but spec drift and nothing beyond the four methods; ADR-0001 named Spring AI.
- **Vendor the glue now.** A fork to follow by hand; the exit if the project stalls.
- **One endpoint per user** with a company on every tool. Noisier tools, session state, no audience per company.
