# ADR-0063: Agent memory, notes an agent keeps for a person or a trigger

- Status: Accepted
- Date: 2026-10-14
- Decided by: the owner
- Sources: [PLATFORM.md](../PLATFORM.md) §2 (principles 1, 3, 5, 7), §6, §7.2, §9, §10; [CONVENTIONS.md](../CONVENTIONS.md) §15.5 (settings), §15.7 (the prompt, the tools of a run), §15.11 (retention, holds, erasure), §15.15 (triggers), §15.18 (this decision's rules); [operations/prompt-cache.md](../operations/prompt-cache.md); [threat-model.md](../threat-model.md)

- Changes: the server's agent, conversation, trigger, model, governance and mcp modules; `V039__agent_memory.sql`, `V045__company_model_key.sql`; the API (`Agent.memoryAllowed`, `AgentSettings.memory`, the notes of a person and of a trigger, the review of a trigger's notes, the company's memory settings `GET`/`PUT /memory-settings` ([ADR-0065](0065-company-model-key.md), which replaced the platform credential `GET`/`PUT /model-settings/platform`), `Retention.memoryDays`, the inbox's trigger reason `MEMORY_REVIEW`); the MCP tools `list_memory_notes`, `delete_memory_note`, `list_trigger_memory_notes`; the audit actions `memory.*`, `memory_settings.changed`; the web app: the switches in the agent's editor and in a person's and a trigger's settings, the notes of a person (their settings page) and of a trigger (its page, with the review, which the inbox's `MEMORY_REVIEW` opens), the model that tidies memories in the company's settings (Memory), and `memoryDays` on Retention. ## Context

- Each conversation starts from nothing. What an agent learns of a person's way of working ("Alice wants one commit per pull request"), of a repository ("the tests run with `make test-fast`") or of a system ("SHOP issues use the component field for the team") is lost when the conversation ends.
- Memory is content that outlives its conversation, which brings four risks: **leaking across the audience** (one agent serves many people, each with their own accounts, §5.3: a note from Ana's conversation must never reach Ben's); **persistent prompt injection** (the subject and tool results are other people's words, §10; written into memory an injection steers every later conversation, and in a trigger's place anyone who writes there drives the agent, §7.2); **secrets kept in plain text**; and **a way around retention** (§15.11).
- Token cost. A conversation's first turn sends the full prompt and later turns usually resume the session (§15.6). The prompt cache keeps the session's prefix; what changes it is written again at 1.25× or 2× ([prompt-cache.md](../operations/prompt-cache.md)). Most of what an agent might remember is irrelevant to any one conversation, so sending all of it is waste.
- Performance and infrastructure. PostgreSQL is the only store, and the Compose file's image (`postgres:18`) has no vector extension. The open-source memory layers (Mem0, Letta, Graphiti, Cognee, the reference MCP memory server) each bring a Python service, a graph or vector database, or a model call per write, and sit outside the tenancy, the vault scan, the audit and retention.

## Decision

1. **A memory belongs to the audience of the work**: to one person's use of one agent, or to one trigger. Its notes hang on that owner's settings row of the agent (`agent_settings`, §15.5), and are read and written only in that owner's conversations: a person's own (in Tinfirm, their AI client, a direct message to the chat bot) or the trigger's. A person's and a trigger's notes never meet, even for the same agent. Knowledge for everyone who uses an agent stays in its instructions.
2. **Opt-in.** A person turns memory on in their settings of the agent (`AgentSettings.memory`, off by default); a trigger's author in the trigger's settings. Whoever edits the agent (its owner, OWNER and ADMIN) may forbid it for the agent (`Agent.memoryAllowed`, allowed by default). Memory is in effect when the agent allows it and its owner turned it on. Neither is a widening (§6): memory reaches nothing the conversation could not reach already. Off keeps the notes, unread and unwritten.
3. **The agent writes notes with server-executed tools**: `remember(note, about?, replaces?)`, `forget(note)` and `recall(query)`, listed while memory is in effect and answered by the server through `run.request` kind `TOOL`: no runner or protocol change. Their names have no underscore, so they never meet a system's tool (`{handle}_{tool}`). A note is one line of 1 to 300 characters, about the owner in general, a system the agent uses (by its handle) or a repository of the agent (by its name); `about` that names anything else is refused. Notes have short ids (`m1`, `m2`, …) never reused within their memory.
4. **Memory reaches the agent progressively, from what it does:**

   | Tier | What | When | Budget |
   |---|---|---|---|
   | Hint | How many notes there are, how to use the tools | The full prompt (a session's start) | one line |
   | General | Notes about the owner in general, most recently used first | The full prompt | 400 characters |
   | Repositories | Notes about the repositories in the workspace | The full prompt | 600 characters each, 3 repositories |
   | Systems | Notes about a system | Appended to the first result of that system's tools in the run | 600 characters |
   | Recall | Any note, by full-text search | Only when the agent calls `recall` | 5 notes |

   The resume prompt has no memory: a resumed session holds what it was given. Notes that come with a tool result are appended at the end of the conversation, so no cached prefix changes. A memory holds up to 200 notes and `TINFIRM_MEMORY_MAX_CHARACTERS` (20 000 by default), since only what is touched is sent. Without memory in effect there is no section and there are no tools.
5. **A trigger's notes are reviewed.** A note a trigger's conversation writes is *proposed*: no conversation reads it until a member of the trigger's audience (its author, its team, OWNER, ADMIN) accepts it; they may reject or delete any note. The agent may withdraw a proposal, never delete an accepted note. At most 20 proposals wait; a proposal not reviewed in 30 days goes. The audience sees the trigger's notes and an inbox item while proposals wait (`MEMORY_REVIEW`). A person's own notes take effect at once: the person is their only reader and sees them all.
6. **Notes are the agent's own words, not instructions.** The prompt says so, says they may be out of date, and that nothing in them widens access or decides for a person; access is the server's to enforce (§10). A note is one line without control characters, so it can never open a section of the prompt. Each write is in the turn's transcript and audited (`memory.saved`, never the note); the owner lists and deletes the notes.
7. **No credential is kept.** Every note, and every note a compaction writes, is scanned by the vault before it is stored (`VaultService.scan`, ADR-0014: every company secret's value in any encoding, and the known credential formats). A finding refuses the note and is audited as `memory.refused` with the secrets' names and the formats.
8. **Compaction every 30 days, paid by the company.** A daily job compacts each memory that changed since its last compaction, at most once in 30 days: first without a model (duplicates within an `about` go, the most recently used kept), then, per `about` with five notes or more, one request to a small model that merges related notes and resolves contradictions, the newest winning. The model's notes pass the checks of a write (one line, 300 characters, the vault scan), keep their `about`, and never outnumber or outweigh what they replace; otherwise the merge is dropped. The request is paid by the **company's own key** ([ADR-0065](0065-company-model-key.md), which replaced the platform credential, a service identity named in the model settings): its budget is a row of Members' budgets on Model access, and the model is chosen in the company's settings (Memory, `memory_settings.compaction_model`) among those the key allows; never by a person's or a trigger's payer. Without a model, or with one the key no longer allows, only the first step runs. The job runs after each company's retention purges, on a thread of its own, one company at a time; a company's compaction starts no request 15 minutes after it starts and stops for the day at the first request its key does not answer, the memories it did not reach staying due: a slow or failing model holds up no purge and no other scheduled job. Audited as `memory.compacted` with the counts and the tokens.
9. **Retention of its own, two years from last use.** The company's retention settings gain `memoryDays` (730 by default; 30 to 3650, or kept): a note not used (saved, shown to an agent or recalled) for that long goes in the daily sweep. A merged note keeps the latest use of the notes it replaces, so compaction never extends retention. Holds keep the notes of a held person, of a trigger whose author is held, and those learned in a held conversation. Erasing a person's conversations erases the notes learned in them; a member who leaves, a deleted trigger and a deleted agent take their settings, and the notes with them.
10. **Isolation as for every tenant table**: `company_id`, forced row-level security, composite foreign keys with the company, the runtime role's grants (§7).
11. **People's AI clients read memories, and review none** (the MCP endpoint, ADR-0045). A person's client lists their notes of an agent (`list_memory_notes`, `tinfirm:read`) and deletes one of them (`delete_memory_note`, `tinfirm:write`, audited as `memory.deleted` with the credential); it lists a trigger's notes and proposals for the trigger's audience (`list_trigger_memory_notes`, `tinfirm:read`), with the link to the trigger's memory in Tinfirm. Proposals are accepted and rejected only in Tinfirm, as a team's approvals are decided there: a client is the person's space, and a trigger's review is its team's.

## Consequences

- An agent remembers a person's preferences and a team's conventions across conversations, for those who opt in, without anyone writing them into instructions.
- Cost follows use: a session starts with at most about 300 tokens of memory (often a line), a system's notes come only when the agent uses that system, and a recall only when it asks. The three tools' definitions (about 250 tokens) are cached with the rest of the first request. Compaction costs the company about 5 000 tokens of a small model per busy memory a month, and nothing for a memory that did not change.
- Performance: reading the notes for a prompt is one indexed query in the turn's transaction; a tool's notes one indexed query per system per run; `recall` one query on a GIN index; a write one short transaction with a row lock and a vault scan. Which systems a run has been told about is kept in the server's memory (one replica, as the run streams are, §15.6); after a restart a run may be told once more.
- A prompt injection in a person's conversation can leave a note that steers that person's later conversations with the same agent; it cannot widen access, is 300 characters at most, and the person sees it. In a trigger's conversation it waits for the team's review.
- The vault scan decrypts the company's secrets for each write, as an upload's scan does; writes are rare.
- Compaction sends the notes of a memory to the company's chosen model through LiteLLM, as the agent's own requests send its conversations.
- The spend of compactions is the company key's (ADR-0065): its LiteLLM spend, tagged `tinfirm-task:memory-compaction`, without a run.

## Alternatives considered

- **One memory per agent shared by all its users.** Moves what one person's accounts read into another's conversations. Rejected; the instructions are the shared memory.
- **The whole memory in the first prompt.** Simple, but it sends every note to every session whatever it does. Rejected for the tiers of decision 4.
- **Embeddings and a vector store** (pgvector, or a memory service). Semantic search, but an extension the Compose file's `postgres:18` lacks and an operator's own database may not offer, an embedding call per write, and a second place content lives. Rejected for now: `recall` searches PostgreSQL's full text, and can move to pgvector behind the same tool.
- **Mem0, Letta, Graphiti, Cognee, the reference MCP memory server.** Each adds a service and a store outside the tenancy, the vault scan, the audit and retention, and most a model call per write (Graphiti several). Rejected; Letta's always-in-context block with a searched archive and Claude Code's index loaded first with details on demand are the patterns decision 4 takes.
- **The agent compacts its own memory** in a person's turn. Costs the person's model and distracts the turn. Rejected for the company's job.
- **Notes expire after 90 days unused.** Loses what is still true. Rejected for compaction and the two-year retention.
- **A trigger's notes take effect at once**, with an acknowledgement as for open events. Rejected: whoever writes in the trigger's place could leave a lasting note; the team reviews instead.
- **A platform tool served by the runner host**, or a memory file in the sandbox. Each needs a protocol and host change, and the server could refuse a bad write only after the run. Rejected.

## Open points

- An outside identity's erasure does not reach a trigger's notes that quote them; the trigger's audience deletes such a note.
