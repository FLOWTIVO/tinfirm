## Context

- People read their email in Outlook and want an agent there: summarise this email, triage it, look at the code a customer complains about, draft a reply. Copying an email into Tinfirm by hand is the only way today.
- Outlook has two kinds of add-in. A **COM add-in** (.NET) runs in classic Outlook on Windows only, which Microsoft keeps "until at least 2029" and which the new Outlook for Windows does not load. A **web add-in** (Office.js) runs in classic Outlook on Windows, the new Outlook for Windows, Outlook on the web and Outlook on Mac, and an Exchange administrator deploys it once from the Microsoft 365 admin center. A web add-in is a web page in a task pane: in classic Outlook it is the top document of an embedded browser (WebView2), in the new Outlook and on the web it is a frame inside Outlook's page.
- Everything a task pane needs already exists for people's AI clients (ADR-0045): the MCP endpoint's tools start a personal conversation (`start_conversation`, origin `CLIENT`: the person's own accounts, settings and budget, the Owner's notice), follow it (`get_conversation`), list the agents the person may use (`list_agents`), and answer in a conversation (`send_message`); their `structuredContent` is the REST API's DTO. Tinfirm is the OAuth 2.1 authorization server, with consent per company, scopes, refresh tokens and "Connected apps" to revoke a grant.
- Three things stop a page in a task pane from using them. The MCP endpoint refuses every request with an `Origin` header, which a browser always sends on a `POST`. The REST API takes only the session cookie, which a frame inside Outlook's page does not get (it is a third-party cookie there). Every response carries `frame-ancestors 'none'` and `X-Frame-Options: DENY`, and a script-src of `'self'`, while Office.js must be loaded from Microsoft's CDN.
- Office's dialog API opens a window for a sign-in. Its first page must be on the task pane's own domain; the dialog may then go anywhere, and its page returns a message to the task pane with `messageParent`. The dialog and the task pane share no storage.
- Office.js sets `history.pushState` and `history.replaceState` to null; a router that uses them must keep them.

## Decision

1. **A web add-in, not a COM add-in.** One Office.js add-in for every Outlook that loads web add-ins, with Exchange Online, Exchange on-premises or Outlook.com mailboxes. It works when a person opens or selects an email; it does not run when an email arrives (automatic triage of incoming email is a matter for the server, later).
2. **Tinfirm serves it, from its own origin.** The task pane and the sign-in callback are routes of the web app, outside the shell: `/outlook/{companyId}` and `/outlook/callback`. No second application and no other host: the add-in is part of every installation, at its `TINFIRM_PUBLIC_URL`, and the person's computer needs to reach that URL, as for the web app.
3. **It is a client of the company's MCP endpoint, as a person's AI client is.** It calls `list_agents`, `start_conversation`, `get_conversation` and `send_message` over the endpoint's JSON-RPC, with a bearer token, and reads their `structuredContent` as the REST DTOs the web app already has types for. A conversation it starts is the person's own, with the origin `CLIENT`, their accounts and budget, the AI clients' hourly limit of starts and the Owner's notice, exactly as one Claude Code starts. It adds no operation to the REST API and no tool to the endpoint.
4. **A built-in OAuth client, `tinfirm-outlook`.** A public client of Tinfirm's authorization server with PKCE, like the MCP Inspector, whose one redirect URI is exactly `{TINFIRM_PUBLIC_URL}/outlook/callback`. The task pane makes the PKCE verifier and a state, and opens the dialog on `/oauth2/authorize` (the task pane's origin, as the dialog API requires) for the company endpoint's resource and `tinfirm:write`. The person signs in there as anywhere in Tinfirm (a local account, the instance's provider, the company's own) and chooses the level on the consent page, which names the client "Tinfirm for Outlook". The callback page returns the code and the state to the task pane with `messageParent`; the task pane checks the state and exchanges the code itself, so the verifier and the tokens never leave the task pane. It keeps the refresh token in its `localStorage`, per company; **Sign out** revokes it.
5. **The MCP endpoint admits Tinfirm's own origin.** `OriginRefusalFilter` refuses every request whose `Origin` is not exactly the origin of `TINFIRM_PUBLIC_URL` (scheme, host and port), with 403 as before; a request without `Origin` passes as before. The guard against DNS rebinding holds: a page that rebinds a name to Tinfirm's address sends its own origin, not Tinfirm's. The chain still ignores the session cookie, so only a bearer token reaches the endpoint. No CORS is configured: the task pane is same-origin.
6. **The add-in's pages carry their own headers.** A document under `/outlook/` gets a CSP that adds Microsoft's CDN, `https://appsforoffice.microsoft.com`, to `script-src` and `connect-src`, and `frame-ancestors 'self'` with Outlook's hosts (`TINFIRM_OUTLOOK_FRAME_ANCESTORS`, by default `https://outlook.office.com https://outlook.office365.com https://outlook.live.com`), and no `X-Frame-Options`. Every other path keeps the strict CSP and `X-Frame-Options: DENY`. The task pane loads Office.js only on these routes, after keeping the two history functions and putting them back once it has loaded. *Amended 2026-10-27 (M10 of the security review of that day): the CSP is path-scoped, not host-wide: `script-src` names Office.js's path `https://appsforoffice.microsoft.com/lib/1/hosted/` and the one file `https://ajax.aspnetcdn.com/ajax/3.5/MicrosoftAjax.js` it loads, `connect-src` the same Office.js path (threat model R50); a reply drafted from the pane is built from escaped text, never from rendered HTML.*
7. **A manifest per company.** `GET /api/companies/{companyId}/outlook/manifest` (any member) answers the add-in-only XML manifest: the task pane's URL with the company, the icons and the `AppDomain` at the public URL, the permission `ReadItem`, one button on the read surface that opens a task pane the person may pin, and an add-in id that is a name-based UUID of the public URL and the company, so that every download of it is the same add-in. An administrator uploads it in the Microsoft 365 admin center; a person may add it from a file under "My add-ins". The add-in-only manifest is the one every Outlook takes, Mac included.
8. **What the task pane does.** It shows the open email (subject, sender, date) and the agents the person may use, and asks one of them to **summarise** it, **triage** it, **investigate** it (with the agent's repositories, as any conversation gets them), **draft a reply**, or follow the person's own instruction. The request it sends is the instruction followed by the email's headers and plain-text body, fenced as other people's words and cut to fit the 100,000 characters of a message. It follows the conversation with `get_conversation` while the turn runs, shows the agent's result, and offers **Reply with this**, which opens Outlook's own reply form with the agent's text for the person to edit and send; it never sends an email. It remembers the conversation of each email on this computer, so that the pane shows it again when the email is opened again, and it opens the conversation in Tinfirm on request.

## Consequences

- Every Outlook that loads web add-ins reaches Tinfirm's agents with one installation and no new service. The add-in inherits the endpoint's rules: the person's role, consent, scopes, rate limits, the hourly limit of starts, the audit (`grantId`), and revocation under "Connected apps".
- A conversation started from Outlook shows as one from an AI client. A badge of its own is later.
- The refresh token sits in the browser storage of Tinfirm's origin, inside Outlook. A script that runs on that origin could read it; such a script could already use a person's session in the web app, and the strict CSP stays on every other page. The token is the person's, at one company, for at most 30 days, rotates on every use and is revocable. The threat model records it.
- Office.js comes from Microsoft's CDN on the add-in's pages, as Microsoft requires of add-ins.
- The default `frame-ancestors` covers Outlook on the web for work and personal accounts and the new Outlook for Windows. A national cloud needs its hosts in `TINFIRM_OUTLOOK_FRAME_ANCESTORS`; classic Outlook on Windows does not frame the pane.
- Not in this step: the email's attachments (the endpoint uploads no file), a unified manifest packaged with the Teams app, single sign-on with the Microsoft account (nested app authentication) for companies whose identity provider is Entra ID, and email as an event source of triggers.

## Alternatives considered

- **A COM add-in.** It could call the MCP endpoint from .NET with a personal access token and no change to Tinfirm, but it runs in classic Outlook on Windows only and would be built again for the new Outlook. Rejected.
- **An add-in backend of its own** that keeps the tokens and calls the endpoint. Another service to deploy, run and secure in every installation, for what the same origin gives. Rejected.
- **REST operations with a bearer token for the add-in.** They would duplicate what the endpoint's tools do through the same services, and widen the bearer chain to the REST API, which ADR-0045 keeps session-only. Rejected; the tools' `structuredContent` is the REST DTO already.
- **The session cookie in the task pane.** It works in classic Outlook, where the pane is the top document, but not in a frame inside Outlook's page, where the cookie is a third-party one. Rejected.
- **A Client ID Metadata Document for the add-in.** Tinfirm would fetch its own URL through the outbound guard, which refuses a loopback or private address, so development and installations on a private network would fail. Rejected for a built-in client.
- **A separate Angular application for the task pane.** A second build and a change of the image for pages that use the same design system and API types. Rejected.
