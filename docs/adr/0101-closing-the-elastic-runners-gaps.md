# ADR-0101: The gaps that elastic runners left open are closed: one image for every runtime, streamed bundles, the VM image's version, runs that a restarted host takes back, and the runner host as a pod of the Helm chart

- Status: Accepted
- Date: 2026-10-27
- Decided by: the owner, 2026-10-27
- Amends: [ADR-0075](0075-companies-and-sign-in-from-the-deployment.md) (a declared company may name its runner host, which the server registers); [ADR-0095](0095-sandbox-bridge.md) (a host restart no longer loses a run on the bridge; the `hello` names the bridge's build and its last frame; `reclaim`); [ADR-0096](0096-a-vm-per-run.md) (the VM image's version is checked; a crash of the host no longer loses its VMs' runs); [ADR-0097](0097-session-bundles.md) (the upload streams; the vault's rewrap covers the bundles' data keys); [ADR-0098](0098-ready-vms.md) (one pool serves every runtime with `--pool-runtime any`); and the acceptance of ADR-0095 to ADR-0099
- Sources: the [Kubernetes runner analysis](../reviews/2026-10-15-kubernetes-runner-analysis.md) §6.3 ("Shapes"), §6.5 and §10; [ADR-0062](0062-runner-host-rebuilds-its-images.md) (the rebuild of stale images); [ADR-0041](0041-pi-and-opencode-runtimes.md) and [ADR-0061](0061-opencode-2.md) (the runtimes); [ADR-0011](0011-envelope-encrypted-vault.md) (the vault and its rewrap); [threat model](../threat-model.md) 6.3, 18.1, R36
- Changes: Compose's `TINFIRM_SESSION_BUNDLES_*` and its `session-bundles` volume; the web app's default runtime of a new agent; the runner image `tinfirm-runner-multi:local` (`images build --runtime multi`) and `run --pool-runtime any`; the server's streamed bundle upload, `vault.StoredDataKeys` and `V070__session_bundle_rewrap.sql`; the bridge's `hello.build`, `hello.txSeq`, `reclaim` and `reclaimed`; `run --vm-image-version`; the runner host's records of its runs (`runs/` in its data directory); decision 8: `TINFIRM_COMPANIES_<KEY>_RUNNER_HOST_NAME` and `_TOKEN` (`company.DeclaredRunnerHosts`, `runner.internal.RunnerHostDeclarations`, `V071__runner_host_declared.sql`), `run --server` and `--token-file`, the image `ghcr.io/flowtivo/tinfirm-runner-host` (the last stage of `deploy/release/runner-musl.Dockerfile`), and the chart's `runner` values with their templates

## Context

ADR-0095 to ADR-0099 built elastic runners and named what they left open:

- Compose did not pass the session bundles' settings to the server, so a Compose install could not turn them on.
- A new agent started on Claude Code whatever models the company has; a company whose gateway serves only OpenAI or open models had to change the runtime by hand on every agent.
- The pool of ready VMs serves one runtime (ADR-0098): its VMs start their container before any run names one, from the image of `--pool-runtime`. A run of another runtime starts cold.
- The server held a bundle's upload whole in its memory to scan it (ADR-0097), about 256 MiB in the worst case, and the vault's rewrap left the bundles' data keys under the old master key.
- A VM's image holds its own copy of the runner host, which runs its bridge and built its runner images. Nothing checked that copy against the host's, as ADR-0062 checks a container's image.
- A restart of the host lost its runs (R36): the bridge's session key lived only in the host's memory, and the bridge stopped the agent after 25 s and ended, its container or VM with it. The work in the sandbox was lost with the run.
- A Kubernetes install ran the server and LiteLLM from the chart, but its runner hosts outside it: a machine with Docker that someone registered in the app and logged in by hand. A host whose sandboxes are VMs needs no Docker, so it can run as a pod; but its token came only from a registration in the app, and its settings only from `login`'s `config.json`, which a Secret cannot be (the host refuses a symlinked file there, and a Secret's files are symlinks).

## Decision

**Each gap is closed as below. A restarted host takes back each of its runs on the bridge and ends it with its work and its session saved; the turn is not continued in place.**

1. **Session bundles in Compose.** The server gets `TINFIRM_SESSION_BUNDLES_STORE` (default `none`), `_DIRECTORY`, the S3 settings and `_RETENTION`, and a volume `session-bundles` at `/var/lib/tinfirm/session-bundles`, owned by the server's user, for the `filesystem` store. The [operations guide](../operations/session-bundles.md) §5 shows both stores.
2. **A new agent's default runtime follows the company's model access.** For a new agent, the editor picks:
   - Claude Code when the company's gateway serves a Claude model, whatever else it serves;
   - Codex when it serves OpenAI's models only;
   - pi when it serves others (pi talks to any provider);
   - without a gateway, the runtime of the person's first subscription that is not invalid (a Claude login or Anthropic key: Claude Code; a ChatGPT login or OpenAI key: Codex);
   - Claude Code otherwise.

   The editor says why in one line. A runtime the person picks wins, and nothing changes for an agent that exists.
3. **One image with every runtime.** `tinfirm-runner-multi:local` holds Claude Code, Codex, pi and OpenCode with their adapters, at the versions their own images pin (a test keeps them equal), and their settings. It has no command of its own: the host names the run's adapter in the bridge's `start` (`claude-agent-acp`, `codex-acp`, `tinfirm-pi-acp`, `opencode acp`). `images build --runtime multi` builds it, `images.json` records it, and `run` rebuilds it when it is stale, as any image (ADR-0062). With `run --pool-runtime any` the ready VMs run it, so every run of every runtime can take one; a Docker host runs each runtime's own image as before. The VM image's recipe builds it too.
4. **The bundle's upload streams.** The server reads the upload once: a pass-through counts it against the cap, hashes it, hands it to the vault's scan as it comes, seals it in 1 MiB chunks and writes it to the store (`BundleObjects.Upload`). The object is committed only when the scan found it clean and the hash and size match the host's; otherwise it is never an object. On S3 an upload of more than one part is a multipart upload of 8 MiB parts, aborted when it is not committed; one part goes up as one `PUT`. The scan streams too (`VaultService.scanner`): the company's values are read in its transaction and the scan runs after it, so no transaction waits on the host's upload, and the time the scan waits for the upload is not its own. The sweeper aborts the uploads a stopped server left.
5. **The vault's rewrap covers the bundles' data keys.** A module that stores data keys wrapped by the vault implements `vault.StoredDataKeys`: the key ids other than the active one, and a batch rewrap. The session bundles' rows implement it in the core, so every edition rewraps the bundles that exist. The rewrap refuses to run while any data key is under a master key that is not configured, then rewraps every module's batches with the secrets'. `V070` lets the SYSTEM context update the bundle rows' key columns, and only those.
6. **The VM image's version.** The bridge's `hello` names what built its binary: the runner host's version and a digest of every runner image's definition as this binary would build it (`0.3.0+images.<12 hex>`). Once a VM's bridge is connected, before the probe, the host compares it with its own. `--vm-image-version warn`, the default, warns once for each build it sees; `refuse` deletes the VM, and a run that waited for it fails with `INFRA`. The host cannot rebuild a VM image: its operator rebuilds it with the host's binary after every upgrade.
7. **A restarted host takes its runs back.**
   - *What the host keeps.* While a run's sandbox lives on the bridge, the host keeps a record of it in its data directory (`runs/<runId>.json`, 0600, in a 0700 directory, written whole): the assignment, the sandbox (a container's name, a VM's id, labels and address, or the test executor's process), the bridge's name and session key, the repositories as they were cloned, the agent's session once it is open, and a block of reserved event numbers. The bridge listener keeps its identity (its certificate and key) and its port beside them (`runs/bridge.json`). A record goes when the sandbox stops.
   - *What the sandbox does.* A bridge whose host has been gone for 25 s stops the agent as before, but keeps the sandbox and its files and tries to connect again for 15 minutes (`reclaim_wait`) before it ends. A host that does not know the session refuses it, and the bridge ends at once. The `hello` names the last frame the bridge sent (`txSeq`), so that a new process's link starts where the bridge's is, and what the bridge sent to the earlier process is dropped.
   - *What the restarted host does.* Before its first `hello` it reads the records:
     - it registers each run as its own, so `hello.activeRuns` lists it and the server keeps it (the server's rules of reconnects and of `LEASE_EXPIRED` apply as before);
     - it starts the bridge listener with the kept identity on the kept port, the runs' sessions registered before the first connection;
     - it holds each VM at once, so the leftover cleanup leaves it, and dials it again.

     When a bridge is back, `reclaim` stops the agent that the earlier process started (the answer says whether it still ran; its exit follows). Then the run ends as a run that its host stopped does: the work comes back and is pushed, `/output` is saved, the session's bundle is stored, and the run is reported failed with `INFRA`, its message saying what was saved; the server's cancel meanwhile makes it cancelled. The run's events are numbered after the earlier process's.
   - *What is not taken back.* A record of another executor, or of a host that no longer runs the bridge, is logged and removed. A sandbox whose bridge does not come back within 2 minutes is removed, and its run fails with `INFRA`, its work lost.
8. **The runner host as a pod of the Helm chart.** With `runner.enabled`, the chart runs one runner host of one declared company, whose sandboxes are VMs (`--executor vm`; on DigitalOcean a Droplet per run), and the server registers it itself.
   - *The declaration.* A declared company may name a company runner host: `TINFIRM_COMPANIES_<KEY>_RUNNER_HOST_NAME` and `_TOKEN`, the token `tfr_` and 43 base64url characters that the operator makes and keeps in a Secret, which the chart gives the server and the pod. At every start, as the declarations are applied (ADR-0075), the server registers the host when the company has none of that name, with the token's hash and `declared` set, audited `runner_host.registered`; replaces the hash when the token changed, audited `runner_host.updated` with `changed: token`, and closes the connection that the old token opened; and does nothing otherwise. A company host of that name that was registered in the app is never taken over: the start fails, as for a declaration it cannot apply. So does a token of the wrong format, or another host's, and neither is ever in a message. A declared host that the declaration no longer names stays, its token working, and is named in a warning at every start; an owner or admin removes it. Nothing else of the host is declared: admins change its slots and pool and may remove it, which the next start undoes.
   - *The pod's settings.* `run --server <url> --token-file <file>` (`TINFIRM_RUNNER_SERVER`, `TINFIRM_RUNNER_TOKEN_FILE`) stands in for `login`: the URL is checked as `login` checks it (https only), and the token is read from the file once, at the start; it is in no setting of the process, so no child process gets it. Every other setting of `run` already has its variable.
   - *The image.* `ghcr.io/flowtivo/tinfirm-runner-host`, the static binary on Debian slim with git, the CA certificates and `kill`, user 10001, the data directory `/var/lib/tinfirm-runner`. It holds no runtime, so it is published, signed and released with the server under the same version; the VM image holds the runtimes, as before.
   - *The chart.* One replica, recreated, never two (a second process with the same token would replace the first's connection): a Deployment with the host's settings in a ConfigMap, the token and the DigitalOcean token mounted as files from their Secrets (0440, the pod's group), the driver's configuration file from a ConfigMap, a PersistentVolumeClaim for the data directory (the records of decision 7, the mirrors, the outputs), and a NetworkPolicy without ingress whose egress is DNS, https and the VMs' bridge port. The pod connects to the server's public URL, as any host. On an upgrade its `preStop` drains it: no new runs, and the active ones finish within `runner.terminationGracePeriodSeconds` (an hour by default); after that the pod stops, and the next one takes its runs back (decision 7). The chart refuses a company that `companies` does not declare, a name a company host cannot have, a template its driver's configuration lacks, and a server URL that is not https.

## Consequences

- A Compose install turns session bundles on with two variables.
- A company with only OpenAI or open models gets new agents on Codex or pi without a change by hand.
- One pool of ready VMs serves every runtime with `--pool-runtime any`, at the cost of one more image, with every runtime's packages, in the VM image.
- A bundle's upload holds about a chunk, the scan's window and an S3 part: some 10 MiB, whatever its size; the operations guide's memory figure drops accordingly. A bundle that the scan refuses never reaches the store. The S3 key needs `s3:AbortMultipartUpload` and `s3:ListBucketMultipartUploads` as well.
- A master key rotation retires the old key once the rewrap ran, bundles included.
- A VM image built by another runner host is named in the log, or refused, instead of running images that the host would not build.
- A restart of the host (an upgrade, a crash, the OOM killer, `kill -9`) no longer loses the work of its runs on the bridge: the work is pushed, the session saved, and the next message of the conversation goes on from there (threat model R36, now partly closed). A Docker host's restart of its machine still stops its containers, and with them its runs; a VM host's machine may restart, since its VMs are elsewhere.
- The turn itself does not go on: the agent that ran is stopped, and the run ends `INFRA`. Continuing it in place would need the ACP client's state, the guards', the MCP sessions' and the run's proxies kept across the restart; it is not built.
- Runs without the bridge (Docker, the agent attached) are lost on a restart as before, and so is a run whose sandbox had not yet started its agent.
- The host's data directory now holds, while a run's sandbox lives, the run's assignment with its credentials (the repositories' tokens, a company model credential's key), the bridge session's key, and the bridge listener's private key. They are files of the host's user, 0600 in a 0700 directory, as its token in the config directory is (threat model 5.2).
- A Kubernetes install runs its runner host from the chart: no machine of its own, no registration in the app, no `login`. The pod needs Pro or Enterprise, as VMs do (ADR-0100): without it the server refuses the host, which stops. The pod reaches the server through its public URL; an ingress controller inside the cluster whose pods listen on another port needs a rule for them.
- The server's environment holds the declared host's token, as it holds the other Secrets' values; the database holds only its hash, as for a host registered in the app (threat model 6.21). Rotating it is a new Secret value, then a restart of the server and of the pod.
- The tests: the declaration (registered, applied again, its token replaced and the old connection closed, the refusals) with a fake runner connected by the token; the properties' binding; `run --token-file`; the chart's lint and templates with `ci/runner-values.yaml`; and, of decisions 1 to 7, the bridge's reclaim with the agent still running, with the agent stopped by its bridge, and with a host that does not know the session; the records; the fake VM driver's VMs that outlive their driver; and two end-to-end tests that kill a host process (SIGKILL) mid-run and take the run back with a second host, over the bridge with the local test executor and with a VM.

## Alternatives considered

- **Continuing the turn in place.** The restarted host would attach to the running agent's ACP stream. That needs every state of the run that lives in the host's memory (the ACP client's pending requests, the mapper's, the guards' counters, the MCP sessions, the proxies' routes and tokens) on disk at every frame, and the frames acknowledged only once processed. Not now: the work and the session are what a restart must not lose, and the next message continues the conversation.
- **Asking the operator to drain before every restart.** `drain` exists and loses nothing, but waits for every run to end, and a crash does not drain.
- **A pool per runtime.** ADR-0098 rejected it; one image is the choice ADR-0098 named.
- **Holding the bundle in memory and lowering the cap.** It would bound the memory by refusing larger sessions, the ones a bundle helps most.
- **Pinning the VM image's version by a file in the image.** The binary is what runs the bridge and built the images; its own build says it without another file to keep in step.
- **The server provisions the VMs**, with the provider's API and token, and the hosts on them only run. The VM executor already keeps the provider's token in its driver, away from the runner host, and the server away from both, and one host serves many runs; the pod keeps both.
- **A pod per run, as Kubernetes' own executor.** A pod shares the node's kernel; a VM per run keeps the isolation of ADR-0096. A cluster that runs Kata Containers may come later, as another executor of the same pod.
- **A registration in the app, with the token pasted into a Secret.** It needs an admin's step after every install and a manual rotation, and the chart cannot know whether the host exists; a declaration is applied at every start, as the companies are.
- **`login` in an init container.** It would write the token into `config.json` on the volume: a second copy beside the Secret, which outlives the Secret's rotation until the next start.
