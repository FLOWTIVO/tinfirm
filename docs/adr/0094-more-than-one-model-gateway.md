# ADR-0094: More than one model gateway: managed LiteLLM or Bifrost, or keys a company's gateway team provides

- Status: Accepted (built: phase 0 and the provided keys of phase 1; not built: Bifrost as a managed gateway (phase 2), keys entered many at once, inbox items for a missing key and for a revoke request, a warning for an old key, a filter for missing keys, and a price list for the relay's estimates)

## Context

- Since ADR-0059 every company's model gateway is a LiteLLM that Tinfirm manages through its admin API: a key per principal with its budget and models, created, rotated, blocked, swept and deleted by Tinfirm, and the budget enforced by LiteLLM.
- Companies run other gateways. Kong AI Gateway is often their API platform's; Bifrost is an Apache-2.0 gateway of LiteLLM's shape (virtual keys with budgets, teams, spend logs). Some companies run LiteLLM or Bifrost but will not give another application its admin API.
- The analysis found LiteLLM wired in at four points: the key lifecycle on its admin API, the budget's refusal (429 `budget_exceeded`, which the runner host recognises by LiteLLM's wording), spend from its logs, and the filter of its body fields. The relay's transport, its usage meter, the runner host and the runner protocol are already the providers' formats and nothing else.

## Decision

1. **The gateway always enforces the budget, and every principal has a key of its own at the gateway.** Tinfirm never enforces a budget in its relay and never pays several principals' work with one shared key. A gateway that cannot hold a key per person with its own limit is not supported.
2. **Two modes**, chosen in a company's model settings:
   - **Managed** (LiteLLM, and Bifrost, planned for phase 2): Tinfirm holds the gateway's admin credentials and manages the keys as ADR-0059 and ADR-0065 describe. The bundled gateway is always managed.
   - **Provided** (any gateway that serves the Anthropic or OpenAI format with keys of its own: Kong AI Gateway, LiteLLM, Bifrost, others): the company's gateway team creates a key per principal and the company's key, with their budgets and models, and hands each to Tinfirm. Tinfirm holds no admin credential. It checks each key with the gateway's model list, keeps it in its vault, pays with it, stops paying with it when the principal is suspended or leaves and records that the gateway team should revoke it, shows when it was entered, and recognises the gateway's refusals. Keys, budgets, revocation and rotation at the gateway are the gateway team's.
3. **Keys reach Tinfirm** from an admin in the app, from the company's automation through the API (one key at a time, and many at once, planned), and, where the company allows it, from the member: a company setting, off by default, that OWNER and ADMIN change. A member's own key is theirs to replace or remove; service accounts' keys and the company's key are admins' and the API's. In provided mode a key was created outside Tinfirm, so its principal may have seen it (amending ADR-0059 decision 2 for this mode); Tinfirm still never sends it to a runner host or a sandbox and never shows it once entered, only its last four characters.
4. **One adapter per vendor** in the server's model module: the key lifecycle and the team (managed mode), the models, spend logs and prices where Tinfirm may read them, the company key's chat, the reading of the gateway's refusals (both modes) and its tag headers. LiteLLM is the first adapter; a provided gateway of a vendor Tinfirm does not know gets a generic one; Bifrost's, planned for phase 2, is the second managed one.
5. **A spent budget is Tinfirm's own refusal.** The relay classifies the gateway's answer with the vendor's adapter and answers the sandbox in the request's format with Tinfirm's wording and the reset time when known. Its type stays `budget_exceeded` and its message starts with the words runner hosts already recognise, so the runner host classifies it as a usage limit whatever the gateway, and keeps recognising LiteLLM's own answers, which servers before this decision passed on.
6. **LiteLLM stays the bundled default.** Bifrost may be bundled instead once it has run with the real runtimes against real providers, which the spike did not do (its §3).

## Consequences

- Companies can bring Kong, Bifrost, LiteLLM without an admin key, or another gateway with per-key limits; Tinfirm's budgets, payers, runs and relay keep their rules.
- In provided mode the gateway team keeps keys in step with Tinfirm's principals: a new principal without a key waits (`NO_MODEL_KEY`), and a leaver's key lives at the gateway until the team revokes it. The audit's `model_key.revoke_requested` tells them; inbox items and keys entered many at once, both planned, keep the two in step with less work.
- Spend per run is exact where Tinfirm can read the gateway's logs (a managed LiteLLM) and the relay's own count elsewhere (`RELAY`).
- Every vendor is an admin API, a body filter and wordings that change with its releases: each adapter pins them in its tests.
- Names that said LiteLLM become neutral (columns, properties, secret kinds, texts); the old properties are read for a release or two.

## Alternatives considered

- **A shared key with budgets enforced in Tinfirm's relay** ("pass-through"). Rejected by the owner: the budget would overshoot by the answers in flight, a leaked key would cost the company's budget, the gateway could not cut off one person, and Tinfirm would need its own price list to enforce.
- **Kong as a managed gateway** (consumers, key-auth and cost limits through its Admin API). Not now: its admin API is the platform team's, many installations are declarative and refuse writes, and its limits are sliding windows. Provided mode serves it.
- **Bifrost as the bundled default at once.** Deferred: it is younger, its spike ran against a mock provider, and it needs a price file and admin credentials of its own in the deployment.
