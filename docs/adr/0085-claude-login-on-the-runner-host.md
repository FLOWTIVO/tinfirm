# ADR-0085: A member's Claude subscription signs in to Claude Code itself; the runner host holds no token

- Status: Accepted
- Date: 2026-10-21
- Decided by: the owner, 2026-10-21
- Sources: [ADR-0007](0007-credentials-stay-in-deployment.md) (a subscription credential belongs to one member, on their own host); [ADR-0059](0059-litellm-budgets-and-the-model-proxy.md) (a run paid by a budget never holds a key); [runner/README.md](../../runner/README.md) (Model access); the [threat model](../threat-model.md), 7.4 and R26; Anthropic's [Legal and compliance](https://code.claude.com/docs/en/legal-and-compliance) page for Claude Code, section "Authentication and credential use", and the [Agent SDK overview](https://code.claude.com/docs/en/agent-sdk/overview), read 2026-10-21
- Amends: ADR-0005 (the Claude Code row of its runtime table: a subscription through `setup-token`), ADR-0007 (the Claude Pro/Max line of its credential list), ADR-0016 (the Codex login's pool of one) and ADR-0059 (decision 4: the triggers a subscription served)
- Changes: the protocol's `CredentialKind` (`CLAUDE_LOGIN` replaces `CLAUDE_OAUTH_TOKEN`, `protocol/runner-v*.schema.json`), `V058__claude_login.sql`, the server's and the web app's enum, the runner host (`credential add claude`, `credential add codex --pool`, `credentials.rs`, the run's mount, the redactor's token shapes, the failure class of a refresh race in `limits.rs`), `V059__triggers_pay_with_a_budget.sql`, the trigger's settings check (`SettingsService`), the trigger editor of the web app, `runner/README.md`, the threat model, `operations/triggers.md`

## Context

- A member may pay for their own turns with a Claude Pro or Max subscription on their personal runner host (ADR-0007, ADR-0059). Until now the member ran `claude setup-token`, pasted the printed one-year OAuth token into `tinfirm-runner-host credential add claude`, and the host stored it in its credential store and set it as `CLAUDE_CODE_OAUTH_TOKEN` in the sandbox of each run, with a pool of three sandboxes by default.
- Anthropic's terms moved in 2026. The compliance page for Claude Code says that OAuth sign-in "is designed to support ordinary use of Claude Code and other native Anthropic applications"; that developers building products that interact with Claude, "including those using the Agent SDK, should use API key authentication"; that "developers may not collect, store, or intermediate Claude.ai credentials or session tokens — sign-in to a Claude account must complete through Anthropic's own flow"; and, as the exception, that nothing "prevent[s] an end user from signing in to the unmodified Claude Code binary with their own Claude subscription, including where a platform hosts Claude Code", under the conditions for hosting it: the binary unmodified, no sign-in method removed, each end user with their own credentials, billed to them, nothing resold or intermediated.
- The Claude runtime is `claude-agent-acp`, which runs the unmodified Claude Code binary through the Agent SDK. Anthropic's own documentation calls `claude -p` "the Agent SDK via the CLI" and the SDK "a library that runs the Claude Code binary", so driving the binary another way would change nothing about which rule applies. What the terms turn on is who signs in and who holds the credential.
- The editors that run Claude Code through the same adapter (Zed, through `claude-agent-acp`) let the person sign in with their own subscription, and sit within the terms: the person is present, the work is their own. What Tinfirm had beyond that was a trigger paid by its author's subscription (ADR-0059, decision 4): it fires on a schedule, a webhook or a channel event with nobody signed in, and its conversation serves its audience, a channel, an issue or a team. That is work the platform starts on a personal plan for other people, which the terms' "on behalf of their users" and "ordinary, individual usage" are written against, and the ChatGPT terms say the same of a Codex login.
- Claude Code keeps a login in `.credentials.json` under its configuration directory (`CLAUDE_CONFIG_DIR`, `~/.claude` by default). It opens that file with `O_NOFOLLOW`, so a link is refused; it writes it in place (`O_TRUNC`), never through a temporary file and a rename; and it reads it again whenever the file's inode, size or modification time changed. Several Claude Code processes share one login file this way on every developer's machine.

## Decision

**The member signs in to Claude Code itself, once, into a directory of their runner host. The host mounts Claude Code's credentials file into the sandbox of each run that pays with that login, read-write, and never reads it. It holds no token of the subscription.**

1. **The login.** `tinfirm-runner-host credential add claude --label <l>` runs `claude auth login` with `CLAUDE_CONFIG_DIR` set to the credential's own directory, `<data>/claude-logins/<l>/`: with the `claude` CLI of the machine when there is one, else with the one in the runner image `tinfirm-runner-claude:local`. Without either, it says how to sign in on another machine and place the file. The sign-in is Anthropic's own flow, in a browser, or by a pasted code where the machine has none. The host then checks, from the file's metadata alone, that `.credentials.json` is there, a regular file, private and not empty, and asks Claude Code itself whether it is signed in (`claude auth status`, exit code 0); it reads no byte of the file. The credential's kind is `CLAUDE_LOGIN`; it has no secret of its own. `credential remove` deletes the directory with the login.
2. **The run.** Before the sandbox starts, the host makes the mount point in the session home, `~/.claude/.credentials.json`, a plain, empty, private file, and refuses a link or a directory in its place. Docker mounts the host's file over it, read-write. The rest of `~/.claude` stays the run's own (the skills the host mounts, Claude Code's settings and sessions), so nothing a run writes there reaches another run. No variable carries the login: `CLAUDE_CODE_OAUTH_TOKEN` is gone. Run acceptance checks the file's metadata as `credential add` does, not its size, which is zero for a moment while Claude Code renews the login in place; a login that Claude Code can no longer renew fails the run with `LOGIN_EXPIRED`, as before, and the member signs in again on the host.
3. **The pool.** The runs of a login share the one file. Claude Code renews the login in place and re-reads it when another process changed it, which is how it already serves several terminals of one developer, so the pool keeps its default of three and its ceiling of sixteen. Anthropic's usage limits, not the pool, bound what the subscription does.
4. **Redaction.** The host no longer knows the tokens by value, and no redactor is ever empty: the outgoing-commit scan runs on every host, for the shapes. It matches their shape instead: `sk-ant-oat01-…` (the access token) and `sk-ant-ort01-…` (the refresh token), with a tail of at least 20 token characters, raw and as base64 at every byte alignment in both alphabets (the encoded prefix is a fixed string there, as the redactor already computes it for the values it knows), anywhere in a run's events, logs and outputs, as a credential hit. The server's upload scan matches the same prefixes (ADR-0014).
5. **The Codex login, the same way.** A Codex ChatGPT login keeps its mounted `CODEX_HOME` and takes a pool like every credential, `--pool` 1 to 16, default three, in place of its fixed pool of one. Codex (0.156) writes `auth.json` in place, reads it again before it renews the login and again on a 401 before it signs the request anew, so one renewal by any run serves the others; the single-use refresh token only means that no copy of the login may live elsewhere. The one case left is two runs renewing at the same moment: ChatGPT refuses the second with `refresh_token_reused`, and Codex gives it the kind of a 401 with the words "refresh token was already used". The host classes those words as `SERVER_LIMITED`, before the kind, so the server retries the turn by itself (ADR-0073) and the login stays valid; the next run reads the winner's renewed file. The host knows a race from a stale login by the file: it notes the modification time, the size and a hash of the content of `auth.json` as the run starts (the host reads the Codex login for redaction already) and looks again at the failure, and once more two seconds later when it is unchanged, since the provider may refuse the loser while the winner still handles its answer. Unchanged then, no run of this host renewed the login, so the refresh token was used elsewhere (a copy of the login on another machine) and every run would lose the same way: the run ends `LOGIN_EXPIRED`, the credential is marked invalid, and the member signs in again.
6. **What stays.** A subscription belongs to one member, serves only their own turns, on their own personal host, never through the server (ADR-0007, ADR-0059).
7. **Triggers pay with a budget, unless the company decides otherwise.** By default a trigger's settings take no subscription, whoever its payer is, the author included: `SUBSCRIPTION_NOT_SERVING` at the save, and the editor offers none. A trigger pays with its payer's budget on the company's gateway, as a service account's trigger always did (ADR-0077: a seated author's budget), and a subscription serves the member's own conversations only, which is the one case the terms' carve-out describes: the person who signed in, working for themselves. The company's OWNER or ADMIN may turn that on (`triggerSubscriptions` of `PUT /settings`, `trigger_setting.subscriptions`, in the web app's General settings behind a question that says what the company takes on): then an author may pay for the triggers they pay for themselves with their own subscription, as ADR-0059 decision 4 had it, and the reading of the vendors' terms is the company's, not Tinfirm's; the switch is audited as `company_settings.changed`. Turned off again, a trigger that still names a subscription pauses at its next firing (`NOT_ENTITLED`, "The company lets a trigger pay only with a budget"), for its author to choose a model under the budget. `V059` adds the switch, off for every company, and moves the settings of every trigger to the budget, with the open conversations of triggers and their queued runs; a trigger whose budget's settings then name no model, or one its payer's key does not allow, pauses at its next firing as any budget's trigger does, and its author sets the model.

## Consequences

- The host collects, stores and intermediates no Claude credential: the file is Claude Code's, written by Anthropic's sign-in and renewed by Claude Code. What remains in the terms' words is that Tinfirm is a third-party product that runs Claude Code and offers the member's own subscription as a way to pay; what is at stake is the member's account, not the company's data.
- A login expires on Anthropic's schedule rather than the `setup-token`'s year; Claude Code warns three days ahead and refuses requests after. The member signs in again on the host, not per run.
- The sandbox can read `~/.claude/.credentials.json`, as it could read the variable before (threat model 7.4, R26); the shape redaction covers a token that leaves through the transcript. It can also overwrite it, for every run of the pool, as it can a Codex `auth.json` (R55): the mount is read-write because the runtime must renew the login itself and the host must not touch the tokens, and what a run can break is its own member's subscription on their own host, which the next run reports as expired.
- Hosts that still hold a `setup-token` credential report `CLAUDE_OAUTH_TOKEN`, which the server no longer knows. The server drops such a credential from the hello and tells the host (`UNKNOWN_CREDENTIAL_KIND`), so the host's other credentials and runtimes serve and it is not kept offline until its upgrade; `V058` removes the stored rows. An upgraded host skips the old credential file with a warning rather than refusing to start, and `doctor` names it: its owner runs `credential remove <label>`, then `credential add claude`. The runner host's tests write a fake `.credentials.json` where they stored a fake token.

## Alternatives considered

- **An ACP adapter of Tinfirm's own that drives `claude -p`**, in place of `claude-agent-acp`. Rejected: Anthropic's documentation names `claude -p` the Agent SDK's CLI form; the same binary runs the same way, and the credential model is what the terms turn on.
- **A shared `CLAUDE_CONFIG_DIR`** mounted whole. Rejected: a run could leave settings, hooks or memory there for the next run of the same member (threat model TB9).
- **A link from the home to the mounted file.** Refused by Claude Code itself (`O_NOFOLLOW`).
- **The host reading the tokens for redaction**, as it reads the Codex `auth.json`. Rejected: the shape suffices, raw and in base64, and the host then reads nothing from the login. What the shape cannot catch is a token an agent transformed beyond base64; the server's own scan is the second line (ADR-0014).
- **A pool of one**, as Codex had. Not needed for either: both write the file in place and re-read it before they renew it. A lock on the file across the runs of a pool, to rule out even the simultaneous renewal: rejected, because neither runtime takes one, so the host could only hold the sandbox back around a renewal it cannot see; the retry costs one turn's restart in a case that needs two renewals in the same second.
- **Dropping subscriptions and keeping API keys only.** Not chosen: a member may use a subscription they already hold, within the terms' carve-out for the person who signed in.
- **Keeping a subscription for the triggers whose payer is the author** (ADR-0059, decision 4, as built), for every company. Rejected by the owner as the default: the author pays, but is not there, and the work is for others; the budget costs the author nothing more than their seat already does. Kept as the company's choice, off by default, so that a company that reads the terms otherwise, or has Anthropic's word, takes that on itself.
- **No switch: budget only, everywhere.** Rejected by the owner: the reading of the vendors' terms for unattended work is the company's to make, and Tinfirm's default is the careful one.
