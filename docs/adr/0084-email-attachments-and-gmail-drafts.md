# ADR-0084: An email's attachments go with it from both add-ins, as files a person's client holds for a start; Gmail's answers become draft replies

- Status: Accepted
- Date: 2026-10-20
- Decided by: the owner, 2026-10-20
- Sources: [ADR-0014](0014-task-attachments-and-upload-scan.md) (a conversation's files and their scan); [ADR-0045](0045-mcp-server-for-peoples-clients.md) (the MCP endpoint); [ADR-0074](0074-outlook-add-in.md) and [ADR-0076](0076-outlook-pane-thread-and-roaming-links.md) (the Outlook add-in, its **Use as reply**); [ADR-0077](0077-licence-editions-and-seats.md) (both add-ins are Pro's and Enterprise's); [ADR-0083](0083-gmail-add-on.md) (the Gmail add-on); [CONVENTIONS.md](../CONVENTIONS.md) §7, §10, §14.11, §15.7; Google's Gmail API (`users.messages.attachments.get`, `users.drafts.create`) and Office.js (`getAttachmentContentAsync`, Mailbox 1.8)
- Changes: ADR-0014, where a person's file reaches a conversation that exists: a person's client may hold one for an hour before the conversation it starts. ADR-0045, where the endpoint is JSON-RPC only: it takes a file at `/files`, and `start_conversation` takes `fileIds`. ADR-0074, where the pane sends the email's text: it sends its attachments too. ADR-0083 decisions 5 and 8, where attachments are not sent and the deployment's scopes are three: the add-on sends them, saves drafts, and asks for the compose scope. The `conversation` module (`StagedFiles`, `V057__staged_files.sql`), the `mcp` module (`McpFilesController`, the Gmail add-on), the `system` module (`GmailCalls`), the web app's Outlook pane

## Context

- The Outlook pane (ADR-0074) and the Gmail add-on (ADR-0083) send an agent the open email's headers and text only. Invoices, logs, screenshots and contracts arrive as attachments, and an agent asked to triage or investigate an email often needs them.
- A conversation's files are the person's uploads to a conversation that exists, checked and scanned for credentials (ADR-0014) and given to each turn in `/attachments`. From an email, the conversation does not exist yet: it is started by the request about the email, and its first turn must see the files.
- The Outlook pane is a client of the company's MCP endpoint (ADR-0045): JSON-RPC, where a file of 25 MB would travel as 33 MB of base64 inside a tool's arguments. Outlook gives an add-in an attachment's content from Mailbox 1.8 (`getAttachmentContentAsync`): base64 for a file, the MIME text (`eml`) for an attached email, a URL for a cloud file.
- The Gmail add-on reads the open message with the Gmail API and the event's per-message token; `users.messages.attachments.get` gives an attachment's content under the same scope. Google waits about half a minute for an add-on's answer.
- The Outlook pane's **Use as reply** (ADR-0076) opens Outlook's reply form with an answer. A Gmail add-on cannot open a form by a URL of its own: it saves a draft with the Gmail API (`users.drafts.create`) under `gmail.addons.current.action.compose`, which reaches drafts only while the person acts in the add-on, with the event's tokens.

## Decision

1. **A person's client holds a file for a start.** `StagedFiles.stage` holds a file for the caller, a member who may start conversations in the company (`WORK`): its name taken as an upload's (the last path segment, NFC, no control or formatting characters, at most 255), at most the largest file (`TINFIRM_ATTACHMENT_MAX_FILE_SIZE`), checked and scanned as an upload is (the value of a vault secret or a credential format refused, content that cannot be scanned refused; nobody acknowledges a credential format here). It is held for an hour, for the caller only, in `staged_file` (RLS, the content as `bytea`). A person holds at most a conversation's files and bytes at once (`TINFIRM_ATTACHMENT_MAX_FILES_PER_CONVERSATION`, `TINFIRM_ATTACHMENT_MAX_CONVERSATION_SIZE`). Their expired files go at their next hold, and a sweep of the worker deletes every expired file each minute. A hold is not audited.
2. **The start moves the files into the conversation.** `ConversationCommands.startFromClient` takes the ids of held files: in the starting transaction, after the conversation's row and before its first turn, each moves into the conversation as a file its person added, within the conversation's limits, and is audited as `attachment.uploaded` with `stagedFileId`. A file the person does not hold, or that expired, is `400 VALIDATION_FAILED`; two of one name `409 DUPLICATE_ATTACHMENT_NAME`; more than a conversation's limits `409 TOO_MANY_ATTACHMENTS`. A start replayed by its idempotency key moves nothing; its files expire.
3. **The MCP endpoint takes a file at `/files`.** `POST /api/companies/{companyId}/mcp/files`, one multipart `file`, behind the endpoint's own chain: its bearer token or personal token, its rate limit, the scope `tinfirm:write` (`403 INSUFFICIENT_SCOPE`), and under a licence without the Outlook add-in, its `Origin` is refused (`403 EDITION_REQUIRED`). It answers `201` with the held file's id, name, type, size and expiry. `start_conversation` takes `fileIds`, the ids this endpoint answered in the past hour. Not a tool: a tool's arguments are JSON, and a file is bytes.
4. **The Outlook pane sends the email's attachments.** When the open email has attachments (not the images of its body), the pane offers **Send its attachments too**, checked. A start reads each from Outlook (when Outlook has Mailbox 1.8; else they are left out with why), holds it through `/files`, and names the held ids in `start_conversation`. An attached email goes as its `.eml`; a link to a cloud file is left out. At most 20 files and 25 MB in all; a name another attachment has gets a number before its extension. A refusal of a file leaves it out with why; a refusal of the person (`RATE_LIMITED`, `INSUFFICIENT_SCOPE`, `EDITION_REQUIRED`, a sign-in that ended) stops the start.
5. **The Gmail add-on sends them too.** The start card offers **Send its attachments too**, checked; it cannot say how many, since opening an email reads nothing from Gmail (ADR-0083, decision 5). A start reads the message, then each of its attachments with the event's tokens (`users.messages.attachments.get`; the parts with a `Content-ID` shown in the body are not attachments), and holds them as the person through `StagedFiles`, with the Outlook pane's limits, so that Google gets its answer in time.
6. **The request names the attachments, in the same words from both add-ins.** Among the fenced headers, never cut: `Attachments (files of this conversation): a.pdf; b.png`, then `Attachments left out: c.zip (larger than 25 MB); d.env (it holds a credential)`. The reasons are the add-ins' own: not sent, more than 20 files, more than 25 MB in all, larger than the largest file, it holds a credential, it cannot be scanned for credentials, a link to a cloud file, the mail client did not give it. A request about an email without attachments is as before.
7. **Gmail: Use as reply saves a draft in the thread.** Under each answer of a turn that succeeded, the conversation card offers **Use as reply**, as the Outlook pane does: the turn's summary, without its next steps. The add-on reads the open message's reply headers (`format=metadata`: `Subject`, `From`, `Reply-To`, `To`, `Message-ID`, `References`) and saves a draft in its thread with `users.drafts.create`: to its `Reply-To`, else its sender (to its recipients when the person sent it), `Re:` and its subject, `In-Reply-To` and `References`, the answer as text and as simple HTML (paragraphs, lists, bold, italics, code and web links; never any HTML of the answer's). Header values are on one line and encoded as RFC 2047 words when they are not ASCII. Tinfirm never sends it: the card says it is saved and offers **Open the draft**, a link to it in Gmail, which the deployment allows (`https://mail.google.com/`).
8. **The deployment asks for the compose scope.** `gmail.addons.current.action.compose` joins the deployment's scopes. A Google Workspace administrator replaces an existing deployment with the new file; each person grants the new scope the next time they open the add-on.
9. **A Gmail start sent again is the same request.** The fence's tag of a Gmail start is derived from its idempotency key, which holds the link's id, and the email cannot know: Google's retry, or a double click, answers the conversation it started rather than `IDEMPOTENCY_KEY_REUSED`. The start asks for the click's conversation first (`ConversationCommands.startedWith`, a read of the key that claims nothing), before it reads the email or holds anything: a click sent again reads, scans and holds nothing twice, and the key's hash cannot drift with what a second hold would leave out. When the core still answers a replay (two clicks raced), or refuses the start, the add-on releases the files this click held (`StagedFiles.release`, the person's own only) rather than leaving them on the person's limits for an hour.

## Consequences

- An agent sees the email's files in `/attachments` from its first turn, as a person's uploads, scanned the same way; the request tells it which are there and which are not, and why.
- Files wait in the database for at most an hour before their start, the person's only, deleted when they expire. A client that holds files releases those its start did not take (a replay of an earlier start, a refusal); a start that fails before it is sent, or a client that releases nothing, leaves them to expire. A person holds at most a conversation's limits.
- A Gmail start sent again is answered from its first conversation before anything is read from Gmail or held: no second download, scan or hold, and the hash of the key stays the first request's whatever a second hold would have refused.
- A start with attachments takes longer: the files travel to Tinfirm first. For Gmail, 25 MB in all keeps the answer within Google's time.
- A Gmail add-on deployed before this must be replaced by its administrator, and each person grants the compose scope once; until then **Use as reply** fails and says so.
- A Gmail draft is a real draft in the person's mailbox, saved by Tinfirm with the person's grant while they act; Tinfirm keeps nothing of it but a log line.
- Not in this step: attachments of a follow-up message; an agent's own files as attachments of the draft; the compose window's actions; email as an event source of triggers.

## Alternatives considered

- **Files as a tool's base64 argument.** A third larger, through the JSON-RPC parser and the tool's logs, and a single request of 33 MB. Rejected.
- **Starting the conversation first, then uploading to it.** The first turn would start without the files, or wait for a second call that may never come. Rejected.
- **The Gmail add-on reading the attachments' names when an email opens.** It would read the email whenever a person opens it in Gmail, which ADR-0083 decision 5 rules out. Rejected: a checkbox that says it sends whatever attachments there are.
- **Gmail's compose action that opens the created draft.** Its response for HTTP add-ons cannot be tried outside Google, and a link to the draft does the same for the person. Rejected for now.
- **Sending the reply.** An agent's text goes out under the person's name only after they read it. Rejected.
