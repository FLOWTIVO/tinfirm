# ADR-0079: An MCP server's endpoint changes, and every account and credential on it goes

- Status: Accepted
- Date: 2026-10-20
- Decided by: the owner, 2026-10-20
- Amended: 2026-10-27, after M8 of [the security review of 2026-10-27](../reviews/2026-10-27-security-review.md): the rule extends to the endpoints of the server's Sign-in app (decision 7)
- Sources: [CONVENTIONS.md](../CONVENTIONS.md) §15.2 ("The kind and the base URL never change: a token is sent only where it was connected"); [ADR-0040](0040-mcp-tool-connections.md) (MCP servers as tool systems); [ADR-0071](0071-mcp-servers-without-accounts.md) (servers without accounts); [ADR-0072](0072-system-credentials-lent-to-groups-and-service-accounts.md) (credentials); the [threat model](../threat-model.md), 8.7 and 8.22
- Changes: `PATCH /systems/{systemId}` takes `baseUrl` for an MCP server; the system dialog shows the endpoint on a change of an MCP server and warns before it saves a new one; `system.changed` names `baseUrl` with `previousBaseUrl`, `accountsRemoved` and `appRemoved`; the event `SystemMoved`; the docs of systems and MCP servers. Later: `Systems.lockShared`, `409 SYSTEM_MOVED` and the callback's `system_moved` (a connect that ran across the move, point 2); `SystemCalls` pinned to the caller's snapshot (point 5); every credential an account reveals pinned to the system's endpoint at the reveal (`Accounts.RevealedCredential.endpoint`, `CallCredential.endpoint`), which `SystemTools`, `SystemPolls` and `SystemWrites` hold a tool call, a poll and a write-back to (point 5)

## Context

- A system's base URL never changed, so that a token is only ever sent to the host it was connected to: an admin cannot point a system that holds people's tokens at another host and collect them there.
- An MCP server's address does change: a company's own server moves to another host, port or namespace. Until now the only way was to remove the system and register it again, which loses its catalogue with the confirmed effects, the agents' tools and the triggers that use it, and gives it a new id.
- Every account and credential on a server holds a token that its owner gave for that server. The OAuth app, discovered at the server's address, is the old authorization server's.

## Decision

**An MCP server's endpoint may change. The change removes every account and credential on the server, and its app, so that no token reaches the new address; the system keeps its id, name, handle, catalogue, agents' tools and triggers.**

1. **Who and what.** Whoever manages the system changes it as any other setting: OWNER and ADMIN for a company server, its owner for a personal one. Only an MCP server's base URL changes; another kind's is `400 SYSTEM_KIND_INVALID`, since a tracker's or a code host's accounts and repositories name the site they were made on. The new endpoint is checked as at registration (`400 INVALID_BASE_URL`; never a private address for a personal server). The same endpoint, trailing slashes aside, changes nothing.
2. **What goes.** In the transaction of the change: every account and credential on the server, each audited as `account.disconnected` with the cause `system.moved`, with its grants to groups and its lendings to service accounts; its pending sign-ins; the app with its client secret; the last test. The system is `NEW` again. The grants at the old server are not revoked: the app goes with the old address, as when a system is removed. A connect whose check ran at the old endpoint stores nothing: the transaction that stores an account or a credential after the system's "who am I", a client's token or a sign-in's exchange locks the system's row shared (`Systems.lockShared`, `FOR SHARE`, which waits for the move's `FOR UPDATE` and holds a move back while it runs) and compares the row's base URL with the one the check went to; one that changed is `409 SYSTEM_MOVED` (a sign-in's callback: `system_moved`), with nothing inserted behind the move (`AccountService.again`). A grant's refresh stores nothing either: its account went with the move.
3. **What stays.** The id, the name, the handle, the catalogue with its confirmed effects and switches, the agents' tools and the triggers. A refresh with a new credential compares the tools at the new address with the catalogue, as any refresh does: a changed definition loses its confirmation.
4. **A server without accounts** (ADR-0071) is reached first at its new endpoint, without a credential and outside any transaction, as when it is set to need none: one that does not answer `initialize` and `tools/list` there is `400 CREDENTIAL_REQUIRED`, and nothing changes. A paused server is not called, so it cannot move while it needs no account.
5. **After the change** the server sets its app up at the new address, as a new server does (its client metadata document, a registration, or none). An app is stored only while the server still has the endpoint it was found at: a setup still running when another change moved the server on stores nothing, and one asked for by hand is `409 OAUTH_NOT_AVAILABLE`, so that no token of one server's authorization server reaches another. Nor does a call prepared for the old endpoint reach the new one: every call of `SystemCalls` (a "who am I", a client's token and identity, a code exchange, a refresh, a revocation) reads the system's row again in its own short transaction and sends nothing when the row's kind or base URL is not the caller's snapshot's (`SystemCallsImpl`: the call fails as if the system were gone, "the endpoint changed meanwhile"), so a token pasted, minted or exchanged for one address is never checked at another. A tool call, a poll and a write-back are held to the same endpoint: a credential an account reveals carries the system's kind and base URL as the reveal's transaction read them, before the account's row (`Accounts.RevealedCredential.endpoint`, `CallCredential.endpoint`; a move removes the account in its own transaction, so an account found is one on the endpoint read before it), and `SystemTools` (a tool's call, a change request opened, read or rewritten), `SystemPolls.open` and `SystemWrites` read the system's row again and send nothing when its kind or base URL is not the credential's (`EndpointPin`: `UNKNOWN_TOOL` for a tool call, as for a system that is gone, `INVALID` otherwise, "the endpoint changed meanwhile: nothing was sent to the new one"). So an agent's call that runs across a move never sends the old token to the new address: the row it reads is the new one, the credential's pin the old. A test or a catalogue refresh at an admin's request compares the row it read before the reveal with the credential's pin the same way (`409 SYSTEM_MOVED`), so a credential stored for the new endpoint is not sent to the old one either. A call without a credential (ADR-0071) is pinned to nothing: there is no token to protect.
6. **Audited and announced.** `system.changed` with `changed` `baseUrl`, the new `baseUrl`, the `previousBaseUrl`, `accountsRemoved` and `appRemoved`; the event `SystemMoved`. The web app warns before it saves a new endpoint that the accounts and credentials go.
7. **The app's endpoints follow the same rule** (amended 2026-10-27, M8 of the security review of that day). The authorization, token, revocation and registration endpoints the server's metadata names must share the issuer's origin, except the origins the operator lists for split-hosted providers (`TINFIRM_OAUTH_DISCOVERY_ALLOWEDENDPOINTORIGINS`). A setup of the app that names another token or revocation endpoint while OAuth accounts or credentials are on the server is `409 SYSTEM_APP_ENDPOINTS_CHANGED`, with what it would remove; confirmed (`confirmEndpointsChange`), they go in the storing transaction as decision 2 says (cause `system.app_endpoints_changed`), so that no refresh token reaches an endpoint it was not issued for.

## Consequences

- A company moves its own server without losing its tools, agents and triggers. The people who used it connect their accounts again, and whoever manages it adds a credential, lends it again and refreshes the tools.
- The rule that a token is sent only where it was connected holds: the change itself sends no token, and the next one is given for the new address.
- Conversations bound to an account that went wait for a new one, as when an account is disconnected.
- An admin who points a server at a host they control gets no token from it, only the people who connect to it again. That is the same exposure as a server they register there, and the change is audited with both addresses.

## Alternatives considered

- **Keep the accounts and credentials.** Simplest for the admin, but every stored token would then reach a host its owner never gave it to. Rejected.
- **Only within the same origin** (a new path or port on the same host). Keeps the credentials safely, but does not cover a move to another host, which is what a company needs.
- **No change of the endpoint; remove and register again.** Loses the catalogue's confirmed effects, the agents' tools and the triggers, and gives the system a new id and maybe another handle. Rejected by the owner.
- **Move every kind's base URL.** A tracker's or code host's accounts and repositories belong to one site; moving them is a migration, not a setting. Not now.
