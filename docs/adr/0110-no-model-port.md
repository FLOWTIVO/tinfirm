## Context

- ADR-0069 put a model port (`model-api`, port 4001) beside the bundled LiteLLM: it served LiteLLM's model routes alone, with LiteLLM's own request fields removed from every body, to the company's services with LiteLLM keys of their own, and the server sent its own model requests through it. LiteLLM's own port, with its admin API, stayed the server's.
- The port protects one gateway, the bundled one. A company that uses its own LiteLLM, or a gateway whose keys its team provides (ADR-0094), exposes that gateway as it decides; the port does nothing for it.
- Tinfirm's own traffic does not need it. The server's relay applies the same filter to every model request it relays, whichever gateway: it removes LiteLLM's own request fields, holds the bodies to its limits and refuses a tool the model's provider would run (ADR-0059, decision 2; the threat model, 13.4).
- The port is a security component of its own: an image to build, sign, release and upgrade with LiteLLM, a second copy of the filter to hold to each LiteLLM version, and a network rule to keep, all for callers that are not Tinfirm's.
- A LiteLLM key can be kept off LiteLLM's management routes (`key_type` `llm_api`), as Tinfirm's keys for its principals are ([CONVENTIONS §15.4](../CONVENTIONS.md#154-model-access-and-runner-hosts)). Such a key still serves every route LiteLLM counts as its LLM API, its pass-through routes to the providers' own APIs among them.

## Decision

**The model port goes. The bundled LiteLLM serves Tinfirm's server on its own port, as a company's own LiteLLM does, and the company's other services there too, where the operator admits them, with LiteLLM keys of their own.**

1. **The server uses LiteLLM's own port.** Its admin calls and its model requests (the runs' requests it relays, its own on the company key) go to `TINFIRM_MODEL_GATEWAY_ADMIN_URL`, LiteLLM's port 4000. `TINFIRM_MODEL_GATEWAY_MODEL_URL` (and its old name `TINFIRM_LITELLM_MODEL_URL`) stays an optional override of where the model requests go, by default the admin URL; the chart and Compose no longer set it.
2. **The relay keeps the filter.** Every model request the server relays has LiteLLM's own request fields removed, its body held to the relay's limits, and every tool the provider would run refused, with no setting that lets one through (ADR-0059, decision 2; ADR-0108). The filter (`LiteLlmRequests`), the bounded reading of answers (`BoundedBodies`) and the cap of request bodies in flight (`InflightBytes`) are the server's own code: the sources and tests of `libs/litellm` and `libs/net` move into the server's, in the same packages, and `libs/jira` is the one shared library left.
3. **Only the server reaches LiteLLM's port unless the operator admits more.** In Kubernetes the NetworkPolicy admits the server's pods to port 4000, and beside them the peers of `litellm.from`, empty by default; it replaces `litellm.modelApi.from`. In Compose LiteLLM sits on the network `gateway`, and a service the operator adds to it calls `http://litellm:4000`.
4. **An admitted service holds a LiteLLM key of its own,** which the operator creates through LiteLLM's admin API with `key_type` `llm_api`, so that LiteLLM refuses it on its management routes, and with its budget and models. LiteLLM checks and meters it; its spend is the key's, not a Tinfirm principal's.
5. **An admitted service is trusted with the company's provider keys.** It reaches LiteLLM's admin API too: its key, not the network, keeps it out. That key serves LiteLLM's pass-through routes to the providers' own APIs, with the provider credentials LiteLLM holds for them. LiteLLM's own request fields are not filtered for it, so its requests may set where LiteLLM sends them, with which credentials, under which metadata, or what LiteLLM answers in the provider's place. The operator admits only services trusted with the company's provider keys. Runner hosts never reach LiteLLM (ADR-0059, decision 2).
6. **No port fronts any gateway.** The model port's image `ghcr.io/flowtivo/tinfirm-model-api`, its own setting of the provider's tools (`MODEL_API_PROVIDER_TOOLS`) and its body limits go with it. A bundled Bifrost, once Tinfirm manages one (ADR-0094), serves the server on its own port too.

## Consequences

- One component fewer: no image to build, sign and release, no second copy of the filter to hold to LiteLLM's versions, and no extra hop for Tinfirm's own model traffic.
- Tinfirm's own traffic is filtered as before, in the relay, whichever gateway the company uses.
- Nothing of the providers' tools changes. The model port refused every provider-run tool as the relay does (ADR-0108), and the relay still refuses them for every request Tinfirm sends; a service the operator admits to LiteLLM's port is not filtered, as a consequence below says.
- The bundled LiteLLM and a company's own are reached the same way, by a key at LiteLLM's own port: one way to configure a service, and one to document.
- A service the operator admits gets less from the bundled LiteLLM than the model port gave it: it can call the admin API, which only its key bars, and LiteLLM's pass-through routes; and LiteLLM's own request fields reach LiteLLM as it sent them ([threat model](../threat-model.md), 13.7, R65). An operator who admits none, the default, gives nothing up.
- A service that called the model port moves to LiteLLM's port: in Kubernetes its peers move from `litellm.modelApi.from` to `litellm.from`, in Compose it joins `gateway` and calls `http://litellm:4000` instead of `http://model-api:4001`; its key stays valid. A key made for the model port without `key_type` `llm_api` is not kept off the management routes at LiteLLM's port: the operator replaces it with one that is before the service moves.

## Alternatives considered

- **Keep the model port for the services.** It protects only the bundled gateway, costs an image, a release and a second copy of the filter, and Tinfirm's own traffic does not need it.
- **The server as the services' model proxy.** Rejected for the reasons of ADR-0069: the server would carry and meter traffic that belongs to no principal of its own.
- **An off-the-shelf proxy with a path allow-list** (nginx, Envoy) in front of LiteLLM for the services. It would bar the admin routes, which an `llm_api` key bars already, and the pass-through routes, but not LiteLLM's request fields, which only a reader of the body removes, as the model port did.
- **No services at the bundled LiteLLM.** A company would need a second gateway, with its own provider keys and spend, for every service that calls a model. An operator who wants this admits none.
