# ADR-0108: No provider-run tools; web search through Tinfirm

- Status: Accepted
- Date: 2026-11-06
- Decided by: the owner, 2026-11-06, before the 1.0 release
- Sources: [the security review of 2026-10-27](../reviews/2026-10-27-security-review.md), M1 and D8, and [its fix round](../reviews/2026-10-27-security-review-fixed.md); [ADR-0039](0039-runner-protocol-v2-server-executed-tools.md) (the server executes every tool); [ADR-0040](0040-mcp-tool-connections.md) (MCP tools through the server, with the credential from its vault); [ADR-0059](0059-litellm-budgets-and-the-model-proxy.md) (the model relay); [ADR-0069](0069-company-model-gateway.md) (the model port); [ADR-0071](0071-mcp-servers-without-accounts.md) (MCP servers without accounts); [ADR-0104](0104-tools-as-data-sinks.md) (a tool is a destination of data); the [threat model](../threat-model.md), 7.2, 13.4, 13.7, R13; Anthropic's [web search tool](https://platform.claude.com/docs/en/agents-and-tools/tool-use/web-search-tool) ("Dynamic filtering"); Claude Code's [tools reference](https://code.claude.com/docs/en/tools-reference.md) ("WebSearch tool behavior")

## Context

- The model providers can run tools themselves for a request: search or fetch the web, run code in a container they provision, call an MCP server at any URL (Anthropic's `mcp_servers` and `mcp_toolset`, OpenAI's `mcp` tool and its connectors), search files, generate images; Gemini's built-in tools (`googleSearch`, `codeExecution`, `urlContext`, ...) reach Google through LiteLLM the same way. The security review of 2026-10-27 (M1, D8) found that the relay forwarded them, so that a prompt-injected agent held by the sandbox's egress allowlist could have the provider carry what it writes to any host.
- The fix of that review refused every provider-run tool but one: a company could let the providers' web search through (`providerTools: WEB_SEARCH` on `PUT /model-settings`, V076), and the model port had its own `MODEL_API_PROVIDER_TOOLS`. `mcp_servers` and `container` were removed silently.
- A provider-run tool is outside everything Tinfirm puts around a tool call. The server executes every other tool (ADR-0039, ADR-0040): each call is audited with its conversation, run, agent and principal, follows the agent's tool settings and their approvals, uses a grant the company gave, has the 64 KiB cap on its arguments and the system's trust class shown (ADR-0104). A provider's web search has none of that: no audit of the query, no rate limit, no data-sink class, no approval, and its results reach the model without Tinfirm seeing them.
- New tool versions keep adding provider behaviour. The tool check reads a versioned type by its name before the date, so under `WEB_SEARCH` Anthropic's dynamic-filtering web search (`web_search_20260209` and later) passed as `web_search`; those versions default to `allowed_callers: ["code_execution_20260120"]`, so Anthropic provisions code execution for the request implicitly. An allowance by name is an allowance of whatever the provider ships under that name next.
- A provider's tool is not portable: each provider and each runtime has its own (Anthropic's `web_search_*`, OpenAI's `web_search` and `web_search_preview`, xAI's live search, Gemini's grounding), with its own results, limits and price; an agent's search would change with the model it runs on.
- Enterprise installs may be air-gapped, their models served on premises: there is no provider search to allow, and the agents still need one.
- The runtimes ask for provider-run tools on their own: Codex 0.156.1's web search is on by default (the runner host already turned it off behind a gateway), and Claude Code's built-in WebSearch is Anthropic's server-side `web_search` tool, so in a Tinfirm run every WebSearch call ended in the relay's `400`. Claude Code's WebFetch runs in the runtime, through the sandbox's egress proxy. OpenCode 2.0.29's web search calls its search providers (Exa, Tavily, ...) from the sandbox, and pi 1.0.4 has none; neither asks the provider to run a tool by default.

## Decision

**No model provider runs a tool itself for a Tinfirm run: no provider-run web search, no provider-run MCP, nothing. Every web search and every MCP call goes through Tinfirm. There is no setting that changes this.**

1. **Always refused.** The relay and the model port (`LiteLlmRequests`) refuse `400`, naming the field or the type: a top-level `mcp_servers`, `container`, `web_search_options` or `search_parameters` that is not `null`; an OpenAI Responses `prompt` object (a prompt stored at the provider, which can carry its own tools); a tool whose `type` is not one the runtime runs (`CLIENT_TOOL_TYPES`), wherever the body defines tools, so every web search and web fetch in every version, code execution, `mcp_toolset` and OpenAI's `mcp` to a server or a connector; a tool that names one of Gemini's built-in tools by a field, in either spelling; and a tool whose `allowed_callers` names anything but `direct`, which would let the provider's own code execution call it.
2. **Refused, not removed.** `mcp_servers` and `container` were removed silently before; now they are refused like the rest. None of the pinned runtimes sends them (Claude Code, Codex, OpenCode and pi run MCP themselves, Codex's MCP tools are functions), so a request with one was not built by a runtime, and a removal would only hide why the model never got its tool. A field set to `null` asks for nothing and passes.
3. **The setting is gone.** `providerTools` leaves the API (`ModelProviderTools` with it), the service, the store and the audit's `model_settings.changed`; `V081` drops `model_settings.provider_tools` and its check (V076 stays as it ran). The model port's `MODEL_API_PROVIDER_TOOLS`, Helm's `litellm.modelApi.providerTools` and Compose's `TINFIRM_MODEL_API_PROVIDER_TOOLS` are removed. A client that still sends `providerTools` changes nothing.
4. **The runtimes' own switches are off through a gateway.** The runner host keeps Codex's `web_search = "disabled"`, and gives Claude Code WebSearch as a disallowed tool of its session (`_meta.claudeCode.options.disallowedTools: ["WebSearch"]` on `session/new` and `session/load`, which `claude-agent-acp` passes to the Agent SDK), so that neither asks for what the relay refuses. Claude Code's WebFetch stays. OpenCode and pi need no switch today; a runtime upgrade that adds a provider-run tool shows as the relay's `400` until the host turns it off.
5. **MCP only through Tinfirm.** The one MCP path of a run is the runner host's MCP listener, whose `TOOL` request the server executes against the system with the credential from its vault (ADR-0039, ADR-0040), or with none on a server that needs no account (ADR-0071).
6. **Web search through Tinfirm.** Agents get web search from a search MCP server the company registers as a system, typically one that needs no account (ADR-0071), which the server calls with its audit, grants and the agent's tool settings, and whose results are tool results, untrusted like any other.

## Consequences

- A provider-run tool cannot carry what an agent writes past the egress allowlist, whatever tool version a provider ships; the threat model's 7.2 records the dynamic-filtering gap as closed.
- An agent's web search is audited, follows the agent's tool settings and approvals, counts as data sent to that system (ADR-0104), and is the same whichever model or runtime the agent runs on, an air-gapped install's included.
- A company that used `WEB_SEARCH` loses the providers' web search until it registers a search MCP server. Nothing else changes for a company.
- An operator whose values set `litellm.modelApi.providerTools` must remove it: the chart's schema no longer takes it.
- Models that search the web by themselves, whatever the request says (Perplexity's Sonar models, OpenAI's `*-search-preview`), are not stopped by the filter; leaving them out of the gateway's model list is the operator's choice (docs/operations/litellm.md, section 2).
- A run of Claude Code or Codex with a provider's own key or a subscription, without a gateway, has no relay in front of it; the runner host leaves those runtimes as they are there.

## Later work

- **A built-in, server-executed `web_search` tool**, so that a company need not run a search MCP server: the operator chooses the engine (SearXNG, Brave, Tavily, ...), its key is kept in the vault, each company turns it on or off, each query is audited, rate-limited and classed as a data sink (ADR-0104), and its results reach the agent as untrusted content. Not built in this change.

## Alternatives considered

- **Keep `WEB_SEARCH` as an opt-in**: the providers' search with none of Tinfirm's controls, a name-based allowance that new versions widen (dynamic filtering brought code execution), different per provider and absent on air-gapped installs.
- **Allow only some web search versions**: a list to keep against every provider's releases, with the same missing audit, limits and data-sink class.
- **Keep removing `mcp_servers` and `container` silently**: hides the refusal from whoever built the request, while no runtime sends them.
- **Turn the runtimes' provider-run tools off only at the relay**: every WebSearch of Claude Code would keep failing with `400`, turn after turn; the runtime's own switch keeps the tool out of the model's context.
