# ADR-0081: The release images and chart signed with FLOWTIVO's cosign key pair, with an SBOM attested to each image, verified offline

- Status: Accepted
- Date: 2026-10-21
- Decided by: the owner, 2026-10-21
- Amended by: [ADR-0106](0106-reusable-workflows-and-pinned-actions.md), under which the release workflow that builds and pushes the images it signs and the scan of its gate are `reusable-release.yml` and `reusable-security.yml` in `.github/workflows/`
- Sources: [ADR-0077](0077-licence-editions-and-seats.md), decision 4 (the air-gapped installation of Enterprise) and decision 6 (one production install per key); `.github/workflows/release.yml` and `reusable-release.yml`, which builds and pushes the images; [ADR-0080](0080-helm-chart-published-to-ghcr.md), under which the release publishes the Helm chart to GHCR; the [threat model](../threat-model.md), §6.3 (supply chain)
- Changes: `release.yml`'s jobs `signing-key` and `sign`, in the protected environment `release`; `deploy/release/sign-images.sh`; the public key `docs-site/content/cosign.pub` (SHA-256 of its DER `f3aa395d8207acf829d58ad3a8d64b2d72f34af38d90ffe177fe93e912106e53`), published at <https://docs.tinfirm.com/cosign.pub>; the docs site's page "Verify your images"; the threat model's asset A38, its §6.2 and §6.3; `.github/CODEOWNERS` on the public keys, the licence's verification and the release

## Context

- Customers run FLOWTIVO's images from `ghcr.io/flowtivo`. An Enterprise customer without a route to the internet copies them into a registry of its own network (ADR-0077, decision 4). Neither can tell today that an image is the one FLOWTIVO released, unchanged: a tag can be moved, and a mirror can be tampered with.
- Keyless signing (Sigstore's Fulcio and Rekor) writes the signer's identity, the repository and the workflow, to Rekor, a public log, and verification needs Sigstore's trust root and log, which an air-gapped network cannot reach.
- GitHub's artifact attestations (`actions/attest-build-provenance`, `gh attestation verify`) are verified against GitHub, which an air-gapped network cannot reach.
- A release publishes two images, built and pushed by the release workflow: the server, `ghcr.io/flowtivo/tinfirm-server`, and the model port, `ghcr.io/flowtivo/tinfirm-model-api`. Nothing else a release publishes is an image: the runner images are built by each runner host from its own Dockerfiles, and the docs site's image is published from `main`, not by a release. The release also publishes the Helm chart, `oci://ghcr.io/flowtivo/charts/tinfirm:<version>`, as an OCI artifact beside the images (ADR-0080). There is no air-gapped bundle yet (planned, ADR-0077).

## Decision

**Every image a release publishes, and its Helm chart, is signed by digest with FLOWTIVO's cosign key pair, with an SPDX SBOM of each image's platforms attested to it, and nothing goes to a transparency log. A customer verifies with the public key alone, offline.**

1. **A key pair, not keyless.** The pair is made with `cosign generate-key-pair` (ECDSA P-256, the private key encrypted with a password). The private key and its password are the secrets `COSIGN_PRIVATE_KEY` and `COSIGN_PASSWORD` of the GitHub environment `release` only, which has required reviewers: only a release run that a reviewer approved can sign. The public key is `docs-site/content/cosign.pub`, published with the docs at <https://docs.tinfirm.com/cosign.pub>, and an operator can compare it with a copy obtained out of band.
2. **What is signed.** Each release image by the digest its version tag names, every manifest of an index with it (`cosign sign --recursive`). Today the server and the model port. The release's chart, `ghcr.io/flowtivo/charts/tinfirm:<version>`, by its digest too, without an SBOM: a chart is no image, and its images have their own (`sign-images.sh sign-chart`). A new image or chart in the release joins the lists in `release.yml`'s `sign` job.
3. **No transparency log.** The signatures and attestations are made with an empty signing config: no Rekor, no timestamp authority, no certificate. They sit in the registry beside the image (as OCI referrers, or the tags cosign uses where a registry has no referrers API). A customer verifies with `cosign verify --key cosign.pub --insecure-ignore-tlog=true`. The trust rests on the key alone.
4. **An SBOM of each image.** syft writes an SPDX JSON SBOM of each platform of the image, attested to its digest as a signed in-toto attestation of type `spdxjson` (`cosign attest`). The release keeps the SBOMs as a workflow artifact too.
5. **Fail closed.** Before the release workflow pushes anything, the job `signing-key` checks that both secrets are set, that the key opens with the password and that it is the key of `cosign.pub`: a release that could not sign never publishes its images. After a successful release, the job `sign` signs, attests, and verifies both as a customer does; it never runs after a failed release, whose version tag could still name an image of an earlier attempt. Images left unsigned (a release that failed after its push, or a failed `sign`) fail verification at the customers: a re-run of a failed `sign` signs them, and a release that failed after its push is released again under a new version.
6. **Pinned tools.** cosign is its release binary checked against pinned SHA-256 sums; syft is its binary from anchore's image, pinned by digest (`deploy/release/sign-images.sh`). Customers need cosign 3.1 or later to verify an image saved to disk for an air-gapped network.
7. **Not signed yet.** The images of `main` and of the rolling prerelease, and the charts `0.0.0-sha-<sha>` of `main` (`ci.yml`), are not releases, and stay unsigned for now; signing them, with the same key or one of their own, is follow-up work. The release's downloadable assets (the runner host binaries, the Compose files) keep their `SHA256SUMS`, unsigned.
8. **Rotation.** A new key pair replaces the secrets and `cosign.pub` in the same change; releases from then on are signed with it, and the previous public key stays published for the releases it signed. After a compromise, FLOWTIVO replaces the key at once, signs the supported releases again with the new one, and tells customers to trust only the new key.

## Consequences

- A customer can prove, without a route to the internet, that an image is one FLOWTIVO released and that its SBOM is FLOWTIVO's. An air-gapped customer carries the image with its signatures and attestation into its network (`cosign save`, `cosign load`) and verifies there.
- Nothing about a release reaches a public log.
- There is no public record of what the key signed: a leaked key can sign an image that verifies until the key is replaced, and customers learn of the replacement from FLOWTIVO. The key lives only in the `release` environment, behind its reviewers. The environment gates who can read the secret, not where it runs: `signing-key`, `sign`, `sign-assets` and every job of `reusable-release.yml` but its `caller` check, the image build among them, run on GitHub-hosted `ubuntu-latest`, a fresh VM for each job, or on a runner group of their own that `vars.CI_RELEASE_RUNNER` names and that runs no pull-request job, with BuildKit cache ids apart from pull-request builds (H3 of the security review of 2026-10-27; GitHub-hosted is the default under [ADR-0106](0106-reusable-workflows-and-pinned-actions.md)).
- The release's `SHA256SUMS` is signed with the same key since the security review of 2026-10-27 (M13), which amends decision 7 for the downloadable assets: `release.yml`'s `sign-assets` checks the assets on the Release against it, signs it with `cosign sign-blob` (no transparency log) and publishes `SHA256SUMS.sig` and the bundle `SHA256SUMS.sigstore.json` beside it. Hosts on auto-deploy check the signature with `cosign.pub` before they install anything ([auto-deploy.md, section 1.1](../operations/auto-deploy.md#11-signed-assets)). The rolling prerelease's `SHA256SUMS` is signed with the rolling key, a key pair of its own (`deploy/compose/auto-deploy/cosign-rolling.pub`), held in the environment `rolling` (the secrets `ROLLING_COSIGN_PRIVATE_KEY` and `ROLLING_COSIGN_PASSWORD`) and used on the CI runners, so that the release key never signs on them.
- Each release waits for a reviewer at the jobs in the environment `release`: `signing-key` before the push, `sign` after it, and `sign-assets` once the assets are up; jobs that wait at the same time are approved together. The release's `tag` and `next`, which read the release App's key, run in `release-deploy` (H3 of the security review of 2026-10-27), an environment with the same deployment branches and no reviewers: it keeps a branch's workflow from the keys without a second approval.
- The threat model gains an asset, the image signing key (A38).

## Alternatives considered

- **Keyless signing with Sigstore's public Fulcio and Rekor.** Puts the signer's identity in a public log, and verification needs Sigstore's services or a trust root and log kept up to date inside the customer's network. Rejected.
- **GitHub artifact attestations.** Verified against GitHub, which an air-gapped network cannot reach. Rejected.
- **A key in a cloud KMS** (`cosign sign --key awskms://…`). Keeps the key out of GitHub. Not chosen; cosign takes a KMS key without a change to the format, so it can come later.
- **Notation (Notary v2).** Another tool for customers, with its own trust store, for the same offline check. Not chosen: cosign is what the registries and admission controllers customers use already read.
- **Signing the images of `main` and `rolling` too.** Not release images. Left as follow-up work.
