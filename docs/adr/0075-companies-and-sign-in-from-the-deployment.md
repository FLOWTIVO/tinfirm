## Context

- Tinfirm is self-hosted. Whoever runs an instance configures it with the Helm chart or with Docker Compose, and already writes its sign-in there: the instance's OIDC providers are registrations of the environment (`auth.oidc.providers`, `SPRING_SECURITY_OAUTH2_CLIENT_REGISTRATION_<ID>_*`), with their email trust (ADR-0026).
- ADR-0045 added a second way beside it: a company's OWNER configures the company's own OIDC provider on the settings page, stored in `company_identity_provider` with its client secret in the company's vault. It assumed an instance whose companies are run by other people than its operator. An instance is usually one company's, or a few companies' whose operator configures all of them.
- The two ways overlap and differ. An instance provider creates users without any membership, so an admin adds each person by hand; a company's provider makes them members of its company, with a role, for the email domains it claimed. Only the company's provider could do what a single-company instance needs.
- A company's provider needed the operator anyway: behind the chart's NetworkPolicy the server reaches only the issuers of `auth.oidc.providers`, so the operator added an egress rule for each provider an owner configured in the app.
- It carried machinery for owners the operator does not trust: the outbound guard on discovery, token, JWK set and userinfo requests (threat model 3.14, 3.15), email domains unique across the instance with a public lookup for the login page and a first-claim-wins race that nothing verifies (3.13, Q24), and accounts tied to the company whose provider created them (`provisioned_by_company_id`, 3.10). About 1 500 lines of server code, 1 300 of the web app, two tables and a vault secret per provider.
- Companies themselves are created in the app: the bootstrap creates the first (`TINFIRM_BOOTSTRAP_COMPANY_NAME`), and an instance admin creates others (`POST /api/companies`), becoming their OWNER.

## Decision

**The deployment's configuration declares an instance's companies and how their people sign in. Nothing in the app creates a company or configures an identity provider. Helm values and Docker Compose's environment both express it, as environment variables of the server.**

1. **Declared companies.** `tinfirm.companies.<key>`: `TINFIRM_COMPANIES_<KEY>_NAME` (required), `_OWNER` (an email; unset, `TINFIRM_BOOTSTRAP_ADMIN_EMAIL`) and `_ID` (an existing company's id to adopt). The key is lower-case letters and digits, starting with a letter, at most 40, as a registration id is, so that it survives an environment variable's name. It is stored in `company.key`, unique, and never changes.
2. **Applied at every start.** After the admin's bootstrap, on one replica at a time, as SYSTEM, each declared company in key order: a company with the key is left as it is; else the company `_ID` names gets the key; else the one company without a key that has exactly the declared name gets it; else the company is created, without members. The server does not start on an invalid key, a blank name, an id that names no company or a company with another key, or two keyless companies of the declared name. A company that no declaration names stays, and the start warns about it; nothing is ever deleted. The declared name is used when the company is created or adopted; the app may rename the company later.
3. **The declared owner.** While a declared company has no OWNER, the active user with the declared owner's email becomes its OWNER: at every start if that user is local (an instance admin made the account), and at a sign-in of that user that is local, or goes through a provider of that company and asserts their email in that very login. An OIDC user's email is what a provider asserted, so another company's provider, or a provider of none, never claims a company's ownership. A company with an OWNER is never changed by it, so an owner the company replaced does not come back.
4. **Sign-in is the instance's providers, each bound to a company.** A registration takes three more settings beside its email trust: `_COMPANY` (a declared company's key; unset, the only declared company when there is exactly one), `_ROLE` (`MEMBER` by default, or `ADMIN`; never `OWNER`) and `_EMAIL_DOMAINS` (when set, only these domains get new users; `EMAIL_DOMAIN_NOT_ALLOWED` otherwise). A user the provider creates becomes a member of its company with its role; a known identity only signs in, and no membership is granted again. The server does not start on a provider that names an undeclared company, an invalid role or a malformed domain.
5. **Removed.** Companies' own providers: the settings page and its API, their tables and client secrets (`V052` deletes them), the registrations `company-{companyId}`, the guarded discovery, the email domains unique across the instance with the login page's lookup, `MANAGE_IDENTITY_PROVIDER`, `DOMAIN_CLAIMED`, `PROVIDER_NOT_FOUND` and `identity_provider.*`. `app_user.provisioned_by_company_id`: any user can be added to any company. `POST /api/companies` and the admin's "Create company". `TINFIRM_BOOTSTRAP_COMPANY_NAME`.
6. **The direct link.** `/login?provider=<registrationId>` offers only that provider and the password form, for any registration of the instance: the link the operator hands a company's people when an instance has several.
7. **Deployments.** The Helm chart's `companies` list (`key`, `name`, `owner`, `id`) replaces `bootstrap.companyName`, and each entry of `auth.oidc.providers` takes `company`, `role` and `emailDomains`; the chart refuses to render a bad key, a duplicate key or a provider of an undeclared company. Compose declares one company, `main`, from `TINFIRM_COMPANY_NAME` and `TINFIRM_COMPANY_OWNER` in `.env`; more companies and their providers go in an overlay file beside `compose.oidc.yaml` and `compose.entra.yaml`.

## Consequences

- One place configures sign-in, the one the operator already edits. A single-company instance needs only its provider: the new user joins the only company, with the role the operator chose.
- An instance with several companies is configured the same way, a provider or more per company, each with its direct link. The login page shows one button per provider.
- The server loses the code that guarded an owner's issuer and claims, and the threats that came with it (3.11 to 3.15, Q24). What remains trusts the operator, who names every issuer and decides which company each may fill.
- An instance from before keeps its companies: a declaration adopts each by id or by name, and an undeclared one keeps working. A company's own provider does not survive the upgrade: its operator declares it in the deployment first, with the same issuer, so that its people keep their accounts (`(issuer, subject)` identifies them), and registers the new redirect URI `/login/oauth2/code/<id>` at the provider. The guide says how.
- Changing who may sign in, or adding a company, is a change of the deployment and a restart, not a click. A company's owner asks the operator.
- The bootstrap admin owns every declared company that names no owner, as an instance admin owned the companies they created before. Owners can read their people's personal conversations (ADR-0045's notice), so an instance with several companies names each one's owner.

## Alternatives considered

- **Keep companies' own providers behind an instance setting, off by default.** It keeps the code and its threats for owners the operator does not trust, and the NetworkPolicy still needs the operator.
- **Declare companies, keep creating them in the app too.** Two sources of companies, one of them without a key, and an instance admin who owns what they create. The owner chose the deployment only.
- **Adopt a company from before only by id.** Safe, but each upgrade needs the operator to look up an id; the name matches the bootstrap's company unless the app renamed it, and a doubt stops the start instead of guessing.
- **Apply the declared name at every start.** It would undo a rename in the app, and the name is not what identifies the company; the key is.
- **A configuration file instead of environment variables.** Compose and Helm already pass the server's whole configuration as variables (CONVENTIONS §4); one more mechanism for a list of a few companies is not worth it.
