# ADR-0051: A connection's own OAuth account: Tinfirm signs in to an MCP server for the company

- Status: Superseded by [ADR-0058](0058-authority-from-the-audience.md) on 2026-10-12 (was Accepted (the owner's request of 2026-10-08: MCP servers that take only OAuth, such as Sentry's, usable by agents))
- Date: 2026-10-08
- Sources: [ADR-0040](0040-mcp-tool-connections.md) (MCP connections), [ADR-0049](0049-agent-kinds-groups-and-personal-accounts.md) §5 to §7 (people's accounts, Tinfirm as an OAuth client, the call path), [ADR-0050](0050-connection-types.md) (the types); PLATFORM.md §4.2, §7.2; CONVENTIONS §14.5, §14.13
- Changes: ADR-0049 §6, where Tinfirm obtains OAuth grants for people only; PLATFORM.md §4.2, where an MCP connection's credential is a token or nothing.
- Amended by: [ADR-0052](0052-shared-accounts.md), under which a company grant on a tracker exists, as a shared account that only interactive agents use

## Context

- An `MCP` connection calls the server with the connection's token (a vault secret, sent as `Authorization: Bearer` or in `authHeader`) or without a credential. A company agent's tool calls, the catalogue read ("Read tools") and the test all use that token (ADR-0040).
- Since ADR-0049 Tinfirm is an OAuth client: it discovers an MCP server's authorization server (RFC 9728, RFC 8414), identifies itself with its client metadata document, a dynamic registration or a stored client, and obtains grants, but only for **people**: a member signs in on My accounts, and an interactive agent calls with that member's grant. A company agent never calls with a person's account (ADR-0049 §7).
- Hosted MCP servers increasingly take **OAuth only**: Sentry's, for one, issues no static token. Such a server cannot be read into the catalogue with the connection's token, because there is none, so its tools reach no agent, interactive agents included (they need the catalogue to be granted a tool). The connection is unusable.
- The discovery, the client identity, the authorization request, the callback, the token exchange, the refresh with its locks and transactions, the revocation and the audit exist for people's accounts (`PersonOAuth`, `PersonAccountService`). What is missing is a grant that belongs to the connection itself.

## Decision

**An MCP connection may hold the company's own OAuth account: a grant an owner or admin obtains by signing in at the server's authorization server, stored as a company secret. While it is connected it is the connection's credential: the catalogue read, the test and every company agent's tool call run with its access token, refreshed as a person's is.**

**The account.** One per connection, `connection_company_account` (`company_id`, `connection_id` primary key, `account_name` when the server names it, `secret_id` of a company secret holding the grant as a person's does, `{"accessToken","refreshToken","tokenType","expiresAt","scope"}`, `scopes`, `access_expires_at`, `connected_at`, `connected_by_user_id`, `last_used_at`, `last_error`), with RLS as every tenant table, deleted with the connection. Only a connection of type `MCP` takes it (`400 VALIDATION_FAILED` otherwise); a tracker's company credential stays its token (a company grant on Jira, GitHub or GitLab is a later decision, since their write-back and polling would act as the signed-in person).

**Connecting.** `POST /api/companies/{companyId}/connections/{connectionId}/company-account/authorize` (OWNER, ADMIN, `MANAGE_CONNECTIONS`; a browser session) answers the authorization URL, built exactly as a person's (ADR-0049 §6: the connection's client identity, PKCE `S256`, the state bound to the caller's session, the scopes, `resource`), when the connection offers OAuth (`Connection.oauth.available`, the same rule as for people; else `400 VALIDATION_FAILED` naming what is missing, a registration happening first where the server takes one). The authorization request records whom the grant is for, `subject` `PERSON` or `CONNECTION`. The one callback `GET /api/me/accounts/callback` serves both: for a `CONNECTION` request it exchanges the code the same way, reads no account name from a profile (an MCP server has none; `account_name` stays empty unless a later profile gives one), stores the tokens as the company secret `CONNECTION_COMPANY_ACCOUNT`, creates or replaces the account, audits `connection.account.connected` (`connectionId`, `userId` of who signed in, `replaced`), reads the tools with the new grant so the catalogue is filled when the browser returns (a failed read records `toolsReadError` as any read does), and redirects to the connection's page, `/c/{companyId}/connections/{connectionId}?connected=company-account`, or with `?error={code}` (the codes of CONVENTIONS §14.13; a grant that cannot be used audits `connection.account.connect_failed`). The secret is kept as the OAuth client secret of ADR-0049 is (CONVENTIONS §9): a company secret other modules wrote, listed on the Secrets page, deleted with the connection. `DELETE …/connections/{connectionId}/company-account` revokes the grant at the revocation endpoint where there is one, deletes the account and its secret, and audits `connection.account.disconnected` (`revoked`); idempotent.

**The credential.** `ConnectionCredentials.connectionToken` and the company path of `callCredential` resolve, in this order: a connected company account (its access token, refreshed first when it expires within the margin, as `PersonAccounts.refreshIfNeeded` does for a person: one refresh at a time per connection on a replica, a transient failure leaving the current token, a refusal setting `last_error`, audited once per streak as `connection.account.refresh_failed`, and the call then failing as a connection without a credential does), else the connection's secret, else none. An account in `ERROR` is still the connection's credential: the secret is not fallen back to until someone signs in again or disconnects, so a failing grant is seen and not papered over. `CallCredential.Service` says whether its token is an OAuth access token, which every client sends as `Authorization: Bearer`, whatever `authHeader` says. The account's `last_used_at` is marked per call. While the account exists, connected or in error, the connection's secret is not used; the page says so.

**No failure before the sign-in.** A server that takes only OAuth answers a read without a token with 401, which is how the discovery finds its authorization server (RFC 9728), not something an owner should see. When a connection has no credential and the discovery finds an authorization server, the catalogue read is skipped rather than failed: `toolsReadError` stays null, the read is audited as skipped for want of a sign-in, and the test says the server asks for a sign-in. A server that wants a plain token still reports its 401.

**What it is for.** `Connection.companyAccount` (`ConnectionCompanyAccount`: `status` `NOT_CONNECTED`, `CONNECTED` or `ERROR` with `lastError`, `accountName`, `scopes`, `connectedAt`, `connectedByName`, `lastUsedAt`; null on every other type) on the connection, and on the Connections list. People's accounts are untouched: an interactive agent still calls with its person's account, never with the company's (ADR-0049 §7).

**Web.** Connecting an MCP server that offers OAuth and got no token ends the dialog with **Sign in with OAuth** and **Not now**, as connecting a tracker offers its repositories; the sign-in goes to the server at once and the tools are read when the browser returns. An MCP connection's page shows the company account beside the token: not connected (with **Sign in with OAuth** for owners and admins when the connection offers it, else why not, as the people's section says it), connected as whom and since when with **Disconnect**, or an error with **Sign in again**. The page handles the callback's return (`?connected=company-account`, `?error=`). The connect dialog's token hint for an MCP server says that a server which takes only OAuth is signed in to on its page after connecting.

## Consequences

- A server that takes only OAuth, Sentry's among them, becomes usable: an owner connects it without a token, the discovery runs with the create, the dialog offers the sign-in at once (the page does later), and the catalogue is read with the grant when the browser returns; company agents call its tools with it, and interactive agents with their own accounts as before.
- The company's grant is a company secret: revealed per call and audited as `secret.accessed` (`connection-tools:{id}`, `connection-test:{id}`, `run-tool:{runId}`, `decision-tool:{id}`, `connection-account-disconnect:{id}`), never sent to a runner host or a sandbox (tools run on the server, ADR-0040), deleted with the connection. The threat model gains it as an asset beside A15 and A25: whoever reaches the server's database and vault key acts as the signed-in person at the MCP server, within the granted scopes, until the grant is revoked.
- The grant is one person's at the system, acting for the company: the audit names who signed in, and the page shows it. An owner who leaves the company does not take the grant with them (it is the company's secret, not an owned one); disconnecting and signing in again is the rotation.
- One callback, one request table, one refresh path: the person and the company account differ in whose secret holds the grant and where the callback returns to, nothing else. `PersonOAuth` becomes the OAuth client of both subjects.
- Not in this decision: a company grant on a tracker; a token and a company account used together (the account wins while connected).

## Alternatives considered

- **A person's account as the company's credential** (a company agent calling with the owner's own account): refused, since it undoes ADR-0049 §7, where a company agent never acts as a person, and would stop working when that person leaves or disconnects.
- **A token field only, with the owner pasting an access token**: Sentry issues none, and an access token expires within the hour; the refresh needs the grant and the client, which is what this decision stores.
- **Trackers too, now**: the same table would serve, but a company grant on Jira Cloud or GitHub would make the poller and the write-back act as the signed-in person, which the connection's service-account token was chosen to avoid (threat model 8.10); it needs its own review.
