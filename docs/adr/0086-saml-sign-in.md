## Context

- Tinfirm signs people in with a local password or an OIDC provider of the instance. The deployment declares each provider and binds it to a declared company, with the role and the email domains of its new users (ADR-0075).
- Many enterprise identity setups offer SAML 2.0 first, or only: ADFS has no usable OIDC for many of its customers, and an Entra ID or Okta tenant's security team often has a SAML template and a review process for it. ADR-0077 sells SAML and SCIM in Enterprise and promises that SAML sign-in keeps working after the licence ends, so that nobody is locked out of their data.
- SAML is XML signed with XML-DSig, posted through the browser. Its history is a history of verification bugs: signature wrapping (XSW), comment truncation of the NameID (2018, several libraries), XXE in the parser, unsolicited responses replayed into another session. A self-hosted product cannot patch each customer quickly, so the verification must be a library that the security community maintains and that Spring keeps in step.
- The server is Spring Boot 4.1 with Spring Security 7, BFF sessions in PostgreSQL (`TINFIRM_SESSION`, `SameSite=Lax`) and a strict CSP whose `form-action` is `'self'` (CONVENTIONS §5).
- Paid features' server code lives under `ee/`, reached by the core through its own interfaces, and checks `Licensing` (CONVENTIONS §15.24). `Feature.SAML` exists and is kept in `features` after an Enterprise key expires.

## Decision

**A SAML 2.0 identity provider is declared in the deployment like an OIDC provider, bound to one declared company, and signs people in under an Enterprise key. Tinfirm is the service provider through Spring Security's SAML 2.0 service provider on OpenSAML 5. Sign-in starts at Tinfirm; IdP-initiated sign-in and single logout are not supported. Every response is verified by the library and by Tinfirm's checks of replay and binding to the browser.**

1. **Declared in the deployment, beside the OIDC providers.** `tinfirm.auth.saml.providers.<id>` (`TINFIRM_AUTH_SAML_PROVIDERS_<ID>_*`; Helm `auth.saml.providers`; Compose in an overlay file beside `compose.oidc.yaml`):

   | Setting | Meaning | Default |
   |---|---|---|
   | `_METADATA_LOCATION` | The IdP's metadata: an `https://` URL, or a `file:` path to a file the deployment mounts (Helm: the value `metadata`, a string, mounted from a ConfigMap) | required |
   | `_ENTITY_ID` | The IdP's entity ID to take from the metadata, when the document holds several; from 2026-10-27 the pin every later document must name (decision 3) | the only IdP in it, pinned at the first good document |
   | `_COMPANY`, `_ROLE`, `_EMAIL_DOMAINS` | As an OIDC provider's (ADR-0075, ADR-0077): the declared company a new user joins, their role (`MEMBER`, `ADMIN` or `VIEWER`, never `OWNER`), the domains a new user's email must be in | as OIDC |
   | `_SUBJECT` | `NAMEID`, or the name of the attribute that identifies the person (decision 5) | `NAMEID` |
   | `_EMAIL_ATTRIBUTES`, `_NAME_ATTRIBUTES` | The attributes read for the email and the name, in order (decision 5) | decision 5 |
   | `_ROLE_SOURCE`, `_ROLE_CLAIM`, `_ROLE_MAP_ADMIN`, `_ROLE_MAP_MEMBER`, `_ROLE_MAP_VIEWER` | Who decides the role, the attribute that carries it and its values for each role, as for an OIDC provider ([ADR-0088](0088-roles-from-the-identity-provider.md)) | `IDP` when an attribute is named, else `APP` (ADR-0088 decision 6) |
   | `_AUTO_PROVISION` | Whether an unknown person gets a new user (decision 7); `false` when SCIM provisions the company (ADR-0087) | `true` |
   | `_REQUIRE_ENCRYPTED_ASSERTIONS` | Refuse an assertion that is not encrypted (decision 9) | `false` |
   | `_METADATA_REFRESH` | How often a URL's or file's metadata is read again (decision 3) | `PT12H` |
   | `_SCIM_MATCH` | How a sign-in finds a SCIM user (ADR-0087 decision 6) | `EXTERNAL_ID` |

   The registration id is unique across the SAML and the OIDC providers (`^[a-z0-9]+$`), so that the login page's buttons and the direct link `/login?provider=<id>` (ADR-0075 decision 6) serve both kinds. The server does not start on a provider of an undeclared company, an invalid role, a malformed domain, a missing or unreadable metadata location, a metadata location over `http:`, metadata without an IdP, a signing certificate or an HTTP-Redirect `SingleSignOnService`, or an id that an OIDC provider also uses.

   **Why the deployment, and not the admin UI.** The owner decided that sign-in is the deployment's (ADR-0075), and the reasons hold for SAML: the operator already writes the OIDC providers there and decides which issuer may create users of which company; behind the chart's NetworkPolicy the server reaches only the hosts the operator allows, the metadata URL among them; and the guarded fetching of an owner's issuer, the domains unique across the instance and the per-company secrets that ADR-0075 removed would all come back. **The admin UI shows** each company's sign-in read-only (decision 15): what the IdP's admin needs (the SP metadata, the entity ID, the ACS URL), the metadata's state and its certificates. A company's OWNER who wants another IdP asks the operator, as for OIDC.

2. **The service provider Tinfirm publishes.** For each registration:

   | | Value |
   |---|---|
   | Entity ID | `{TINFIRM_PUBLIC_URL}/saml2/service-provider-metadata/{id}` |
   | Metadata | the same URL, public, `application/samlmetadata+xml` |
   | Assertion consumer service (ACS) | `{TINFIRM_PUBLIC_URL}/login/saml2/sso/{id}`, HTTP-POST binding only |
   | Start of a sign-in | `{TINFIRM_PUBLIC_URL}/saml2/authenticate/{id}` |
   | `AuthnRequestsSigned`, `WantAssertionsSigned` | `true`, `true` |
   | NameID formats | `persistent`, then `emailAddress`, then `unspecified` |
   | Keys | the SP's signing and encryption certificates (below), every one in force and the next |
   | Single logout service | none (decision 10) |

   **The SP's keys** are the instance's, in the deployment as the OIDC client secrets are (threat model A8): `TINFIRM_AUTH_SAML_SP_CREDENTIALS_<KID>_KEY` (a PKCS#8 PEM RSA 3072 or EC P-256 private key) and `_CERT` (its X.509 certificate, self-signed is fine), and `TINFIRM_AUTH_SAML_SP_ACTIVE_CREDENTIAL` naming the one that signs. Every credential listed is published in the metadata and is tried to decrypt; only the active one signs. **Rollover:** add the next credential, wait until every IdP read the metadata again (or the IdP's admin uploaded it), make it active, and remove the old one later, as the vault's keys rotate (threat model §6.2). The server does not start with SAML providers and no SP credential, or with an expired active certificate; it warns from 30 days before its end.

3. **The IdP's metadata Tinfirm accepts.** A metadata document (an `EntityDescriptor`, or an `EntitiesDescriptor` with `_ENTITY_ID`), from a URL or a file, never pasted in the app.
   - **Refresh.** Read at the start and every `_METADATA_REFRESH`, sooner when its `cacheDuration` or `validUntil` asks, by a `worker` replica, which stores the result in PostgreSQL (`saml_idp_metadata`: the registration, the whole validated document and its hash, its entity ID, its signing certificates with their end dates, the time it was read, the last error). Every replica builds the registration from the stored document, never from its own fetch, and builds it again when the stored hash changes, so that every replica uses the same keys and the same `SingleSignOnService` location. A URL is fetched with the server's HTTP client, TLS verified, at most 1 MiB, without following a redirect to another host; a file is read again as well, so a replaced ConfigMap needs no restart. A metadata document is parsed as a response is (decision 8): by OpenSAML's hardened parser pool, with no DTD, no external entity, no XInclude, secure processing on and nothing resolved from the network or the file system while parsing.
   - **A failed refresh** keeps the last good metadata and logs a warning, and the company's sign-in page shows the error; metadata whose `validUntil` passed is not used: sign-in through that registration fails with `SAML_LOGIN_FAILED` (reason `metadata_expired`) until a refresh succeeds.
   - **Certificate rollover.** Every `use="signing"` (or unmarked) key of the IdP's `IDPSSODescriptor` is trusted, so an IdP that publishes its next certificate beside the current one rolls over without a sign-in failing: Entra ID, Okta and ADFS all do. A change of the certificates is audited (`saml.idp_keys.changed`, decision 13). Certificates are trusted as keys: their issuer, chain and validity dates are not checked, as the SAML metadata profile says, but the sign-in page shows each one's end date and the server warns from 30 days before the last one ends.
   - **Signed metadata.** When the IdP signs its metadata, the signature is not required: TLS to the operator's chosen URL, or the operator's own file, is the trust. Not required (decided 2026-10-23).
   - **The entity ID is pinned** (amended 2026-10-27, H4 of the security review of that day). `_ENTITY_ID` no longer only picks an IdP out of a document with several: it is the pin, and without it the entity ID of the provider's first good document is (`saml_idp_metadata.entity_id`). A later document that names another IdP is refused (`entity_id_changed`) and the last good one stays in use; a document that names the IdP of another provider reading other metadata, or an OIDC registration's issuer, is refused (`entity_id_in_use`); the server does not start while configured or stored entity IDs collide that way. The first document of a provider without `_ENTITY_ID` is trusted on first use (threat model 16.9, R62).

4. **SP-initiated sign-in only.** The login page shows a button per SAML provider the person may use, as for OIDC. It goes to `/saml2/authenticate/{id}`, which sends a signed `AuthnRequest` with the **HTTP-Redirect binding** (a `302`, signed in the query string with `SigAlg` and `Signature`), never the HTTP-POST binding, whose self-submitting form the CSP's `form-action 'self'` forbids. The request names the ACS URL and asks for the configured NameID format; it asks neither `ForceAuthn` nor `IsPassive`, and no `RequestedAuthnContext`: how strongly the person signs in (MFA) is the IdP's policy.
   - **The request is saved server-side**, keyed by its ID, single use, for 5 minutes (`saml_authn_request`: the registration, the hash of a browser binding, the time). The browser binding is a random value in a cookie of its own, `TINFIRM_SAML` (`HttpOnly`, `Secure`, `SameSite=None`, `Path=/login/saml2/sso/`, 5 minutes). The IdP's response arrives as a cross-site POST, which carries no `SameSite=Lax` session cookie, so the request cannot be kept in the session; the binding cookie replaces it, and the session cookie stays `Lax`. The ACS is exempt from the CSRF token, as Spring exempts it; the binding cookie and `InResponseTo` (decision 8) bind the response to the browser that asked for it. A browser sends a `SameSite=None` cookie only over https: SAML needs an https `TINFIRM_PUBLIC_URL`, except `localhost` for development, and the server does not start otherwise.
   - **After the ACS** the server creates a new session (the ID rotated, CONVENTIONS §5) and redirects to `/`, or to a saved authorization request of its own, as after an OIDC login (threat model 3.4). `RelayState` is not used for a destination. The session ends at the earlier of `TINFIRM_SESSION_MAX_AGE` and the assertion's `SessionNotOnOrAfter`.

   **IdP-initiated sign-in is off and not offered** in this decision. An unsolicited response has no `InResponseTo`, so nothing ties it to the browser that receives it: an attacker who holds a valid response for their own account can post it from any page and sign a victim in as the attacker (login CSRF), whose conversations the victim then fills; a response captured in transit or from a log is replayable for its whole validity, and the replay cache (decision 8) is the only defence left; and it is a second code path for every check. The app tiles of Entra ID's My Apps, Okta's dashboard and ADFS's sign-on page still work: each guide makes the tile open `/saml2/authenticate/{id}`, which starts an SP-initiated sign-in (Entra ID: the application's "Sign on URL"; Okta: the SAML application's own tile hidden and a bookmark application to the start URL shown to the same people; ADFS: the start URL published as the portal's or intranet's link instead of `idpinitiatedsignon`). A response without `InResponseTo` is refused (`unsolicited`). It is not offered as an option either (decided 2026-10-23).

5. **Who the person is, their email and their name.**
   - **The subject.** A SAML user is identified by `(the IdP's entity ID, subject)`, as an OIDC user by `(issuer, subject)` (CONVENTIONS §5), never by email; a known identity signs in whatever its email attributes say, and the server never links a sign-in to an existing user by email (`EMAIL_IN_USE`, threat model 3.3), except to a SCIM user as ADR-0087 decision 6 says. The subject is the `NameID` of the assertion's `Subject`, unless `_SUBJECT` names an attribute: its single value, then. A `transient` NameID, which changes at each sign-in, is refused (`transient_subject`). An `emailAddress` NameID is accepted but changes with the person's email; each guide sets a stable one: Entra ID the attribute `http://schemas.microsoft.com/identity/claims/objectidentifier`, Okta the NameID `user.getInternalProperty("id")` in `persistent` format, ADFS a `persistent` NameID from `objectGUID`. The subject is at most 255 characters.
   - **The email**, for a new user: the first of `_EMAIL_ATTRIBUTES` that holds a value that looks like an email address, by default `email`, `mail`, `http://schemas.xmlsoap.org/ws/2005/05/identity/claims/emailaddress`, `urn:oid:0.9.2342.19200300.100.1.3`, and last the NameID when its format is `emailAddress`. SAML carries no `email_verified`: a SAML provider is always trusted as an OIDC provider under `TRUST_ISSUER` is (ADR-0026, threat model 3.9), so the guides tell the operator to set `_EMAIL_DOMAINS`. Without an email the sign-in fails with `EMAIL_MISSING`; outside the domains with `EMAIL_DOMAIN_NOT_ALLOWED`, checked before `EMAIL_IN_USE`, as for OIDC.
   - **The name**: the first of `_NAME_ATTRIBUTES` with a value, by default `displayName`, `http://schemas.microsoft.com/identity/claims/displayname`, `urn:oid:2.16.840.1.113730.3.1.241`, `name`; else `givenName` and `surname` (or `http://schemas.xmlsoap.org/ws/2005/05/identity/claims/givenname` and `…/surname`) joined; else the email's local part; at most 100 characters, as for OIDC.
   - An attribute of several values gives its first. Attributes are read only from the verified assertion's `AttributeStatement`, decrypted when encrypted (`EncryptedAttribute` too).

6. **The role: OWNER, ADMIN, MEMBER, VIEWER, as [ADR-0088](0088-roles-from-the-identity-provider.md) decides for every provider** (decided by the owner, 2026-10-22).
   - **OWNER is never given or taken by SAML.** A company's owner comes from its declaration (ADR-0075 decision 3), which a SAML sign-in serves as an OIDC one does: while a declared company has no OWNER, a sign-in through a SAML provider of that company whose assertion gives the declared owner's email, under its domains, makes that user OWNER. An OWNER's role is never changed by an assertion, and an OWNER is never refused for an attribute that maps to no role.
   - **The provider decides (`_ROLE_SOURCE=IDP`, the default when `_ROLE_CLAIM` names an attribute).** At every sign-in the attribute's values give ADMIN, MEMBER or VIEWER through `_ROLE_MAP_*` (for example the Entra ID app role values `Tinfirm.Admin`, `Tinfirm.Member`, `Tinfirm.Viewer`, sent as `http://schemas.microsoft.com/ws/2008/06/identity/claims/role`, or an Okta group sent as `groups`), and the membership takes it, with the seat fallback; the app cannot change it (`409 ROLE_MANAGED`). An attribute that maps to no role refuses the sign-in (`ROLE_NOT_MAPPED`), the membership and its content kept.
   - **The app decides (`_ROLE_SOURCE=APP`).** The mapped role, or else `_ROLE`, is given to a new user once, as ADR-0075 decision 4 does for OIDC; the app changes it after.
   - When SCIM manages the membership, SCIM's role wins and the assertion's is not applied (ADR-0088 decision 8).

7. **New users just in time, with the seat fallback.** With `_AUTO_PROVISION` (the default), an unknown subject whose email is accepted gets a new user (`authSource` `SAML`) and a membership of the provider's company with its role, in one transaction, exactly as an OIDC provider's new user (CONVENTIONS §5): `user.created` with `authSource`, `provider` and the attribute the email came from; `member.added` by `SYSTEM` with `provider`. **Seats:** under a key that counts seats, a role that holds one becomes `VIEWER` when none is free (`ProvisionedMemberships.grant`), `member.added` carries `seatFallback: true` and `providerRole`, and the company's Owners and Admins get the `SEAT_FALLBACK` inbox item (ADR-0077 decision 5, CONVENTIONS §15.24). Signing in never fails for want of a seat. With `_AUTO_PROVISION=false` an unknown subject is refused (`not_provisioned`), unless SCIM created them (ADR-0087 decision 6).

8. **The checks of every response.** Spring Security's `OpenSaml5AuthenticationProvider` verifies, and Tinfirm adds what it lacks. A response passes only if every check passes; the first failure is the audited reason (decision 13).

   | Check | By |
   |---|---|
   | The ACS request body is at most 256 KiB; the `SAMLResponse` is base64 of a `Response` | Tinfirm, before parsing |
   | Parsed by OpenSAML's hardened parser pool: no DTD, no external entity, no XInclude, secure processing on, schema-typed `ID` attributes | the library |
   | `Status` is `Success` | the library |
   | `Issuer` of the response (when present) and of the assertion is the registration's IdP entity ID | the library |
   | **A signature** on the `Response` or on the `Assertion`, verified against the IdP metadata's signing keys only, with OpenSAML's signature profile: one reference, whose URI is the signed element's own `ID`; only the enveloped and exclusive canonicalisation transforms; RSA-SHA256 or stronger, or ECDSA; SHA-1 and MD5 refused (OpenSAML's algorithm exclusions, set explicitly). Unsigned, or signed by another key: refused. When only the `Response` is signed, the assertion used is the one inside that signed element | the library; the algorithm list by Tinfirm |
   | **Exactly one** `Assertion` or `EncryptedAssertion`: a response with several, or with both, is refused (`multiple_assertions`), so that the assertion verified is the assertion read | Tinfirm |
   | `Destination` of the response equals the ACS URL; required when the response is signed | the library; required by Tinfirm |
   | **Audience**: an `AudienceRestriction` holds the SP's entity ID | the library |
   | `SubjectConfirmation` with method `bearer`, whose `Recipient` is the ACS URL, whose `NotOnOrAfter` is in the future and whose `InResponseTo` is the request's | the library |
   | **`InResponseTo`** of the response and the subject confirmation names a saved request of this registration (decision 4), not used, not older than 5 minutes, whose browser binding matches the `TINFIRM_SAML` cookie; the request is deleted once the response has passed every check, so a refused response leaves it for the IdP's own | Tinfirm (the request repository) |
   | **`NotBefore` and `NotOnOrAfter`** of `Conditions`, and the assertion's `IssueInstant` not older than 5 minutes, with a **clock skew** of 60 seconds (Spring's default of 5 minutes is lowered) | the library, skew set by Tinfirm |
   | **One-time use**: the assertion's `ID` is inserted into `saml_assertion_seen (registration, assertion_id)` kept until its `NotOnOrAfter` plus the skew; a conflict is a replay (`replayed`); a `OneTimeUse` condition is honoured by the same table | Tinfirm, in PostgreSQL so that every replica sees it |
   | An `AuthnStatement` is present | the library |
   | The licence holds `SAML` (decision 14) | Tinfirm |

   **Against signature wrapping**, the defence is that the object read is the object verified: OpenSAML unmarshals the document once, verifies the signature of that unmarshalled `Response` or `Assertion` object, checks that its reference points at that object's own `ID` and that the `ID` is unique in the document, and Spring reads the subject and attributes from that same object, never by searching the XML again; Tinfirm adds the one-assertion rule. **Against XML comments in the NameID** (the 2018 truncation), OpenSAML for Java reads an element's whole text, comments removed, never its first text node, and canonicalisation is exclusive without comments; the attack samples in decision 16 prove both. Tinfirm never writes or reads XML signatures by hand: no code of its own parses the response before the library, verifies a digest or a signature, or picks an assertion by XPath.

9. **Signed and encrypted assertions.** Signing is required (decision 8). **Encryption** of the assertion, of its NameID and of its attributes, is accepted when the IdP encrypts with the SP's published encryption key: key transport RSA-OAEP, content AES-GCM or AES-CBC (RSA PKCS#1 v1.5 key transport refused). It is off by default because TLS protects the transport and every IdP needs an extra step for it (Entra ID's token encryption certificate, Okta's "Assertion Encryption", ADFS's relying party encryption certificate); `_REQUIRE_ENCRYPTED_ASSERTIONS=true` refuses a plain one (`not_encrypted`). The guides recommend it: an encrypted assertion keeps the person's attributes away from browser extensions and from logs of the IdP's front end.
10. **No single logout.** Tinfirm publishes no `SingleLogoutService`, sends no `LogoutRequest` and accepts none. Logging out of Tinfirm ends its session only (CONVENTIONS §5); the IdP's session is the IdP's. Front-channel SAML logout chains the browser through every SP in hidden frames or redirects, fails silently where third-party cookies are blocked, needs the session cookie on a cross-site request, and would need a frame exception in the CSP. What logout would protect is better done by removing the person: deactivation at the IdP reaches Tinfirm at once through SCIM (ADR-0087), which ends their sessions; without SCIM an instance admin deactivates the user, and sessions end at the idle timeout (threat model 3.6, R8).
11. **Where the code lives.** The SAML login is under `ee/`, in the identity module's package (`ee/src/main/java/com/flowtivo/tinfirm/identity/internal/saml/`): the relying-party registrations built from the metadata, the request repository, the response checks Tinfirm adds, the replay cache, the metadata refresh and the mapping to a user. The core's `SecurityConfiguration` asks for a port of its own, `identity.internal.SamlLogin` (found when used, `ObjectProvider`), to add `saml2Login` and the metadata endpoint to the web app's chain; without `ee/` there is no SAML. The provisioning of a user and its membership stays the core's: `OidcProvisioning` becomes `ExternalProvisioning`, which both kinds call with a kind, an issuer, a subject, the email, the name and the role, so that the email checks, `EMAIL_IN_USE`, the declared owner and the seat fallback are one code. The dependencies are the server's (`spring-security-saml2-service-provider`, OpenSAML 5, which is published in the Shibboleth Maven repository `https://build.shibboleth.net/maven/releases/`, added to `server/pom.xml` for the `org.opensaml` and `net.shibboleth` groups only); all are Apache-2.0, inside ADR-0082's allow list.
12. **Errors at the login page.** A refused SAML sign-in redirects to `/login?error=<code>` as an OIDC one does: `EMAIL_MISSING`, `EMAIL_DOMAIN_NOT_ALLOWED`, `EMAIL_IN_USE`, `ROLE_NOT_MAPPED` (decision 6, ADR-0088), `EDITION_REQUIRED` (decision 14), and `SAML_LOGIN_FAILED` for every other reason, whose detail is only in the audit and the log, never in the page: telling an attacker which check failed helps them.
13. **Audit.** Every sign-in, succeeded or failed, in the instance chain, with the company's chain as for OIDC (CONVENTIONS §8):

    | Action | When | Details |
    |---|---|---|
    | `auth.login.succeeded` | A SAML sign-in | `method: saml`, `provider`, `companyId` when the provider's company made them its declared owner |
    | `auth.login.failed` | A refused SAML response or start | `method: saml`, `provider`, `reason`: `metadata_expired`, `invalid_response`, `status_not_success`, `issuer_mismatch`, `unsigned`, `signature_invalid`, `weak_algorithm`, `multiple_assertions`, `destination_mismatch`, `audience_mismatch`, `recipient_mismatch`, `unsolicited`, `in_response_to_mismatch`, `browser_mismatch`, `not_yet_valid`, `expired`, `replayed`, `not_encrypted`, `decryption_failed`, `transient_subject`, `email_missing`, `email_domain_not_allowed`, `email_in_use`, `not_provisioned`, `role_not_mapped`, `inactive`, `edition_required`; the user when known. Never the response, an attribute's value or an email |
    | `user.created`, `member.added`, `member.role.changed` | A new user, their membership, a declared owner | as for OIDC, `authSource: SAML`, `seatFallback`, `providerRole`, `declaredOwner` |
    | `saml.idp_keys.changed` | A refresh found other signing certificates | `provider`, the old and new certificates' SHA-256 fingerprints and end dates |
    | `saml.metadata.failed` | A refresh failed, the first time after a success | `provider`, the reason (`unreachable`, `invalid`, `no_idp`, `expired`, `too_large`; from 2026-10-27 `entity_id_in_use`) |
    | `saml.idp_entity_id_changed` | A refresh read a document that names another IdP than the pinned one (amended 2026-10-27, H4); refused, the last good document stays | `provider`, `pinned`, `named`; instance chain |

    Failures are counted per client address by the login throttle (CONVENTIONS §5, per IP), so a flood of forged responses is `429` before it is parsed; a failed response is audited at most once a minute per address and reason, and logged.
14. **The edition, and after the licence ends.** SAML signs people in while the licence holds `SAML`: Enterprise in force, in `EXPIRING` and `GRACE`, and **after an Enterprise key expired** (`EXPIRED` keeps `SAML` in `features`, ADR-0077 decision 7): a company that bought SAML keeps signing in, creating its new users and making its declared owner, with no seat counted then. Under Community never licensed, or Pro, a declared SAML provider does not stop the start (a warning is logged), is left out of `GET /api/auth/providers`, and its start and ACS redirect to `/login?error=EDITION_REQUIRED`, audited `edition_required`. A new Enterprise key restores it at once.
15. **The API and the web app.**
    - `GET /api/auth/providers` gives each provider its `kind` (`OIDC`, `SAML`) and its start URL; the login page shows SAML providers as it shows OIDC ones, and the direct link offers either kind.
    - `GET /api/companies/{companyId}/sign-in` (`getCompanySignIn`, `MANAGE_MEMBERS`: OWNER, ADMIN, an instance admin's ADMIN view) answers the company's providers, OIDC and SAML, each with its id, kind, role, email domains and direct link; a SAML one adds the SP entity ID, the ACS URL, the SP metadata URL, the IdP's entity ID, where its metadata comes from (a URL's host, or "file"), when it was last read, the last error, its `validUntil`, and each IdP and SP certificate's subject, SHA-256 fingerprint and end date; and whether the licence serves SAML now. It also carries the company's SCIM (ADR-0087 decision 11). Nothing in it can be changed.
    - The web app's **Settings → Sign-in** page, which OWNER and ADMIN open, shows it, with a button to download each SP metadata and to copy the URLs, the guide for each IdP, and the SCIM part of ADR-0087.
16. **Testing.**
    - **Conformance against Keycloak in CI.** The server's tests start Keycloak in Testcontainers (as `make up-oidc` runs it; the dasniko Testcontainers module, Apache-2.0), import a realm with a SAML client signed, then signed and encrypted, and drive the whole SP-initiated flow without a browser: the start, Keycloak's login form, the posted response, the ACS, the session. The same realm runs under `make up-saml` in Compose for development.
    - **The checks one by one** (`SamlResponseChecksTest`): responses built with OpenSAML and signed with test keys, each changed in one way: unsigned; signed by a key not in the metadata; SHA-1; a wrong issuer, audience, destination, recipient or `InResponseTo`; another browser's binding cookie; a request already used or older than 5 minutes; an unsolicited response; before `NotBefore` and after `NotOnOrAfter`, at the skew's edge on both sides; a replayed assertion on another replica's session; two assertions; a transient NameID; a plain assertion when encryption is required; RSA 1.5 key transport.
    - **Known attack samples** (`SamlAttackSamplesTest`), fixtures in the repository: the eight signature wrapping variants XSW1 to XSW8 (as SAML Raider generates them) on a response signed by the test IdP; the comment injection of 2018 (`user@example.com<!---->.evil.com` in the NameID and in the email attribute); an XXE, an external DTD and a billion-laughs payload; an XSLT transform in the signature; a duplicate `ID`; a signature over an empty reference. Each must fail with its reason, and a correct response must pass beside it.
    - **The IdPs**: the guides for Entra ID, Okta and ADFS are followed against real tenants before the first release with SAML, and their screenshots and attribute names come from that run; `docs-site/` records the date each was checked.
    - **Licence**: `EditionGatesIntegrationTest` gains SAML refused under Community and Pro, served under Enterprise and after it expired.

## Consequences

- An Enterprise customer whose IdP speaks SAML signs in with it, with the IdP's own MFA and conditional access, and the operator configures it where they configure OIDC.
- The server gains Spring's SAML service provider and OpenSAML 5, a library set of about 10 MB with Santuario and Shibboleth's support libraries, and a second Maven repository for two groups only. A Shibboleth repository outage stops a clean build; the release builds from the dependency cache as for Maven Central.
- Three small tables (the saved requests, the assertions seen, the metadata's state), each swept by the sweep that already removes expired rows.
- The ACS needs a `SameSite=None` cookie and an https public URL; a development instance on plain http signs in with SAML on `localhost` only.
- The user's identity columns now hold a SAML subject as well as an OIDC one (the IdP's entity ID in the issuer's place); `authSource` gains `SAML`.
- Without single logout, a person who signs out of the IdP stays signed in to Tinfirm until their session ends. With SCIM their removal ends it at once; without it, as with OIDC today, an admin deactivates them.
- IdP-initiated sign-in from a portal works only because each guide sets the tile to Tinfirm's start URL; a customer whose IdP cannot do that cannot launch from the portal.
- The threat model gains a boundary, TB16 (the server and a SAML IdP), with its rows, and the asset A39 (the SP's private keys).
- CONVENTIONS changes when it is built: §4 (the `TINFIRM_AUTH_SAML_*` settings), §5 (a SAML bullet beside OIDC: the identity, the email, the checks, the binding cookie, the errors), §6 (the row "Read the company's sign-in" for OWNER, ADMIN and an instance admin; `SAML_LOGIN_FAILED`), §8 (the actions of decision 13), §15.24 (the core interface `identity.internal.SamlLogin` and `ee/`'s implementation in the table of paid features' code, the `SAML` row of the gates, and the tests).
- `docs-site/` gains an operator page (declaring a SAML provider, the SP keys and their rollover) and the admin guides for Entra ID, Okta and ADFS, each with the subject, email, name and role attributes, the start URL for the portal's tile, and encryption.

## Alternatives considered

- **SAML providers configured by a company's OWNER in the admin UI.** It brings back what ADR-0075 removed: a stored metadata or URL per company, a guarded fetch of an address an owner chose, and a NetworkPolicy the operator must open anyway. Not chosen: the owner decided that sign-in is the deployment's.
- **A SAML bridge outside Tinfirm** (Keycloak, Dex or an IdP proxy that speaks SAML to the customer and OIDC to Tinfirm). It needs no SAML code in Tinfirm and works in every edition today, and the guides may mention it. Not chosen as the product's answer: the customer runs and secures one more service in the sign-in path, Enterprise sells SAML itself, and the attribute mapping and the SCIM binding would happen outside Tinfirm.
- **Another SAML library** (`java-saml` of OneLogin, `pac4j`). `java-saml` is DOM-and-XPath based, was among the libraries the 2018 comment attack affected, and is slow to change; `pac4j` wraps OpenSAML too, but outside Spring Security's filter chain, sessions and CSRF. Spring's own service provider fits the server's security chain and is maintained with it.
- **Verifying the XML signature in Tinfirm's code**, with the JDK's XML-DSig. Never: every signature wrapping bug is a gap between what is verified and what is read, and a library that unmarshals once closes it.
- **IdP-initiated sign-in on by default, or as an option now.** Decision 4's reasons; the tiles work SP-initiated. Not offered (decided 2026-10-23).
- **Single logout.** Decision 10's reasons. Spring supports it, so adding it later is configuration and tests, not a rewrite; it is not an open point unless a customer asks.
- **Keeping the saved request in the session, with `SameSite=None` on the session cookie.** It would make every cross-site request to Tinfirm carry the session, which the CSRF token then has to stop alone. The separate binding cookie on the ACS path only is narrower.
- **The HTTP-POST binding for the `AuthnRequest`.** Needed for very large requests, which Tinfirm does not send, and blocked by the CSP's `form-action 'self'`. The redirect binding is what Entra ID expects and Okta and ADFS accept.
- **Identifying a SAML user by email.** Emails change and are reused; the subject is the identity, as for OIDC.
- **The role at the first sign-in only, the app deciding after**, as this ADR first proposed. Replaced by the owner's decision of 2026-10-22, [ADR-0088](0088-roles-from-the-identity-provider.md): the provider decides by default, at every sign-in, for OIDC and SAML alike; `_ROLE_SOURCE=APP` keeps the first behaviour.

## The owner's decisions on the open points

All decided; none is open.

1. **IdP-initiated sign-in**: not offered; portal tiles start an SP-initiated sign-in (2026-10-23).
2. **The role at every sign-in**: the provider decides by default, at every sign-in, for OIDC and SAML alike ([ADR-0088](0088-roles-from-the-identity-provider.md), 2026-10-22).
3. **Encrypted assertions**: accepted, not required (`_REQUIRE_ENCRYPTED_ASSERTIONS=false` by default) (2026-10-23).
4. **Signed IdP metadata**: not required; TLS to the operator's URL or the operator's file is the trust (2026-10-23).
5. **The SP's keys**: in the deployment, rotated by the operator (2026-10-23).
