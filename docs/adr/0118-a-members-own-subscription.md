# ADR-0118: A member's own subscription keeps a VM on a personal host, may pay for the member's own triggers, and a personal host is easier to set up

- Status: Proposed
- Date: 2026-11-21
- Decided by: the owner, 2026-11-21 ("We need to find a way how to support personal use of anthropic and openai subscriptions"), who chose what to make possible and in which form ("The owner's decisions"). Nothing of it is built: this record states the decisions, the providers' texts as they were read that day, and what was not verified. The code follows in pull requests of its own
- Edition: the core, in every edition. Triggers, schedules and webhooks, and personal runner hosts with Docker are in every edition ([ADR-0077](0077-licence-editions-and-seats.md), decision 4), and Kata is a Docker runtime of such a host; nothing of this goes under `ee/`
- Sources: [ADR-0007](0007-credentials-stay-in-deployment.md) (a subscription belongs to one member, on their own host); [ADR-0059](0059-litellm-budgets-and-the-model-proxy.md) and [ADR-0085](0085-claude-login-on-the-runner-host.md) (the member signs in to the provider's own program, the runner host holds no token, and a trigger pays with a budget unless the company decides otherwise); [ADR-0112](0112-no-credential-on-a-sandbox-machine.md) (decisions 5, 6 and 7: the single machine and the login file kept in step are set aside, and Kata's removal waits for its replacements); [ADR-0113](0113-levels-of-isolation-and-placement.md) (a Kata host reports `container`); the providers' pages listed under "The providers' texts", read on 2026-11-21

- Changes, when built: the server's `trigger` and `agent` modules (the check of a trigger's settings in `TriggerEditor` and `SettingsService`, the pause at a firing in `TriggerGateImpl`, `trigger_setting.subscriptions` and `PUT /settings`), the web app (the trigger editor and the company's General settings), `api/openapi.yaml`, a migration, the runner protocol's `welcome` (the host's scope) and the runner host (a Kata runtime on a company host, once Kata is removed there; the commands that install and connect a personal host), the release's assets, `runner/README.md`, the user's and the admin's guides, the threat model (R12, R26, R55 and the rows on a personal host)

## Context

**What exists.** A member may pay for their own turns with their own Claude or ChatGPT plan (ADR-0007, ADR-0059, ADR-0085). They run a personal runner host on their own machine and sign in there with the provider's own program: `credential add claude` runs `claude auth login`, and `credential add codex` runs `codex login`. The login stays a file of that program, and Docker mounts it read-write into the sandboxes of that member's own conversations: Claude Code's `.credentials.json`, and Codex's whole `CODEX_HOME`. The runner host holds no token. The server enforces whose it is: a company host's credentials are refused (`PERSONAL_HOST_CREDENTIAL_ONLY`), a subscription serves only the runs of the member whose host reports it, and a trigger's settings take a subscription only when the company's switch `triggerSubscriptions` is on and the trigger's payer is its author (off by default, ADR-0085 decision 7).

**What stands in the way.** The owner named three things on 2026-11-21.

- *A VM on the member's machine.* A mount reaches a container, and it reaches a Kata VM, since Kata is a Docker runtime (`run --sandbox-runtime` with a name that starts with `kata`) and shares files with its VMs. It cannot reach a Firecracker VM, which shares no file with its host: `--executor vm` binds neither login, and a Codex run there fails. The two answers that ADR-0112 had for a personal host with VMs, the single machine and a login file that the bridge keeps in step, were set aside the same day (ADR-0112, decisions 5 and 6). And ADR-0112 removes Kata once sandbox nodes are ready for production (decision 7). A personal host would then run a subscription in containers only.
- *Triggers and unattended work.* A trigger fires with nobody signed in. ADR-0085 let a subscription pay for one only by the company's switch, because a trigger's work goes to its audience and the providers' terms for a personal plan cover a person's own use.
- *The set-up.* A personal host is a release archive to download and check, Docker Desktop or Docker Engine, and commands in a terminal (`login`, `credential add`, `images build`, `run`). The release has binaries for Linux and for a Mac with Apple silicon. Windows is planned.

**The providers' texts,** read on 2026-11-21. This is what the pages say, not legal advice, and not a reading that either provider has confirmed.

- *Anthropic, a platform that hosts Claude Code* (code.claude.com/docs/en/legal-and-compliance, no date shown): running Claude Code in a product "requires agreeing to our Commercial Terms", "The Claude Code binary must not be modified", a product "may not remove, disable, or restrict any authentication method built into it", and "Each end user must authenticate with their own Anthropic API key, Claude subscription plan credentials, or 3P inference provider credential". The page does not "prevent an end user from signing in to the unmodified Claude Code binary with their own Claude subscription, including where a platform hosts Claude Code".
- *Anthropic, what a developer may not do* (the same page): "Anthropic does not permit third-party developers to offer Claude.ai login into their own applications, or to route requests through Free, Pro, Max, or Ultra plan credentials on behalf of their users. Moreover, developers may not collect, store, or intermediate Claude.ai credentials or session tokens — sign-in to a Claude account must complete through Anthropic's own flow." And: "Customers may not pay for, resell, or intermediate Claude usage on their end users' behalf." The Consumer Terms (anthropic.com/legal/consumer-terms, effective 2025-10-08): "You may not share your Account login information, Anthropic API key, or Account credentials with anyone else. You also may not make your Account available to anyone else."
- *Anthropic, unattended use by the subscriber* (code.claude.com/docs/en/authentication, no date shown): `claude setup-token` makes "a one-year OAuth token" for `CLAUDE_CODE_OAUTH_TOKEN`: "Use this for CI pipelines and scripts where browser login isn't available." A help article (support.claude.com/en/articles/15036540, update of 2026-10-07): "when you're signed in with your Claude plan, the Claude Agent SDK and claude -p still draw from your subscription limits." The Consumer Terms allow access "through automated or non-human means" only with an API key "or where we otherwise explicitly permit it".
- *OpenAI, the account* (openai.com/policies/terms-of-use, effective 2026-01-01): "You may not share your account credentials or make your account available to anyone else and are responsible for all activities that occur under your account."
- *OpenAI, a Codex login on another machine and in automation* (learn.chatgpt.com/docs/auth and /docs/auth/ci-cd-auth, no date shown): "If you can complete the login flow on a machine with a browser, you can copy your cached credentials to the headless machine", with an example that copies into a Docker container, and "Treat `~/.codex/auth.json` like a password". For automation: "The right way to authenticate automation is with an API key. Use this guide only if you specifically need to run the workflow as your Codex account", as "an advanced workflow for enterprise and other trusted private automation", only when "the runner is trusted private infrastructure" and "only one machine or serialized job stream will use a given `auth.json` copy", and: "Do not use this workflow for public or open-source repositories." Codex access tokens, "intended for trusted scripts, schedulers, and private CI runners", are "currently supported for ChatGPT Business and Enterprise workspaces", not for Plus and Pro.
- *OpenAI, apps that let a person use their plan* (the Sign in with ChatGPT Terms, openai.com/policies/sign-in-with-chatgpt-terms, effective 2026-11-04, section 3.1): "Requests must be for the authenticated user and arise from their activity or expressly authorized automations or background processes", "Another user's activity must not trigger requests to the authenticated user's account", "Requests must originate from the user's local runtime or a remote runtime only that user controls", and no "Using one user's subscription to fulfill another user's requests". Tokens kept for longer "must be local and under the user's control, not in a remote or managed environment". These terms bind an application registered with that programme, which Tinfirm is not; they are OpenAI's nearest stated rule for a third party's product.
- *What the texts do not say.* Neither provider speaks of a product that runs the provider's unmodified program on the member's own machine with the login that the member made there, which is Tinfirm's case; of a login file mounted into a container; or of a schedule that the subscriber sets for themselves in such a product. Anthropic names its sales contact for "permitted authentication methods for your use case". As far as the texts go, both providers draw their line between the subscriber's own work and work for other people, and neither draws it between attended and unattended work.

**What the code has.** A trigger has no field for an audience. It has a team or none (`team_group_id`: "sees its conversations, decides their approvals, runs it now; NULL: the author alone"), a payer who is its author or a service identity, accounts that are its author's or a service identity's, and one of four sources. Only a schedule is closed to other people's words (`TriggerSource.openToWriters()` is `this != SCHEDULE`): a tracker's issues and comments, a channel's mentions and a webhook's deliveries are written by others or by systems. A trigger's conversations are always seen by the company's Owners and Admins. The runner host does not know whether it is a personal or a company host: only the server keeps that (`HostScope`), and neither `hello` nor `welcome` carries it. A Kata host reports the level `container`, since its VMM is root on the machine that holds the credentials (`isolation.rs`), and the Kata-only code of the runner host is small: a few dozen lines of `sandbox.rs` and one file of the Ansible role.

**A Mac and Windows.** On a Mac, Docker Desktop puts every container in one Linux VM. Apple's `container` (1.7.1 of 2026-11-06, past its 1.0, for macOS 26 on Apple silicon) "runs a lightweight VM for each container", takes OCI images and binds directories and single files read-write through virtiofs. It is driven by its own command and service, not by the Docker Engine API that the runner host speaks; a third party's adapter offers part of that API over it and calls itself "Intended for local development". Reaching the host from such a container needs a setting made with `sudo` that the documentation calls limited. On Windows, Docker runs Linux containers in one shared VM (WSL 2 or Hyper-V), and Hyper-V's VM per container takes Windows images only. None of this was tried on a machine.

## Decision

**A member's own subscription stays where it is, on the member's own machine, in the provider's own program, with no token in the runner host's hands. Three things change around it: Kata stays on personal hosts, the member's own triggers may use it, and a personal host gets an easier set-up.**

1. **Kata stays on personal hosts.** When Kata is removed from company hosts (ADR-0112, decision 7), a personal host keeps it: `run --sandbox-runtime` with a Kata runtime, on Linux with KVM, with the login a mount as today.
   - That is what gives a member's subscription a VM per run without a new way to carry a login. Nothing new is built for it now, and nothing changes until Kata is removed from company hosts.
   - The level does not change. A Kata host reports `container`, on a personal host too. So an agent that its company holds to a stronger level cannot be paid by a subscription (`NO_HOST_OF_LEVEL`), and that stays so.
   - The single machine and the login file kept in step stay set aside (ADR-0112, decisions 5 and 6). No token is carried into a VM: Claude's one-year token would put a credential into the runner host's store again, which ADR-0085 ended, and the Codex app-server's mode for tokens from a host application is marked in its source "FOR OPENAI INTERNAL USE ONLY - DO NOT USE".
   - *How the two kinds of host are told apart, when Kata is removed from company hosts:* the server knows a host's scope and says it in `welcome`, and a company host that runs a Kata runtime is then refused. It is specified with that removal, not now.
2. **A member's own trigger may pay with the member's subscription.** A trigger's settings take its author's subscription, without a switch of the company's, when all of this holds:
   - the trigger has no team;
   - its payer is its author;
   - its source is a schedule or a webhook;
   - every account it acts with is its author's own;
   - the subscription is one that the author's own personal host reports and that serves the trigger's runtime, as for a conversation today.
   - *A schedule* is fired by its author's own timetable, and nobody else's words reach its agent.
   - *A webhook* is the owner's choice against the narrower rule of schedules alone: it is fired by a system that its author connected, such as the CI of their own repository. Another person's push or comment can be what set that system off, which is the case OpenAI's terms for apps name ("Another user's activity must not trigger requests to the authenticated user's account"), and the delivery's body is text that the author did not write. Both are said where the author chooses the subscription.
   - *A tracker's or a channel's trigger,* and any trigger with a team, serves other people. It pays with a subscription only by the company's wider setting (decision 3).
3. **The company's setting has three values.** `triggerSubscriptions` stops being a switch:
   - `NEVER`: no trigger pays with a subscription;
   - `OWN`, the default: the triggers of decision 2;
   - `AUTHOR_PAID`: every trigger that its author pays, whoever it serves, which is what the switch allows today when it is on, with today's question to the Owner or Admin who chooses it.
   - A company that left the switch off gets `OWN` at the upgrade, and one that turned it on keeps `AUTHOR_PAID`. The change of default is in the changelog and the upgrade notes, since a company's members can then do what they could not before.
   - A trigger whose settings name a subscription that the setting no longer covers pauses at its next firing with today's reason, and the change is audited as today (`company_settings.changed`).
4. **A personal host is easier to set up.** Three parts, planned and not built:
   - *One install command.* A script that belongs to each release and is signed with the release's key. It checks the runner host's binary against the release's signed checksums, checks Docker and git, registers the host as a service of the member's own user that starts with the machine (a systemd user unit on Linux, a LaunchAgent on a Mac), and hands over to the command that connects the host. It installs no Docker and asks for no root: where Docker is missing or cannot be reached, it says what to do and stops. It comes from the release, with a mirror for a company that does not reach GitHub, and never from the company's Tinfirm server (the owner): that server must not be what hands out code that runs on members' machines. The web app shows the command, and beside it the careful way: download, verify, then run.
   - *Connect from the web app.* A page gives a code that works once and for a few minutes. The machine makes its own host token and sends only its hash, so no token crosses the network, and the member confirms the machine that arrives on the page, by its name and a short check that the terminal shows too. The page then guides the sign-in to Claude or ChatGPT, which happens on the member's machine in the provider's own flow, and shows only what the host reports. No login, token or sign-in code passes through Tinfirm's server, and nothing in the web app asks for one.
   - *Updates.* A personal host updates itself by default (the owner): it follows the version of the company's server, checks the release's signature before it replaces itself, never goes back to an older version, waits for its runs to end, and can be turned off. A host on the rolling prerelease is updated by hand.
   - *Windows.* The Linux runner host inside WSL 2, kept running by a task at the member's logon, set up by an install script for Windows (the owner). It needs no new code in the runner host and gives what a Mac has. A native port is decided after one release: a compile check of it found errors in 17 files, and it would come without the sandbox bridge, the confinement of the reader and the front, Kata and the VM executor.
5. **A Mac and Windows get no VM per run now.** A personal host on a Mac or on Windows runs containers in the one VM that Docker keeps there, and reports `container`. Apple's `container` is the candidate for a VM per run on a Mac. It needs a second way for the runner host to drive a sandbox and a Mac to try it on, and nothing is built or promised before that trial.
6. **What is not done.** A member's subscription does not run on a company's runner hosts: the owner did not choose it, and both providers' texts speak against a login kept outside its owner's control. A subscription still serves only its member, and `pi` and OpenCode still take API keys only.

## Consequences

- A member with a plan and no budget can let an agent work on a timetable, or on their own repository's events, on their own machine. That machine has to be on: a trigger whose host is offline waits, as a conversation does.
- A subscription's usage limits are spent with nobody watching. A plan that is used up shows as it does today (`Cooling down`), now also for runs that nobody started by hand.
- The accepted risks of a login in a sandbox (R12, R26, R55) now also hold for runs with nobody at the keyboard. With a webhook, text that the author did not write reaches an agent that can read the login in its sandbox. The threat model says so when decision 2 is built, and the editor says it where the author chooses the subscription.
- Tinfirm takes a reading of the providers' texts for decision 2 that it left to each company before: that a subscriber's own schedule, and a webhook of a system they connected themselves, on their own machine, is the subscriber's own use. A company that reads them otherwise sets `NEVER`.
- Kata's code, its role and its rows of the threat model stay for as long as personal hosts have it. ADR-0112's "one way for Tinfirm to run a VM" then holds for company hosts only.
- OpenAI's page on a Codex login in automation asks for "one machine or serialized job stream" per copy of the login. Tinfirm keeps one file on one machine and makes no copy, and a pool lets several runs share it (ADR-0085, decision 5). Whether triggers on a Codex login should run one at a time is to be decided with the build.

## Alternatives considered

- **Rebuild the single machine for personal hosts,** with Firecracker and the node agent beside the runner host. Not taken: it was set aside the same day for reasons that hold here too, it needs root on the member's machine and Linux with KVM, and it brings the question of how a login reaches a VM, which a VM that mounts does not have.
- **Carry a token into the VM.** For Claude, the one-year token of `claude setup-token`, which Anthropic documents for "CI pipelines and scripts" and which other products pass to their sandboxes. Not taken without Anthropic's word: the runner host would store a credential of the member's plan again, on the wrong side of "collect, store, or intermediate" by the careful reading that ADR-0085 took. For Codex, the app-server's mode for tokens from a host application: marked for OpenAI's internal use only.
- **Schedules only** for decision 2. Recommended to the owner as the narrower rule, since only a schedule is fired by its author alone. The owner included webhooks.
- **Every trigger without a team,** tracker and channel included. Not taken: other people write a tracker's issues and a channel's mentions, which is work for others on one person's plan.
- **Keep the company's switch as it is.** Not taken: a member's own schedule is their own use by every text read, and a company of one had to find a switch to allow itself what the terms' own examples describe.
- **No setting at all for the member's own triggers.** Not taken: the reading of the providers' terms is still a company's to refuse, so `NEVER` stays.
- **A member's subscription on the company's runner hosts,** with a sign-in from the web app. Not chosen by the owner, and against both providers' texts: a login outside its owner's control, on a machine that serves other people.

## To specify and verify during the build

- **The providers' word.** None of the readings above is confirmed by a provider. Anthropic names its sales contact for a use case's permitted authentication. OpenAI's Sign in with ChatGPT programme offers a plan's usage to "all open-source partners and selected private clients", with an interest form for "a paid or remotely hosted app"; it has a documented way to start the Codex app-server with a one-hour access token, which would carry a Codex plan into any sandbox without a mounted file and keep the refresh token out of it, under that programme's terms. Whether Tinfirm asks either provider is the owner's to decide.
- **A webhook's author.** That a webhook without a team is "a system its author connected" rests on who holds its address and secret. To check with the build: who can read them, and what the editor says about the people whose activity can fire it.
- **Runs at once on a Codex login,** as said under Consequences.
- **Apple's `container`.** To try on a Mac before anything is designed: whether the runner host's Docker calls work through the third party's adapter, whether the sandbox reaches the host's proxies, and what a single-file bind exposes of its directory.
- **The set-up, in slices,** each a pull request of its own: the register dialog no longer puts the host's token on a command line (it does today, which the runner host's own `login` warns against); `run` waits for Docker and finds Docker Desktop's socket on Linux; the service's commands; a credential added while `run` runs reaches the server without a restart; the server's enrolment with its code, its audit and its rate limit; the `connect` command; the page; the install script as a signed asset of the release; the signed update; the documents; the install script for Windows.
- **What the set-up cannot test in CI,** and so needs a check by hand at a release: the LaunchAgent, Docker Desktop's mounts and its name for the host, how long WSL 2 stays up, and the signature's check with the `openssl` that a Mac has. Also to verify: that a member can keep a user service running after logout without root, and that the install script can be checked before it runs by whoever wants to.
- **The installer and the updater as controls of the supply chain.** Both run code on members' machines by a signature. The threat model gains them when they are built: whose key signs a release and the rolling prerelease, where it is held, and what a stolen code of the connect page gives (a host that is not the member's, until the member refuses it on the page).

## The owner's decisions

2026-11-21, in the owner's words where quoted:

- "We need to find a way how to support personal use of anthropic and openai subscriptions." Of four cases put to the owner, three were chosen: "In a VM on the member's machine", "For triggers and unattended work", "Easier set-up of a personal host". Not chosen: a member's subscription on the company's runner hosts.
- A VM on the member's machine: "Keep Kata for personal hosts" (decision 1), over rebuilding the single machine.
- Which unattended work: "The member's own triggers" (decision 2), then, made precise against the trigger's fields: "Schedules and webhooks", over schedules only.
- The company's setting: "Yes, three settings" (decision 3).
- The set-up, to plan first: "One install command", "Connect from the web app", "Windows" (decision 4). Then, from the plan: Windows as "Linux host in WSL2 first", over a native port; the install command "From the release on GitHub", over the company's Tinfirm server; updates "On by default".
- Where: "A new ADR here, code later": this record, Proposed, with the code in pull requests of its own.
