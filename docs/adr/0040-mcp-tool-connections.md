# ADR-0040: Remote MCP servers as tool connections, with tools granted per agent

- Status: Accepted
- Date: 2026-10-06
- Sources: the owner's requests of 2026-10-06 (companies implement their own tools for the agents; each agent gets only the tools it is given, so that of a server with five tools one agent may use three, another two and a third all five); PLATFORM.md §3 (principle 5), §4.1, §4.2, §7.2, §14; CONVENTIONS §14.5, §14.6, §14.10; [ADR-0007](0007-credentials-stay-in-deployment.md), [ADR-0039](0039-runner-protocol-v2-server-executed-tools.md)
- Changes: PLATFORM.md §4.2, where remote MCP servers were later work: they are a connection kind. §4.1 and CONVENTIONS §14.6, where tool access was per connection: of an MCP connection it is per tool.
- Amended by: [ADR-0046](0046-agent-tool-permissions.md), under which the agent's entry for a tool is `ALLOW`, `ASK` or `DENY` instead of a list of names, and a denial beats a thread's `ACCESS` grant
- Amended by: [ADR-0049](0049-agent-kinds-groups-and-personal-accounts.md), under which an interactive agent's server-executed tool calls run with the person's own account, not the connection's token
- Amended by: [ADR-0079](0079-an-mcp-servers-endpoint-changes.md), under which a server's endpoint may change, every account and credential on it removed with the old one

## Context

- A company has systems of its own beyond Jira, GitHub and GitLab: a CRM, a wiki, internal documentation, databases, deployments. The restart's server-executed tools read the connections of those three kinds (`{handle}_get`, `{handle}_search`, ADR-0039), and nothing else. A company that wants a specialist to search its CRM has no way to give it that.
- MCP is what tool servers speak, and the restart already routes every tool call through the server: the runner host lists `run.assign.tools` on its MCP listener and forwards each call as a `TOOL` request, which the server checks and executes with the connection's token, so the token never leaves the server (PLATFORM.md principle 5). A remote MCP server fits that path without a change to the runner host or the protocol.
- The owner asked for tools per agent, not servers per agent: the same server, with a different subset for each agent. The restart's tool access is per connection (`READ` or `WRITE`), which fits a tracker's two reads but not a server with twenty tools of which an agent should get three.
- A company's MCP server changes over time: it is redeployed with new tools, or loses some. Grants must survive that, and a tool that disappears must not break an agent or a run.
- What a tool returns is content from outside, as a brief or a comment is (TB9).

## Decision

**A remote MCP server is a connection of kind `MCP`: tools only. The server reads its tools into a catalogue that owners and admins allow or deny per tool, agents are granted its tools by name, and a run calls them through the server-executed tools of ADR-0039, with the connection's token.**

**Connection.** An `MCP` connection has a name, its MCP endpoint as the base URL (https, or http where the operator allows it, through the one outbound client and its guard against private addresses), an optional vault secret with its token, and `authHeader`: the header the token goes in, or `Authorization: Bearer` when none. It has no subjects, no events, no triggers, no accounts, no repositories, and is never polled. The server speaks the part of MCP Streamable HTTP it needs: `initialize`, `notifications/initialized`, `tools/list` page by page, `tools/call`, the session id the server gives, and JSON or server-sent events in the answers; one session per read and per call.

**Catalogue.** On create and on every test (`POST /connections/{id}/test`, the Connections page's "Read tools"), the server reads `tools/list` with the token, revealed with purpose `connection-tools:<id>`, outside any transaction, and brings the catalogue (`connection_tool`) up to date in another: each tool's name, title, description (cut to 4000 characters), input schema, when it was first and last seen, whether it is **present**, and its **policy**, `ALLOW` or `DENY`. A new tool joins allowed; a tool the read did not list becomes absent and keeps its row, its policy and the agents' grants; it is present again when listed again. A name outside `^[A-Za-z0-9_-]{1,59}$`, or one that repeats an earlier name ignoring case, is skipped and counted. A failed read records `toolsReadError` and leaves the catalogue as it was; it never fails the create. `PUT /connections/{id}/tools` sets the policy of the named tools; `DENY` is the company's switch: no agent calls the tool, whatever its grants, which stay. Audited as `connection.tools.read` (the outcome, the names added and removed, never the token) and `connection.tools.changed`.

**Agent access.** An agent's tool access to an `MCP` connection names the tools it may call (`AgentToolAccessInput.tools`, at least one of the catalogue, present or not, with access `READ`; `WRITE` has no meaning there yet). It is replaced as a whole with the rest of the tool access and audited as `agent.access.changed` with the names. Whoever may change the agent grants them: owners and admins for every agent, an operator for its own. A thread's `ACCESS` decision for the connection (`request_access` with the connection's name or handle) grants the thread every served tool of the connection, as it grants a tracker's two reads; an agent that holds some tools of the connection may still request it.

**Run.** `run.assign.tools` lists, per `MCP` connection the agent may use, the tools that are present, allowed and granted (every served tool when the thread was granted the connection), as `{handle}_{name}` with the name in lower case, the server's own input schema, and the description "A tool of the company's MCP server `{connection}`: {the server's description}". The names follow the protocol's rule and never collide with a platform tool; a catalogue name is at most 59 characters so that the whole fits in 100. The prompt's `# Tools` section lists them like the reads. A `TOOL` request names such a tool: the server checks the run, that the tool is served, and that the agent was granted it or the thread the connection (`NO_ACCESS` otherwise; a denied or absent tool is `UNKNOWN_TOOL`), reveals the token with purpose `run-tool:{runId}`, and calls `tools/call` with the agent's arguments as an object of at most 64 KiB (the server validates them against its own schema). The answer is `DONE` with the server's result as it sent it: its text blocks, any other block as a text that names its type, its structured content and its error flag; a JSON-RPC error or a failed call is an error result the agent sees; a result above 800 KiB is `RESULT_TOO_LARGE`; the tool timeout applies. Each call is audited as `tool.called` with the connection, the tool and whether it worked.

**Web.** The Connections page connects an MCP server (endpoint, optional token, token header) and shows its catalogue with a checkbox per tool, "Read tools" and the read's outcome. The agent dialog's Tools section lists an MCP connection's tools as checkboxes, with "All" and "None", marking the denied and the no longer listed ones.

## Consequences

- A company adds tools by running an MCP server and connecting it; nothing in Tinfirm or on the runner hosts is redeployed. Each agent gets the least it needs: the catalogue is what exists, the grant is the agent's subset, the policy is the company's switch.
- The token stays on the server, as every connection token does (A15); the runner host and the sandbox see only the tool names and the results. The agent cannot reach the server itself: it talks to the host's listener, the host to the server, the server to the MCP server.
- What a tool returns is other people's words in the prompt (PLATFORM.md §7.1), as a brief or a comment is; a prompt-injected result steers the agent as a hostile issue would, and the containment is the same (9.1, R15). An MCP server reached by the Tinfirm server is a URL owners and admins choose: the outbound client's guard, the audit of the URL and the egress policy contain it, as for a tracker (8.11, 8.17).
- A tool server sees one token for all agents; a company that wants a credential per agent connects the server once per credential.
- Every call opens a session (`initialize`, `initialized`, `tools/call`): three requests per call. Keeping a session per connection, and the HTTPS side channel for results above 800 KiB, are later work. Writes with side effects behind `APPROVAL` (the `sourceWrite` policy) apply to these tools as to the trackers' when they come; until then an MCP tool that writes is simply a tool the company allowed and granted, which the guide says to think about.
- A tool that disappears from the server disappears from the runs and keeps its grants; a server that is down makes every call an error result. Neither fails a run.
- Runner hosts on protocol v1 get no server-executed tools, these included.

## Alternatives considered

- **Tools executed on the runner host, with the token in `run.assign`.** Rejected by ADR-0039: it spreads the company's tokens to every host, personal ones included, while the server already holds the tokens, the access rules and the audit log.
- **Pass the MCP server to the agent in `mcpServers` with its headers.** The token would be in the sandbox, and the agent would see every tool. Rejected (ADR-0007).
- **Grant the connection, not its tools, as for a tracker.** Rejected: the owner asked for a subset per agent, and a server with `delete_customer` next to `search_customers` needs it.
- **A policy per agent and tool (allow, ask, deny).** The grant is the per-agent allow and the catalogue's `DENY` the company's switch; "ask" is the `APPROVAL` decision that tools with write effect get later, for these tools too.
- **A stdio MCP server inside the sandbox image.** The company would ship its tools into the runner images, and their credentials would be in the sandbox. Rejected.
