# ADR-0046: Granular tool permissions per agent: platform tool policies, and a mode per tool of a connection

- Status: Superseded by [ADR-0058](0058-authority-from-the-audience.md) on 2026-10-12 (was Accepted (packages 1 and 2 built 2026-10-07; package 3, `ASK` and the `label` write, built 2026-10-08))
- Date: 2026-10-07
- Sources: the owner's request of 2026-10-07 (set, per agent, which MCP tools it may use: deny an agent `request_network_access`, deny it a tool that updates an issue); the [solution design](../reviews/2026-10-07-agent-tool-permissions.md); PLATFORM.md §4.1, §4.7, §6, §7.2, §14; CONVENTIONS §14.3, §14.6, §14.10; [ADR-0039](0039-runner-protocol-v2-server-executed-tools.md), [ADR-0040](0040-mcp-tool-connections.md), [ADR-0044](0044-sandbox-egress-proxy.md)
- Changes: ADR-0040, where a thread's `ACCESS` grant gave every served tool of a connection and the per-agent grant was a list of names; PLATFORM.md §4.1, where the policies were only what needs approval and the tool access of a tracker was per connection; §7.2, where every run had every platform tool.

## Context

- A run offers three kinds of tool through the runner host's MCP listener (PLATFORM.md §7.2): the platform tools the host serves itself (`ask`, `finish`, `request_access`, `request_network_access`, `save_artifact`, `list_repositories`), the reads of a tracker connection (`{handle}_get`, `{handle}_search`) and the tools of the company's own MCP servers (ADR-0040).
- Before this decision, every agent had every platform tool: nothing in its settings removed `request_network_access`, and a member could only decline each request as it came. A tracker's tools were granted per connection (`READ` or `WRITE`), not per tool. And for an MCP server's tools, "not granted" was not "denied": a member who approved the agent's `request_access` for the connection gave the thread every served tool, the ungranted ones included.
- The owner asked for the gap to be closed per agent: one strict agent next to a free one, down to one tool.
- ADR-0040 considered "a policy per agent and tool (allow, ask, deny)" and chose the grant plus the company's switch; the owner's request reopens the per-agent part.

## Decision

**Every tool a run can offer has a mode for the agent, from one rule, enforced on the server.**

**The rule** (`RunTools.modeOf`), the first step that applies winning: (1) the company's switch: a tool of an MCP connection whose catalogue policy is `DENY`, or that its server no longer lists, is not served; (2) the agent's own entry for the tool, `ALLOW` or `DENY`; (3) the agent's level on the connection: a tracker's `READ` or `WRITE` allows its reads (its writes, when they come, under `WRITE` and the `sourceWrite` policy); an MCP connection's level grants nothing by itself; (4) the thread's grant: an approved `ACCESS` decision for the connection makes every served tool that is not denied by 1 or 2 `ALLOW` for that thread; (5) the default: a platform tool is `ALLOW`, a connection's tool is not granted. A denial beats a thread's grant.

**Platform tools: four policies.** `AgentPolicies` gains `ask`, `requestAccess`, `requestNetworkAccess` and `saveArtifact`, each `ALLOW` (the default) or `DENY`, next to `changeRequest` and `sourceWrite` (`ALLOW` or `ASK`); `PolicyMode` gains `DENY`, and each policy takes only its own modes (`400 VALIDATION_FAILED` otherwise). `finish` and `list_repositories` have no switch. A denied tool is enforced in two places: `run.assign.platformTools` names the platform tools the agent may use, so the host lists only those (and always `finish` and `list_repositories`), and the server refuses a `run.request` of the tool's kind (`ASK`, `ACCESS`, `NETWORK`, `ARTIFACT`; v1's `run.ask` too) with the code `TOOL_DENIED` and a message that says what to do instead, whatever the host listed. With `ask` denied, the open questions of a `BLOCKED` result stay text in the end-of-turn comment and raise no `QUESTION` decision. With `requestAccess` denied, the run lists no requestable repositories. With `saveArtifact` denied, a file the agent names with the tool is `REJECTED` with `TOOL_DENIED` at the upload endpoint (the host says `source=save_artifact`), while the files in `/output` (`source=output`, or no source from an older host) are saved: `/output` is the job's result channel, not a tool. The prompt's `# How to work` names only the allowed tools and says what to do instead of a denied one.

**Connection tools: a mode per tool.** `agent_tool.tool_names` (the granted names of an MCP connection) becomes `agent_tool.tools`, a JSON object from tool name to mode, for every kind: on an MCP connection the tools granted (`ALLOW`) or denied (`DENY`), at least one entry, access `READ`; on a tracker the exceptions to its level, usually none. A row of denials only brings the connection into no run but keeps its denials against a thread's grant. Every connection with tools has a catalogue: an MCP connection's as its server listed it (ADR-0040); a tracker's fixed (`SourceTools`: `get` and `search`, each with effect `READ`, Tinfirm's own schema and description, always allowed and present). The API shows it as `Connection.tools` for every kind, with `effect` (null for an MCP tool). `request_access` for a connection whose every served tool the agent is denied is refused with `TOOL_DENIED`: no decision nobody could satisfy. The `# Answers` line of an approved grant names what the thread got: the served tools the agent is not denied.

**Audit.** `agent.created` and `agent.updated` record the six policies; `agent.access.changed` records the modes per connection. A refusal is audited as `tool.denied` by the agent (the kind, the tool, the connection), once per run and tool: a prompt-injected agent that keeps calling a denied tool is one row, not a flood; every attempt still reaches the agent as the tool's error, which the transcript shows.

**API.** `AgentPolicies` (six fields, all required in responses), `AgentPoliciesInput` (every field optional: the default on a create, unchanged on an update), `PolicyMode` with `DENY`, `ToolMode` (`ALLOW`, `DENY`), `AgentToolMode {name, mode}`, `AgentToolAccess.tools` and `AgentToolAccessInput.tools` as `[{name, mode}]`, `ConnectionTool.effect` with nullable seen-at times, `Connection.tools` for every kind with tools. Nothing is released, so the shape of `tools` changed instead of a second list beside it.

**Web.** The Permissions tab gains the group "What it may do" with the four policies on Allowed/Denied controls; the Access tab lists every connection's tools with a Deny / Default / Allow control each and the effective state as a hint; a tracker's connection page shows its fixed catalogue read-only. The glance shows what is denied.

**Who sets it.** Whoever may change the agent: OWNER and ADMIN for every agent, an OPERATOR for its own (CONVENTIONS §14.1), as for every other setting of an agent.

## Consequences

- The owner's two examples are met: `requestNetworkAccess: DENY` takes the tool from an agent's runs and refuses its requests; an MCP server's `update_customer` set to `DENY` is never listed for that agent and no thread grant lifts it.
- Enforcement does not depend on the runner host. An older host that lists a denied tool, or a process that reaches the listener (threat model R28), gets `TOOL_DENIED`; the host's filter is the courtesy that keeps the agent from trying. An older host also sends no upload `source`, so a denied `save_artifact` file from such a host is saved: the server enforces where it can tell, and the host filter closes the rest.
- R33 narrows: a member who decides can no longer grant a thread a tool the agent is denied. Q19 (whether tool access needs an OWNER or ADMIN) stays open: under one rule for every setting, an operator can lift a denial on their own agent, which a company default per platform tool could change later.
- `/output` stays a door under `saveArtifact: DENY`, by design: it is the result channel of every non-code specialist, and the same scans apply as to an upload. A "no documents" policy would be a different switch, on the job's result.
- `ASK` per tool (each call an `APPROVAL` decision, the deciding transaction executing the call) is the solution design's package 3, built with the first tracker write, `label` (2026-10-08, for a triage agent that could recommend labels but not apply them): `ToolMode.ASK` on any tool of a connection; the fixed catalogue of a GitHub or GitLab connection gains `label` with effect `WRITE` (`{key, add?, remove?}`; Jira's labels are not written); under the agent's `WRITE` level a tracker's write takes the `sourceWrite` policy as its mode, `ASK` by default; a thread's grant of a connection gives its reads and an MCP server's tools, never a tracker's writes. A `TOOL` call under `ASK` is checked like any call, then raises an `APPROVAL` decision whose subject holds the tool, its arguments (at most 64 KiB) and what the call does, answered `PENDING` with the decision (the same request id gets the same decision; at most 10 open per thread); the agent ends its turn as after `request_access`. On `APPROVED` the run module executes the call in the deciding transaction, on the connection the decision names (the tool's name alone would follow a renamed connection) and with its token (`secret.accessed`, purpose `decision-tool:{decisionId}`), keeps the result as the decision's answer and audits `tool.called` with the decision; a failure is a SYSTEM comment and never fails the decision; the DECIDED turn's `# Answers` carries the outcome, the note and the result. `DENIED` runs nothing. The remaining writes (`comment`, `transition`, `close`) join the same catalogue later; an MCP tool that writes is still one the company allowed and the agent was granted, unless the agent's entry asks for it.
- A company switch for a tracker's tools (a `DENY` in its fixed catalogue, as for an MCP catalogue) is later work.
- The runner protocol gains one optional field; v1 hosts get nothing new, and the server refuses v1's `run.ask` under `ask: DENY` with the same code.

## Alternatives considered

- **Deny by instruction.** Tell the agent not to ask for network access. Rejected: instructions are advice to the model (R15); a prompt-injected agent ignores them, and the request still lands in a member's inbox.
- **A company-wide switch per platform tool** instead of per agent. Not what was asked: one strict agent next to a free one. A company default that new agents inherit can come later behind the same fields.
- **One table for platform and connection tools alike.** Uniform storage that people never see: the web shows platform tools among the policies and connection tools under access either way. Each kind stays where it already lives.
- **A map only, no `READ`/`WRITE` level.** Every tool named explicitly for every agent. Rejected: every new tracker write tool would need every agent edited, and "may read Jira" is what most agents need. The level stays as the default, the map as the exception.
- **Deny as a host-side filter only.** Rejected: the host is semi-trusted (R28), an older host ignores the field, and the sandbox can send any frame the host forwards.
- **Additive API fields** (`deniedTools` beside `tools`). Rejected before a release: two lists that must not overlap are worse than one map with a mode, which also takes `ASK` without a third list.
- **`ASK` first, or `ASK` never.** The owner asked for deny; `ASK` was designed so the model takes it and built when the first tracker write needed it.
- **A thread's grant that gives a tracker's writes too.** Rejected with the writes: a member who approves "access to the tools of GitHub" grants reads; a write is the agent's own level (`WRITE`, set by whoever manages the agent) under its approval policy. Otherwise an agent that may only read could write once a thread was granted the connection.
- **Executing the approved call after the commit, or on the next turn.** Rejected: the DECIDED turn is requested in the deciding transaction, so a result that came later would miss its prompt; the call runs before the turn is requested, as a change request opens on approval, and the outbound client's timeouts bound it.
