# ADR-0072: A system holds the company's credentials and lends them to groups and to service accounts

- Status: Accepted
- Date: 2026-10-17
- Decided by: the owner, 2026-10-17
- Sources: [ADR-0058](0058-authority-from-the-audience.md) (principals, systems, accounts and grants), [ADR-0052](0052-shared-accounts.md) (a company credential on a connection, granted to groups; superseded by ADR-0058), [ADR-0059](0059-litellm-budgets-and-the-model-proxy.md) (a key and budget per principal), [ADR-0065](0065-company-model-key.md), [ADR-0071](0071-mcp-servers-without-accounts.md); [PLATFORM.md](../PLATFORM.md) §3, §4, §5 and §7; [CONVENTIONS.md](../CONVENTIONS.md) §15.1 to §15.3, §15.15 and §15.16; the package 1 contract's invariants I1 to I10 ([reviews/2026-10-12-package-1-contract.md](../reviews/2026-10-12-package-1-contract.md))
- Changes: ADR-0058 decision 3, where an account is a principal's credential on a system and a grant lends a service identity's account: a service account's credentials are the system's, lent to it. The account module (credentials, lendings, the binding rule's grants), the system module (the system page's credentials, reading tools with a credential), the trigger module (a row names a service account and the credential lent to it), the conversation module (a binding names a credential), the chat module (a bot is a credential lent to a service account), a migration, the API, the MCP endpoint's renderings, the web app; PLATFORM.md and CONVENTIONS.md; the threat model

## Context

- Since ADR-0058 a system holds no credential of its own. Every credential is an account of a principal: a member's own, or a service identity's, which a grant lends to a group (`READ` or `WRITE`) and a trigger's author picks per system ("Use the accounts of: svc-dev").
- Setting up a company system therefore spans three pages. An admin registers an MCP server on Systems; creates a service identity and connects its account on the server on Service identities; lends it to groups on the same page or its Grants tab; and returns to the system to read its tools.
- Reading an MCP server's tools uses only the admin's own account (`refreshSystemTools`). An admin without one on a server that asks for a token gets *"The server answered 401 to initialize"*, and the system turns `ERROR`, though its test says *"The server answers and asks for a token"*. The way out, connecting a personal account on the Accounts page, is said nowhere, and leaves the admin with an account that then binds first in their own conversations.
- A service identity holds one account per system (I1). Two tokens of different scope on one system, a read-only one for analysts and a writing one for support, need two service identities, each with its own LiteLLM key and budget.
- Service identities also do what credentials alone cannot: their key and budget pay for triggers, suspending one stops everything it does (I7), groups are given the right to use one on triggers, and a chat system's bot is one's account (I9). The owner keeps all of that.
- The name "service identity" says neither that it holds credentials nor that it pays. The owner calls them service accounts.

## Decision

**A company credential belongs to its system. Whoever manages the system adds it on the system's page and lends it to groups, `READ` or `WRITE`, and to service accounts, each of which borrows at most one per system. Service accounts, as service identities are called from now on, keep their budget, their suspension, who may use them and their place in triggers and chat bots. A member's own account is unchanged.**

1. **Names.** The web app and the documents call a service identity a **service account**. "Account" keeps its meaning for a member's own credential on a system ("Your account on Jira"); a **credential** is a company credential that a system holds; to **lend** is to give a group (a grant) or a service account the use of a credential. The API, the code and the tables keep `serviceIdentity` and `principal.kind = 'SERVICE'` (open point 4); a field of the API that holds a credential says so (`credentialId`, `botCredentialId`, an inbox item's `credential`), never `accountId`, which stays for a member's own account or either.
2. **A credential** belongs to a company system, never a personal server (I6 stays: only its owner's account acts there). It is an `account` row that no principal holds (`principal_id` null, `principal_kind = 'SYSTEM'`), so that grants, trigger rows, bindings, refresh and revocation keep one table. It has a name, 1 to 100 characters, unique on the system ignoring case; a kind, `TOKEN` or `OAUTH`; its secret, a managed company secret (`SYSTEM_CREDENTIAL`; those migrated keep `SERVICE_ACCOUNT`), as a service identity's account kept it (I3); who it is at the system, from the system's "who am I" as an account's check reads it (`external_id`, `login`, `api_base_url`); its status `OK`, `RECONNECT` or `ERROR` with the last error; whether it is enabled; when it was connected and by whom, and its last use. A system holds any number. OWNER and ADMIN add, store again or sign in again, rename, disable, enable and remove one on the system's page (`MANAGE_SYSTEMS`, `/systems/{id}/credentials`); a token is checked as a stored token is now, a sign-in is an admin signing in as the user the credential should be, with the system's app and the one callback. Audited as an account is, `account.connected`, `account.reconnected`, `account.disconnected` and `account.refused`, with the detail `credential` (its name) in place of `principalId`; renaming, disabling and enabling as `credential.changed`; never with the token.
3. **Identities.** I2 becomes: one identity per system belongs to members' own accounts or to the company's credentials, never both. A member whose own token or sign-in is a credential's user is refused (`409 IDENTITY_IN_USE`, `details.holder` `CREDENTIAL` with its name, which every member may see). Two credentials of one system may share an identity: two tokens of one bot user with different scopes.
4. **Lending to groups.** A grant (`account_grant`, `account_principal_kind = 'SYSTEM'`) lends a credential to a group, `READ` or `WRITE`, once per group. The binding rule of a personal conversation is unchanged in its order: the person's own account when it is `OK`; else the grants to their groups whose credential is `OK` and enabled, `WRITE` before `READ`, then the oldest, one `Granted`, several `Choose`; else `ConnectRequired`. `READ` is enforced as now. I5 becomes: a grant lends only a company credential.
5. **Lending to service accounts.** A service account borrows at most one credential per system (`service_account_credential`, unique per service account and system), `READ` or `WRITE` (open point 1); a credential may be lent to several service accounts. Lending, changing and withdrawing are audited as `credential.lent` and `credential.withdrawn` with the service account. A service account's page lists what it borrows, by system, read-only; lending is done on the system's page.
6. **Triggers.** The editor's choice "Use the accounts of: You | svc-dev" stays. A row of the trigger's table names the author's own account, or a service account the author may use together with the credential lent to it then. The check at every use (`Accounts.check`) also requires that the credential is still lent to that service account, `OK` and enabled. A trigger follows its service account (open point 3): when an admin lends the service account another credential on the system in place of the one it borrowed, the trigger's row names the new one in that transaction (`trigger.accounts_changed`, `why` `lending.replaced`), its open conversations bind it at their next check (audited as `conversation.binding.bound` with the credential it `followed`, and said in the thread), and its author is told in their inbox as of an admin's change on their behalf. When the admin withdraws the credential, the trigger stops and pauses as when its author loses a right, until the author names another. The service account's key and budget pay, as now.
7. **Service accounts keep** their LiteLLM key and budget (ADR-0059), their suspension (I7: a suspended service account's borrowed credentials act for nothing through it, while the groups' grants of the same credentials go on), the groups that may use them on triggers (`service_identity_user`), and deletion, which withdraws what they borrow and removes no credential (`409 SERVICE_IDENTITY_IN_USE` while live triggers use them, as now).
8. **Two switches.** Suspending a service account stops what acts through it; disabling a credential stops every use of it, by groups and by service accounts, at its next check, until it is enabled again: the binding rule and the check read it as a credential an admin must fix (`RECONNECT_COMPANY`, addressed to an admin), as one the system refused. Pausing a system stops every credential on it, as now. The chat bot is disabled only with the bot.
9. **Chat bots.** A chat system's bot is a credential on that system lent to a service account (open point 2): `external_system.bot_account_id` names the credential, and I9 becomes "at most one bot, a credential lent to a service account". It is lent to no group.
10. **Reading tools and testing.** `POST /systems/{id}/tools/refresh` and `POST /systems/{id}/test` take an optional `credentialId`: one of the system's credentials (OWNER, ADMIN), revealed with the purpose `system-tools:{id}` or `system-test:{id}`. Without it they use the caller's own `OK` account, else the system's only enabled `OK` credential, else no credential. Their answers say what was used (`withAccount`, `credentialId`), and the refresh's whether the server asked for a credential (`credentialRequired`). A server that asks for one when none was given was reached: the system's status stays `OK`, as its test says, and the page offers to add a credential and read the tools again. A credential named that is disabled or not `OK` is not sent; the answer says so.
11. **The system's page** shows, for a company system, how agents act there: a member's own account (how many members hold one, as Members says it); no credential (an MCP server set so, ADR-0071); and the system's credentials, each with its status, its identity, the groups it is lent to with their access and the service accounts that borrow it, with **Add credential** (name; a token, or **Sign in** where the system offers it; lend to groups and to service accounts). Registering a system, adding its credential, lending it and reading its tools need no other page. Service accounts keep their own page, for their budget, suspension, who may use them and what they borrow (`GET /service-identities/{id}/credentials`); their own accounts' endpoints go.
12. **Migration** (one, lossless). Every service identity's account becomes a credential on its system, named after the service identity, keeping its secret, identity, status and dates, lent `WRITE` to that service identity; every grant names that credential instead; every trigger row and every conversation binding that names such an account names the service account and the credential (a binding through a grant loses its holder: the credential is the company's); every chat bot names its credential, which its service account borrows. Members' accounts do not move. Pending sign-ins are dropped: they expire in ten minutes. Audit events written before keep their names and stay readable (V049).

## Phases

Both phases ship together, so no group ever borrows a token two ways:

1. **Credentials, lent to groups.** The credential, its grants, the system page, reading tools with a credential (which fixes the case in the context), the identity rule, and the rename in the web app.
2. **Lent to service accounts.** Lending to service accounts, triggers and chat bots through it, and the migration of service identities' accounts and their grants (decision 12); service identities' own accounts go.

## Consequences

- An admin sets up a system on its page: register it, add a credential, lend it, read the tools. Members keep connecting their own accounts on Accounts.
- Two tokens of different scope on one system are two credentials, not two service accounts, and no new key or budget is made for them.
- What a service account is stays as it was, for triggers, budgets and bots; it no longer owns a credential, so deleting one never deletes a token another service account or a group uses.
- A credential is the company's: anyone it is lent to acts as its user at the system. The audit of a call names the credential, the person or service account that acted, and the grant or lending.
- The binding's and the trigger table's rules, I2, I5 and I9 change, and with them the database checks of V001, V011 and V048 (replaced in V049) and their constraint tests. In the threat model, A29 becomes the systems' credentials, and the lending to service accounts is threat 8.44.
- Not in this decision: credentials on personal servers; a credential lent to a member alone; renaming the API's and code's names.

## Open points

Decided by the owner (2026-10-17):

1. **A service account's lending `READ` or `WRITE`.** Either, `WRITE` as the page proposes it, enforced as a grant's `READ` is (tools, the workspace and the trigger editor's open writes) and the write-back: a row whose binding's token is lent `READ` at the attempt is dropped before any writer, with a notice in the thread that names the credential and the service account (`OutboxDelivery`, I9), and the editor refuses a tracker trigger whose source row is lent read-only while its results write there (`400 ACCOUNT_READ_ONLY`; a lending narrowed after the save pauses nothing); a read-only service account bounds a channel trigger that anyone in the channel may drive (PLATFORM.md §7.2). A service identity's own account was always `WRITE`, and the migration lends `WRITE`.
2. **A chat bot as a lent credential.** So that every company credential lives on its system. Setting the bot (`PUT /systems/{id}/bot`) adds or replaces the credential and lends it to the bot's service account; the bot's credential is changed and removed only with the bot.
3. **A trigger when its service account's lending changes.** *Decided again by the owner, 2026-10-17. At first it stopped and paused (`USE_RIGHT_GONE`), as PLATFORM.md §7.1 then said ("it never switches account or payer").* The trigger acts through the service account, and an admin who lends the service account another credential means its triggers to act with it: pausing them asked every author to save a row that could name nothing else, and left their open conversations waiting for good. So a replaced credential is followed, by the trigger's row and its open conversations, and the author is alerted; a withdrawn or disabled one still stops it, since nothing replaces it. The identity the trigger acts as on the system may change with the credential: the lend dialog says how many triggers switch and that their authors are told, and the audit keeps the lending, each trigger's new table and each binding that followed. A credential stored or signed in again keeps its id, so rotating a token changes no trigger.
4. **The API's names.** `serviceIdentity` stays in the API and the code until a version of the API renames it on purpose; the web app and the documents say service account.

## Alternatives considered

- **Keep the model and set up on the system page**, creating a service identity behind each token there. One page, but every token makes a principal with a LiteLLM key and budget, on Service identities, in the trigger editor and in the budgets.
- **Credentials on systems instead of service identities** (as ADR-0052): simplest for setting up, but triggers lose a payer of their own, the switch that stops a bot user everywhere, and one choice for every system. The owner keeps service accounts.
- **Groups hold credentials**, groups and service identities merged. Groups also share agents and form trigger teams, and a group made only to share a token would mix the two; membership would decide both who acts with a token in conversations and who uses it on triggers.
- **Several credentials per service identity.** Two tokens on one system without a second service identity, but the setup stays on the service identity's page.
- **Other names**: bots (says neither credentials nor budget, and collides with the chat bot), wallet (says money, and collides with budgets), mandate (exact, but rare in software). The owner chose service accounts.
