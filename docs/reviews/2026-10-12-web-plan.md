# The web app on the redesign: a plan

Status: decided on review (§11) · 2026-10-12 · Owner: J. Balcar

This plan rebuilds Tinfirm's web app (`web/`, Angular) on the redesigned API: the [design of record](../PLATFORM.md), [the record of the redesign](2026-10-12-platform-redesign.md), the contracts of packages [1](2026-10-12-package-1-contract.md), [2](2026-10-12-package-2-contract.md), [3](2026-10-12-package-3-contract.md) and [4](2026-10-12-package-4-contract.md), and the built API (`api/openapi.yaml` 0.6.0, packages 1 to 3). It covers the navigation and every page, the reuse of today's code, the build order in slices with estimates and review points, the tests, and the questions for the owner. Nothing here was built when it was written.

This plan holds the UI to the design's test, **fewer nouns**, and to one rule of its own: **every page that starts work says who acts and who pays before it starts.**

## 1. Where things stand

**On 2026-10-12 the web app still targeted the 2026-10-05 API.** Its domain is work items, jobs, connections, agent kinds and model credentials. Of the 111 operations it imports from the generated client, 48 no longer exist (`listWorkItems`, `getJob`, `startThread`, `listConnections`, `createTrigger`, `listModelCredentials`, `createSharedAccount`, `decide` and others). Most of the 63 that remain changed shape: `Role` lost `OPERATOR` and `VIEWER`, `Agent` lost its kind and credential, and `Decision`, `Inbox` and `Run` were reshaped. The app does not compile against the built contract, so the rebuild starts by making it compile.

**What is sound:** Angular 22 (standalone, zoneless, signals, `OnPush`), spartan/ui with Tailwind 4 and 25 helm components in `src/app/ui/`, the design system in [DESIGN.md](../../DESIGN.md) (sage ground, white sheets, green for the agent, orange only where a person must act), the session and auth guards, the generated client (`ng-openapi-gen`, regenerated by `prestart`, `prebuild` and `pretest`), RFC 9457 problem mapping, the SSE run stream with its polling fallback, the transcript renderer, sanitized Markdown, file previews, Vitest specs with fake HTTP and a fake `EventSource`, and Playwright against a running server.

**The built API, as it shapes the UI:**

| Fact | Consequence |
|---|---|
| `getAgentReadiness` answers, before anything starts, the settings in effect, who pays (`READY`, `WAITING`, `REFUSED`), how each system would bind and whether a host can run it | The "who acts / who pays" panel before a conversation needs no logic of its own in the client |
| `Conversation` carries `bindings[]` with a ready sentence (`text`: "GitHub: via Analysts, read-only"), `payer`, `seenByOwner`, `waitingOn` and `waitingReason`, `activeRunId`, its turns as runs, decisions, outputs and attachments | One read draws the conversation page |
| Live updates exist per run only (`streamRunEvents`); a conversation has no stream | The conversation page streams its active run and polls `getConversation` while visible (§8, gap 3) |
| `Decision.mayDecide`, `Agent.usableByMe` and `editableByMe`, `Agent.widening`, `AgentSettings.widening` | The UI repeats the server's answers and never re-derives rights |
| Triggers (package 4), chats and the webhook (package 5), spend views and the leaving flow (package 6) are not built | Their pages are planned against the contracts and built when the API lands |

## 2. Rules for every page

1. **The design's nouns, and only those**: member, service identity, group, system, account, grant, model access (shown as "who pays" and "budget"), agent, settings, trigger, conversation, question, approval, runner host. Never on screen: work item, job, thread (as an object), connection, credential, agent kind, shared account, profile, pool.
2. **Who acts and who pays before work starts.** One component, `app-who-acts-who-pays` (`shared/who-acts-who-pays.ts`), draws it from `AgentReadiness`, `Conversation`, `Run` or a trigger preview: one line per system ("Jira: your own account", "GitHub: via Analysts, read-only", "Confluence: connect when first needed"), then who pays ("Your budget: $38.20 of $50 left, resets 1 Nov"; "Your Claude subscription on my-laptop"; "svc-ba's budget"), then where it runs ("A company host" or "Your personal host only"). It appears on the new conversation page, the agent page, the settings per agent, the conversation page, the run page, the trigger editor and the trigger page.
3. **Orange only where a person must act** (DESIGN.md's Two Voices and Scarce Orange rules): open decisions, Connect cards, the injection acknowledgement, a widening waiting for acceptance on the agent's own page. Everything waiting on a runner, a budget reset or an admin stays neutral for the person who waits.
4. **The server decides.** A `404` shows the not-found page and nothing more. A `403` or `409` shows the problem's message from `api/problem.ts`, mapped per code. Buttons follow `usableByMe`, `editableByMe` and `mayDecide`.
5. **Other people's words stay text**: agent output, comments and files render through `renderMarkdown()` and the sanitizer, as today (ADR-0047).

## 4. The decisive pages

### 4.1 The conversation page: `conversations/:conversationId`

**Purpose:** one agent's work for one person, readable at a glance: what was said, what the agent is doing, what it needs from you, with whose accounts and on whose budget.

**Operations:** `getConversation`, `renameConversation`, `postConversationMessage`, `cancelConversation`, `retryConversation`, `endConversation`, `chooseConversationBinding`, `continueConversationBinding`, `decideDecision`, `streamRunEvents`, `listRunEvents`, `listAttachments`, `uploadAttachment`, `downloadAttachment`, `deleteAttachment`, `startMyAccountSignIn`, `storeMyAccountToken`, `getMyModelAccess` (budget left, for one's own conversations), `getAgent` (status, `editableByMe` for "for good" approvals). Package 4 adds `EXTERNAL` messages, team approvals and the `RESULT` review; package 5 adds `CHAT_THREAD`.

**Layout:** a thread sheet, and from `lg` a 20rem side column. On a phone it is one column, the side column opens as a sheet from the header's "Details" button, and the composer sticks to the bottom.

| Part | Component | Holds |
|---|---|---|
| Header | `ConversationHeader` | Title (rename in place), key and branch in mono, the agent (a link), the subject chip (`subject.key` to `subject.url`), the state chip from `waitingOn`, and a menu with Cancel turn, Retry and End (with a confirm dialog) |
| Who acts / who pays | `app-who-acts-who-pays` | `bindings[]` by `text` and state, then "Other systems connect when the agent first needs them"; `payer` with the budget left and its reset, or the subscription's label; the runtime; the last turn's host and its kind (`runnerHostKind`) |
| The Owner notice | `OwnerNotice` | For the person: "The company's Owner can read this conversation in full." (`seenByOwner`, security review row 18). For the Owner reading someone else's: a banner, "{person}'s conversation. Only {person} writes, decides and connects accounts here", and no composer; cancel, retry and end stay, as the API allows |
| Messages | `MessageList` | `PERSON` bubbles (yours on the right), the agent's answers with a status line per turn ("Worked 6m · 14 tool calls · $0.42 · View run", from `turns[]` by `runId`) and "Show work" folding the turn's transcript (`TurnWork`, `listRunEvents` on first open), `SYSTEM` notes in faint text, messages waiting for the next turn, unanswered ones after a cancel |
| The live turn | `LiveTurn` | For `activeRunId`: a `RunStream` on `streamRunEvents` with "Working · 2m 10s · editing files" and the latest step. While queued, `queueReason.text` with a link to the fix: `BUDGET_SPENT` to Accounts › Budget with the reset time, `ACCOUNT_REQUIRED` to the card, `NO_HOST_FOR_CREDENTIALS` and `NO_RUNNER_HOST` to the runner hosts, `AGENT_PAUSED` to the agent |
| Cards | `BindingCard`, `DecisionCard` | Shown where they were raised; open ones also pinned above the composer while the reader is scrolled away |
| Composer | `Composer` | Markdown; "This answers the open questions" while questions are open (`answersOpenQuestions`); "Your message waits for the next turn" while a turn runs; attach a file (the credential scan's `422 CREDENTIAL_FOUND` named, and an acknowledgement for OWNER and ADMIN) |
| Side column | `ConversationSide` | Outputs (change requests with their state, documents with preview and download, links), files (add, preview, download, delete; `ATTACHMENT_IS_OUTPUT` explained), workspace (each repository, read-only and why: "the grant of Analysts is read-only"), network hosts (`hosts`, `grantedHosts`), turns (each a link to its run) |

**Binding cards** (`shared/binding-card.ts`, shared with the inbox), by `ConversationBinding.reason`:

| Reason | The card | Actions |
|---|---|---|
| `NONE`, `RECONNECT_YOURS` (orange) | "Connect GitHub to continue: {agent} asked to use it" / "Sign in to GitHub again" | "Sign in with GitHub" (`startMyAccountSignIn`, `returnTo` this page) when the system has an app; "Paste a token" (`storeMyAccountToken`, then `continueConversationBinding`) |
| `PICK_GRANT` (orange) | "Act on GitHub through:" each choice with its group, holder and access | `chooseConversationBinding {grantId}`; "Connect my own instead" `{reconnect: true}` |
| `CHOOSE` (orange) | "Your GitHub account needs signing in again, or use the grant of Analysts (read-only)" | Reconnect, or the grant |
| `RECONNECT_COMPANY`, `SUSPENDED` (neutral) | "An admin must sign svc-dev in again. Admins were told." | None for the person; the admin's inbox has an `ACCOUNT` item |
| `SYSTEM_OFF` (neutral) | "Personal MCP servers are switched off in this company" | None |
| `GONE` with any reason (neutral) | "GitHub can no longer be used in this conversation (the grant was removed)" | "Start a new conversation with {agent}" |

Back from a sign-in, the page reads `?account=connected&system=`, calls `continueConversationBinding` and confirms; `?account=denied` and the other reasons of `completeSignIn` get a sentence each (`account-labels.ts`, adapted).

**Decision cards** (`shared/decision-card.ts`, adapted): a question with its options and a free answer; an approval by `subject.type`. `TOOL_CALL` shows `what`, the system and the account it runs as, with the arguments folded. `REPOSITORY` and `HOST` offer "This conversation" or, only when `editableByMe`, "The agent, for good"; a repository also offers `READ` or `WRITE`. `CHANGE_REQUEST` names the repository. Approve or deny with a note. With `mayDecide` false the card reads "Waiting for {approverName}". A decided card loses its orange and shows the outcome and an approved call's result.

**States:**

| State, from the API | The page |
|---|---|
| Running (`waitingOn AGENT`) | Green "Working" line; messages wait for the next turn |
| Waiting on a runner (`waitingOn RUNNER`, the run's `queueReason`) | A neutral line with the reason in words and the link that fixes it; `BUDGET_SPENT` with the reset (V7) |
| Waiting on the person (`waitingOn PERSON`: `QUESTION`, `APPROVAL`, `ACCOUNT`) | Orange: the open cards above the composer and a "Needs you" chip |
| Failed (`turnStatus FAILED`) | The failure in words with Retry; `USAGE_LIMIT` with the reset; `RUNTIME_REMOVED` with "Start a new conversation"; `MODEL_NOT_ALLOWED` with a link to your settings |
| Cancelled | Neutral, with Retry; unanswered messages marked |
| Agent paused (`AGENT_PAUSED`) | "{agent} is paused; its turns wait" |
| Ended (`state ENDED`, `endedReason`) | Read only, no composer; outputs and files stay |

**Freshness:** `ConversationStore` (`pages/company/conversations/conversation-store.ts`) holds the `Conversation` signal. Every mutation answers the conversation and replaces it. While `activeRunId` is set, the run stream drives the page and its final `run-status` re-reads the conversation. Otherwise `pollWhileVisible` re-reads it every 5 s while it waits on a runner or the agent, and every 30 s otherwise; polling stops once the conversation has ended.

### 4.2 New conversation: `conversations/new?agentId=&subjectSystemId=&subjectKey=`

**Purpose:** say who acts and who pays before the first message goes. It is a page rather than a dialog, so that it has room on a phone.

**Operations:** `listAgents (usable=true)`, `getAgentReadiness`, `getAgent` (its repositories), `listSystems` (the subject's system: `JIRA_DC`, `JIRA_CLOUD`, `GITHUB`, `GITLAB`), `acceptAgentVersion`, `startMyAccountSignIn` and `storeMyAccountToken` (connect now, returning here), `startConversation`.

**States:** no usable agent ("No agent is shared with you yet", with "Create an agent"); the payer `REFUSED` ("An admin must set up model access first", Start disabled); the payer `WAITING` ("You can start; the first turn waits until 1 Nov"); `hosts.runnable` false, with its `reason`; a system to connect or choose (an optional orange "Connect now, or when the agent first needs it"); a widening pending (the widening card, §4.3).

**Interactions:** pick the agent, and the panel fills from readiness. Optionally a subject (system, key, link, title) and the repositories (the agent's, preset from the settings' defaults). Then the message. Start calls `startConversation` and opens the conversation; `MODEL_ACCESS_UNAVAILABLE` and `NO_HOST_FOR_CONVERSATION` are explained with `details.reason`.

| Page | Operations | States | Interactions |
|---|---|---|---|

| **Agent** `agents/:agentId` | `getAgent`, `getAgentReadiness` (when usable), `acceptAgentVersion`, `pauseAgent {stopRunning}`, `resumeAgent`, `deleteAgent` | Paused banner; widening pending; not usable ("Shared with Analysts; ask its owner {ownerName}"); `AGENT_HAS_ACTIVE_RUNS` on delete | Reads the definition: what it may use (systems, each tool's mode as "Allowed" or "Needs your approval", each tool's effect, repositories with `READ` or `WRITE`, hosts), whom it is shared with, its owner and version. **The editor** is one page of sections with a section index (not a wizard): *Who it is* (name, `@handle`, description, runtimes in order, the first the default); *Instructions* (the Markdown editor); *Systems and tools*: add a company system with tools or repositories, which fills its tools (reads "Allowed", writes and unconfirmed tools "Needs approval"); each tool shows its effect ("Reads", "Writes", "Unconfirmed: counts as a write") and a two-way mode switch; rows the system no longer serves read "no longer offered"; *Repositories* (`READ` or `WRITE`, from the listed code hosts); *Network hosts* (today's `agent-network-hosts`); *Sharing* (groups). One sticky bar saves: a new agent in one `createAgent` (version 1); a change sends only the changed sections, in that order. Before saving, a notice computed in the client names a **widening** (a new system, tool, repository or host, `READ` to `WRITE`, "Needs approval" to "Allowed"): "People who use {agent} keep version 4 until they accept this change; what you remove applies at their next turn" (security review, row 11). Instructions and descriptions never widen, and the notice says nothing for them.

**The widening card** (`agents/widening-card.ts`), on the agent page, the settings page and the new conversation page when `widening` is present, in orange because only the person can accept: what the current version adds over the accepted one (systems, tools with their mode and what they were, repositories with their access and what it was, hosts), then "Accept version 6", which calls `acceptAgentVersion {version: widening.currentVersion}`, naming the version shown so that nothing is accepted unseen.

### 4.4 Settings per agent: `agents/:agentId/settings`

**Purpose:** one person's narrowing of one agent, and what it means for who acts and who pays.

**Operations:** `getMyAgentSettings`, `putMyAgentSettings`, `resetMyAgentSettings`, `getAgent`, `getAgentReadiness`, `listGatewayModels`, `getMyModelAccess` (subscriptions, the key's models), `listSystems` and `listSystemTools` (one's own MCP servers), `acceptAgentVersion`.

**The form** (`shared/agent-settings-form.ts`, which the trigger editor reuses with a trigger as owner) is one card, without headings for when a setting applies:

- the runtime, among the agent's, and who pays, your budget or a subscription by host and label, among those serving the runtime; where there is a choice, each says that open conversations keep the one they started with;
- the model, picked from those your key allows, or empty for the runtime's default;
- effort;
- your added instructions ("added after {agent}'s"); a person's only, as the trigger has its own instruction;
- default repositories and default projects;
- each of the agent's systems on or off;
- each tool as "As the agent says", "Ask me" or "Off", never "Allowed" where the agent asks (I4);
- your own MCP servers, each tool "Allowed" or "Needs approval".

Everything but the runtime and who pays applies from each open conversation's next turn.

Below the form, `app-who-acts-who-pays` is read again after each save.

**States:** defaults (`stored` false: "Nothing saved yet; these are the defaults"); widening pending; the gateway not configured (`listGatewayModels` `409`: the model field is disabled, with the reason); a subscription gone; field errors `RUNTIME_NOT_LISTED`, `MODEL_NOT_ALLOWED`, `SUBSCRIPTION_NOT_SERVING`, `SETTINGS_WIDEN`. "Back to defaults" calls `resetMyAgentSettings`.

### 4.5 The trigger editor (package 4): `triggers/new`, `triggers/:triggerId/edit`

**Purpose:** a standing rule that reads as one sentence and says, before it is saved, who acts, who pays, who can drive it and what runs without approval. This page holds the most choices of any, so it gets two owner reviews (§7).

**Operations (package 4, §6 of its contract):** `listAgents (usable=true)`, `listSystems`, `GET /triggers/choices`, `listGatewayModels`, `listGroups`, `POST /triggers/preview` before every save, `POST /triggers`, or `PATCH /triggers/{id}` with `PUT /triggers/{id}/accounts` and `PUT /triggers/{id}/settings`.

**Layout:** the form on the left, the preview sticky on the right. On a phone the preview sits below, with a sticky summary bar: "Acts as svc-ba · paid by svc-ba · can run".

1. **When**: the source (a tracker system, or a schedule); up to five events with their values; the subject kind; the scope (project, `owner/repo`, path, or "everything this account sees"); groups of conditions; once or every time. A schedule takes its cron and time zone, adapted from today's `trigger-schedule-fields`.
2. **The agent does**: the agent, the instruction.
3. **Acts as**: one choice, "Use the accounts of: You | svc-ba | svc-dev", from `/triggers/choices`. Each choice shows its account and status per system, its budget and the systems it would leave out. It fills the account table. The author may change or remove any row, except the source's row, which must exist (`SOURCE_ACCOUNT_REQUIRED`). Systems without a row are listed as "Not available to this trigger's runs".
4. **Paid by**: the payer and its model access, with the budget left. A subscription is offered only when the payer is the author.
5. **Narrowed for its runs**: `agent-settings-form` in trigger mode. For open events it prefills "Ask" on every write tool. One's own MCP servers are offered only while every row is one's own account (security review, row 12).
6. **Team**: a group, or "Only you".
7. **Results**: comment on the issue, review before writing, and the on-success and on-failure actions (today's `trigger-actions`, adapted).

**The preview** (debounced after every change) shows the sentence; who acts per system (account, holder, identity, status); who pays (the budget left and its reset, or the wait or refusal); whether a host can run it; the next three firings of a schedule; and for a change, "3 open conversations keep the accounts they started with". **The injection warning** (`openToAnyone`) is an orange box: "Anyone who may comment on issues in SHOP can drive {agent} with these accounts. Without an approval it would comment and transition as **you** (your own Jira account)." It offers two fixes in one click each: "Use svc-ba instead" and "Ask before every write". While a row is the author's own and an `ALLOW` write remains, Save needs the checkbox "I understand" (`acknowledgeOpenEvents`). Save is enabled once the preview passes. `ACCOUNT_NOT_ENTITLED` marks its row; `CANNOT_RUN_ANYWHERE` and `MODEL_ACCESS_UNAVAILABLE` mark the panel.

## 9. Gaps in the built API

Small server changes the plan needs or would like. Each has a workaround until it lands.

1. **`Member.principalId`** (and its status): the Members page needs it to set a member's budget with `getPrincipalModelAccess` and `updatePrincipalModelAccess`. Until then, budgets are set for service identities only.
2. **The caller's principal** (`Company.myPrincipalId`), to tell one's own conversation from one the Owner reads. Workaround: `getMyModelAccess().principalId`.
3. **A conversation stream** (`GET /conversations/{id}/events/stream`: changed, message, decision, binding). Until then: the run stream and polling while the page is visible (§4.1). Proposed with package 6's work on server replicas.
4. **One call for an agent's definition**, so that one Save makes one version. Optional: several versions in one save still show as one widening.
5. **The Owner's reads audited** (security review, row 18): the Owner's banner says "this read is recorded" only once the server records it.
