## Inventory, 2026-10-05

Made before the restart, read-only, over the server, the runner host, the web app and the deployment. The findings that shaped the design:

- The server's infrastructure (tenancy with forced RLS and definer lookups, identity, vault, audit chain, the runner WebSocket handling with epochs and leases, dispatch and queue reasons, transcripts and SSE, attachments with the scan, the code host and tracker clients, the markup converter) is sound and tested: 615 tests, isolation tests generated from the OpenAPI contract, migration tests. It stays.
- The run module drove tasks through a thirty-method port, `run.task_id` was not null, and the platform tools spoke of tasks and backlogs: the seam the restart cuts.
- The tracker write-back enqueued after the commit on an in-memory executor, so a crash could lose a write: the restart writes the outbox row in the committing transaction.
- Four separate outbound HTTP clients without a guard against private addresses: the restart has one client with the guard.
- The runner host's sandboxing, git proxy, push lease, redaction, connection robustness and test harness are the best part of the code and change only where the protocol gains the generic request frame, the tools list and the output folder.
- The web app's core, API client, problem mapping, run stream and transcript builder are reusable; the pages of the old domain (projects, tasks, trackers, routines, overview) are not, and run events had two renderers.
- The deployment contract (image, UID, ports, probes, environment names, Helm values, secret names, the runner endpoint) is what deployments depend on; it does not change.

## Cleanup pass, 2026-10-05

After the eight packages, one pass over the code, in four parts, each verified as below. Server: `cd server && ./mvnw -B -ntp clean verify` against PostgreSQL 16. Web (Node 24): `npm run lint`, `npm test`, `npm run build`. Runner: `cargo test --workspace`, clippy with `-D warnings`, `cargo fmt --check`.

**1. The outbound guard at connect time, and retried reads**.
- DNS rebinding: `java.net.http` resolved a connection's host again when it connected, after the guard had checked it. `GuardedResolverProvider` is now the JVM's resolver (JEP 418, `META-INF/services/java.net.spi.InetAddressResolverProvider`): while a request to a host is in flight (`ConnectionHosts`, a ref-counted registry that `OutboundHttp` opens per request), its lookups lose loopback, link-local, private, shared, unique-local, unspecified and multicast addresses; every other lookup (the database, the identity provider) is the built-in resolver's. IP literals never reach a resolver and are checked as they are. Without private addresses allowed, the server refuses to start when the resolver is not installed; the executable jar and the image install it (checked by starting the jar for the end-to-end run below). Chosen over a per-client resolver (Apache HttpClient 5's `DnsResolver`) because it keeps the one JDK client every connection kind already uses, adds no dependency, and filters only hosts with a request in flight.
- Reads (`GET`) answered 502, 503 or 504, or that could not connect, are tried again twice, after 0.5 s and 2 s, or after a 503's `Retry-After` of at most 5 s; a request that timed out waiting for its answer, and every write, are not repeated (the outbox retries writes).
- The tests package 6 lacked: GitLab's whole-connection listing (`scope=all`) and a FAILED schedule firing (recorded with the reason, rolled back, the schedule moves on).
- Verified: 456 server tests, 0 failures (443 + 13: the resolver with a fake delegate, retries in WireMock scenarios, IP literals, the two sync tests).

**2. The API contract's gaps**.
- `Problem.credentialMatches` in the schema; the web reads it typed.

- `Decision.options` required; `Job.connectionName` (the origin phrase); `Run.workItemTitle`; `Run.failureClass` and `Run.usage` nullable; one `FailureClass` (the runner's classes and `LOST`) for runs and turns, a turn that failed without a class keeps its cause (`V008__run_counts.sql` replaces `job_failure_ck` by `job_failure_class_ck`); `RunRepository` documented as the git result; `Run.counts` (tool calls, messages, thoughts as a transcript shows them), computed from the events in the statement that ends the run (`V008`), so the folded turn needs no events.

A company should be able to implement its own tools for the agents, and each agent should get only the
tools it is given: of a server with five tools, one agent three, another two, a third all five. The first build of
the feature, before the restart, proxied the company's MCP servers on the runner host with the token in
`run.assign`; the restart's ADR-0039 rejects that path, so the feature was rebuilt in the restart's shape
([ADR-0040](../adr/0040-mcp-tool-connections.md)): a connection of kind `MCP` is a remote MCP server the company
runs; the server reads its tools into a catalogue on create and on "Read tools" (the test), owners and admins allow or
deny each tool for the whole company, and an agent's tool access to such a connection names the tools it may call. A
run lists the granted, present and allowed tools as `{handle}_{name}` with the server's own input schema next to the
reads of the trackers, and a `TOOL` request of one is checked like a read and executed by the server:
`initialize`, `notifications/initialized` and `tools/call` at the connection's base URL through the guarded outbound
client, one session per call, with the connection's token revealed for the run. The result reaches the agent as the
server sent it (text blocks, structured content, the error flag; a block the frame cannot carry is named); a JSON-RPC
error is an error result. The token never leaves the server; a tool the server dropped keeps its policy and the
agents' grants until it is listed again; a denied tool is called by nobody. The web app connects an MCP server
(endpoint, optional token, token header), shows the catalogue with a checkbox per tool, and the agent dialog ticks the
tools of each MCP connection, with "All" and "None". The guide is
[operations/mcp-servers.md](../operations/mcp-servers.md), with a minimal server in Node.js.
