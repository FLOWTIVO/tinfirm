# tinfirm-server

The Tinfirm control-plane server: a Spring Boot 4.1 app on Java 25. It serves the JSON API (`/api/**`), the OIDC login flow and the SPA, and also the runner hosts' WebSocket endpoint with the model relay, each company's MCP endpoint for people's AI clients, and Tinfirm's own OAuth 2.1 authorization server.
The binding contracts are [`docs/CONVENTIONS.md`](../docs/CONVENTIONS.md) and [`api/openapi.yaml`](../api/openapi.yaml).

## Build and test

```bash
./mvnw -B verify        # needs Docker: the tests start PostgreSQL 18 with Testcontainers
./mvnw -B test -Dtest=TenantIsolationTest   # a single test class
```

The tests connect as the real `tinfirm_app` role, so row-level security is exercised. Flyway runs as `tinfirm_owner`.
The build also compiles the sources of the shared libraries `libs/jira`, `libs/litellm` and `libs/net` and runs their tests (CONVENTIONS §2).

## Run locally against the Compose database

Start only the `postgres` service of `deploy/compose/compose.yaml` (`make dev-db`). Then:

```bash
export SPRING_DATASOURCE_URL=jdbc:postgresql://localhost:5432/tinfirm
export SPRING_DATASOURCE_USERNAME=tinfirm_app   SPRING_DATASOURCE_PASSWORD=<from deploy/compose/.env>
export SPRING_FLYWAY_USER=tinfirm_owner         SPRING_FLYWAY_PASSWORD=<from deploy/compose/.env>
export TINFIRM_VAULT_KEYS="dev:<base64 of 32 random bytes>"  TINFIRM_VAULT_ACTIVE_KEY=dev   # openssl rand -base64 32
export TINFIRM_BOOTSTRAP_ADMIN_EMAIL=admin@example.com  TINFIRM_BOOTSTRAP_ADMIN_PASSWORD=<at least 12 characters>
export TINFIRM_COMPANIES_MAIN_NAME="My Company"   # a declared company, owned by the bootstrap admin (ADR-0075)
./mvnw spring-boot:run
```

- API and SPA: <http://localhost:8080>. Management: <http://localhost:8081/actuator/health/liveness>, `/readiness`, `/actuator/prometheus`.
- The server refuses to start without valid vault keys, and with an invalid company declaration (`TINFIRM_COMPANIES_<KEY>_*`) or a provider that names an undeclared company (CONVENTIONS §5).
- When the user table is empty and both bootstrap variables are set, the server creates the first instance admin. It refuses to start when the admin's email is invalid or the password is shorter than 12 characters. At every start it then creates or adopts each declared company, and makes its declared owner (the bootstrap admin unless a declaration names another) its OWNER while it has none ([ADR-0075](../docs/adr/0075-companies-and-sign-in-from-the-deployment.md)). A company name is 1 to 100 characters.
- Without `TINFIRM_MODEL_GATEWAY_ADMIN_URL` and `TINFIRM_MODEL_GATEWAY_ADMIN_KEY` no LiteLLM is bundled, so no budget pays for a run until a company configures its own ([CONVENTIONS §15.4](../docs/CONVENTIONS.md#154-model-access-and-runner-hosts)). `make up` runs the whole stack, LiteLLM and the model port included.
- The SPA is not part of this module. The Docker build (the repository's `Dockerfile`) copies the Angular build into `src/main/resources/static/`. During development, use `npm start` in `web/`.
- Logs are structured JSON (ECS) on stdout.

The database needs both roles, and `tinfirm_owner` must own the database, and with it the `public` schema.
`src/test/resources/db/test-roles.sql` shows the minimum.

### The outbound guard

The guard ([CONVENTIONS §14.4](../docs/CONVENTIONS.md#144-invariants)) lives in `shared.net`: `OutboundUrls` checks a URL, `AddressGuard` the addresses its host resolves to, and `GuardedResolverProvider`, the JVM's resolver (`META-INF/services/java.net.spi.InetAddressResolverProvider`, installed from the image's class path and from the executable jar), answers the connect-time lookups of every host in `GuardedHosts` without those addresses, so DNS rebinding cannot reach them. Its users:

- the system module's outbound client, [`system/internal/http/OutboundHttp.java`](src/main/java/com/flowtivo/tinfirm/system/internal/http/OutboundHttp.java): every call to a company system, a member's personal MCP server included. Without private addresses allowed, it refuses to start when the resolver is not installed. A read (`GET`) that the system answers with 502, 503 or 504, or that fails to connect, is tried again at most twice, after 0.5 s and 2 s (a 503's `Retry-After` of at most 5 s instead); a write is never tried again;
- the identity module's fetch of OAuth client metadata documents (https only, never a private address);
- the model module's client of a company's own LiteLLM (`GatewayHttp`): its admin API and the model requests the relay forwards there. The bundled LiteLLM is the operator's address and is reached as configured.

When the resolver is not installed, the identity and model clients refuse to send a request that needs the guard.

### How the pieces fit

- **Generated API.** `openapi-generator-maven-plugin` writes the interfaces and DTOs to `target/generated-sources/openapi` on every build. It uses the `spring` generator with `interfaceOnly`, `useSpringBoot4` and `useJackson3`. `src/main/openapi-templates/pojo.mustache` is the upstream template with two changes: `toString()` masks `writeOnly` fields, and optional arrays and maps start as `null` instead of empty, so an omitted array differs from `[]`.
- **Tenant context.** The application `DataSource` is wrapped by `TenantAwareDataSource`. When any transaction begins, it writes `app.company_id`, `app.user_id`, `app.instance_admin` and `app.system` with `set_config(..., true)`. Work outside a transaction sees no tenant rows. A request enters a company only through the `CompanyAccessGuard`, after it has checked access (`TenantScope.enterCompany`); the other callers of `enterCompany` are trusted server code (creating a company, the vault's reveal and scan, the suspensions that an instance admin's deactivation of a user makes). Server-side work runs in `SystemContext`: `call` instance-wide (the only context with `app.system`), `callInCompany` for one company, `callUnscoped` for none.
- **Migrations.** `src/main/resources/db/migration`, `V001__baseline.sql` to `V080`. `V001` is the fresh baseline of the platform redesign ([the design record](../docs/reviews/2026-10-12-platform-redesign.md), Part 9; ADR-0058): no data is migrated from the design of 2026-10-05. Never edit a released migration.
- **Module ports.** Dependencies point one way ([CONVENTIONS §10](../docs/CONVENTIONS.md#10-server-code-conventions)). Where a lower module needs something of a higher one, it defines a port that the higher module implements and that it looks up when used: `MembershipDirectory` (identity, implemented by company), `PrincipalDependents` (what goes with a principal), `RunnerSessionListener` (the run side of the runner protocol), `TurnSource` (a turn's content, from the conversation module).
- **Cross-company work.** The runner endpoint finds the host of a token before it knows the company. It calls the narrow `SECURITY DEFINER` function `runner_host_for_token` (the baseline migration), owned by the schema owner with a fixed `search_path`, executable only by the runtime role, which returns the host id and the company id only. Everything else happens in the tenant context of that company (`SystemContext.callInCompany`, `SystemTransactions`), under the normal policies. The owner role gets a SELECT-only policy on `runner_host` for this function; the runtime role never matches it.
- **Runner endpoint.** `/api/runner/v1/**` has its own security filter chain (no session, no CSRF): the WebSocket, the runner hosts' file and skill endpoints, and the model relay. The WebSocket handler authenticates the `Bearer` host token and closes with 4401 when it is bad; the file and skill endpoints take the host token too (`RunnerAuthentication`), and the relay a run's one-run token. Frames are validated (Bean Validation on the `RunnerMessages` records plus payload checks) and never logged. Inbound frames are limited to `tinfirm.runner.max-message-bytes` (1 MiB).
- **Runner protocol versions ([CONVENTIONS §14.10](../docs/CONVENTIONS.md#1410-runner-protocol-v2)).** A host's `hello` names protocol 1 or 2; the connection speaks it from then on: the codec decodes the frames of that version, and `welcome.protocolVersion` echoes it (`RunnerConnections.protocolVersion`). Runs go to v2 hosts only (`run/internal/RunnerSessionHandler.java`): the dispatcher picks hosts that speak v2, and a v1 host's `run.ask`, `run.repository_request` and `run.task_create` are answered `REJECTED` / `RUN_NOT_ACTIVE`. A v2 `run.request` of kind `TOOL` is checked in a short transaction, then executed off the connection's thread (`RunRequestRouter`, on the virtual threads of `RunWorkers`) by the conversation module's `ToolCalls`, bounded by `TINFIRM_RUN_TOOL_TIMEOUT`, and its ack goes to the host's current connection with `RunnerConnections.send`. Tests: `FakeRunner` says hello in v1 unless it sends `helloV2`, and validates every server frame against the schema of its version.
- **Runner capacity ([ADR-0016](../docs/adr/0016-runner-capacity-settings.md)).** A host reports its ceilings in `hello`. OWNER and ADMIN for a company host, or the owner for a personal host, store a desired number of concurrent runs (`PATCH` on the runner host), which bumps `runner_host.config_version`. The endpoint sends `host.config` right after `welcome` (before any other frame) and after every change, with that value and no credential pools, and a connection takes runs only after its first `host.config.applied` (`RunnerConnections.isConfigured`). A personal host's subscription takes as many runs at once as the pool it reports. Tests: `FakeRunner` answers `host.config` itself unless `manualConfig()` is set.
